# 팩: 게임 기획·규칙 (TR-10)

> 특성 카탈로그 TR-10이 `해당`일 때 PM·ARCH가 함께 읽는다(레지스트리 `SK-PACK`). `해당(대체)`(게임 규칙은 범위 밖이고 판 흐름만 다룸)이면 이 팩은 읽지 않는다.
> 기획 모드(프로파일 §1 "PM 진행 방식: 기획")에서는 1절이 P1.5 기획안의 체크리스트다. 분석 모드에서는 1절을 P2 질문 목록으로 쓴다.
> 예시(장르, 인원, 수치, 이름)는 형식을 보여 줄 뿐 프로젝트 사실이 아니다. 값은 요구사항·사용자 답변·채택된 제안에서 가져온다.
> 함께 판정할 특성: 실시간 진행이면 TR-03(실시간 팩), 턴 시간 제한이 있으면 TR-05, 매칭이 있으면 TR-04(매칭 팩), 점수·순위가 있으면 TR-16, 게임 화면이 있으면 TR-09.

## 1. PM

### 1.1 기획안 요소 (P1.5 체크리스트, 분석 모드에서는 P2 질문)
요소마다 "정해짐 / 빈칸"을 판정하고, 빈칸은 제안(`PRO-xx`)으로 대안 2~3개를 낸다(작성 규칙은 PM 스킬 P1.5). **1차 차수에는 컨셉·진행 형태·매치 구조·코어 루프만** 묻고, 나머지는 2차에 묶어서 묻는다. 이탈·공정성 규칙의 주인은 이 표이고, 실시간 팩·매칭 팩의 이탈 관련 질문은 이 답을 참조한다(다시 묻지 않는다).

| 요소 | 정할 것 | 대안의 예 |
|---|---|---|
| 컨셉 | 한 문장 설명, 플레이어가 느낄 재미(경쟁·협동·수집·퍼즐 등) | "4인 실시간 퀴즈 대전" / "2대2 턴제 카드 대전" |
| 대상·세션 | 누가, 한 판에 몇 분, 어디서(브라우저·모바일 브라우저) | 3분 이내 / 10분 내외 |
| 진행 형태 | 라운드 제출형(모두 행동을 제출한 뒤 함께 판정, 가장 단순) / 차례형(한 명씩 차례로) / 연속 실시간(이동·충돌처럼 끊김 없이 진행) | 연속 실시간은 1.2의 연속 진행 형식과 지연 NFR이 필요하고 만드는 양이 크다 |
| 매치 구조 | 인원, 개인전·팀전, 라운드·턴 수, 판 시작 조건 | 4인 개인전 / 2대2 팀전 |
| 코어 루프 | 플레이어가 반복하는 행동 → 즉시 받는 결과 → 보상의 한 바퀴 | 답 고르기 → 정답 공개 → 점수 |
| 핵심 규칙 | 할 수 있는 행동, 행동이 언제 무효인지, 판정 방법 | 먼저 맞힌 사람만 점수 / 맞힌 사람 모두 점수 |
| 승리·종료 | 판이 끝나는 조건, 승패·순위 결정, 무승부 | 라운드 N개 후 합계 / 목표 점수 선착 |
| 이탈·공정성 | 중간에 나간 사람, 늦은 응답, 같은 시각 행동의 처리, 조작해도 괜찮은 게임인지(판정을 서버가 확정해야 하는지 — 위치는 ARCH가 정한다) | 이탈자 패배 처리 / 남은 사람끼리 계속 |
| 밸런스 변수 | 나중에 조정할 값(시간 제한, 점수 배분, 라운드 수 등)과 초기값·허용 범위 | 아래 1.3 |
| 진행·보상 | 판 밖에서 쌓이는 것(전적, 점수, 등급 — TR-16) | 전적만 / 전적 + 실력 점수 |
| 시작 경험 | 처음 들어온 사람이 규칙을 아는 방법 | 첫 판 전 안내 / 판 안 도움말 |
| 제외할 것 | 이번 범위에서 하지 않을 것(아이템, 채팅, 관전 등) | — |

- 원문에 근거가 있는 요소는 제안하지 않고 REQ를 그대로 쓴다.
- 대안끼리 서로 다른 특성 판정을 부르면(예: 실시간 진행 → TR-03, 턴 시간 제한 → TR-05) 쉬운 설명의 "무엇이 달라지나"에 적는다.

### 1.2 P3 게임 상태 흐름 (형식)
판 상태와 판 안의 라운드·턴 상태를 따로 쓴다. 상태 이름은 예시다.

**판**
| 상태 | 들어오는 전이 (주체) | 나가는 전이 (주체) |
|---|---|---|
| 시작 전 | 판 생성 (시스템, 매칭 성사 등) | 시작 (시스템, 시작 조건 충족) / 무산 (시간) |
| 진행 중 | 시작 | 종료 조건 충족 (시스템) / 무효 (시스템, 규칙에 따름) |
| 끝남 | 종료 | — (결과 확정) |

**라운드·턴** (진행 형태가 라운드 제출형·차례형일 때)
| 상태 | 들어오는 전이 (주체) | 나가는 전이 (주체) |
|---|---|---|
| 행동 대기 | 라운드 시작 (시스템) | 행동 제출 (플레이어) / 제한 시간 만료 (시간, TR-05) |
| 판정 | 모두 제출 또는 만료 | 결과 공개 (시스템) |

**연속 진행** (진행 형태가 연속 실시간일 때, 라운드·턴 표 대신)
| 항목 | 정할 것 |
|---|---|
| 상태 갱신 | 다른 플레이어의 변화가 화면에 반영되는 빈도(예: 초당 N번) |
| 지연 허용 | 조작부터 다른 사람 화면 반영까지 허용 지연(NFR, 실시간 팩 1.3 형식) |
| 판 도중 복귀 | 끊겼다 돌아온 사람이 판에 다시 들어오는 방법(실시간 팩 "현재 상태 보기") |

**규칙 INV 예시**
- `INV-xx 끝난 판의 결과는 바뀌지 않는다`
- `INV-xx 한 라운드에 한 플레이어는 행동을 한 번만 제출한다`
- `INV-xx 판정은 서버가 확정한다(클라이언트가 보낸 결과를 그대로 쓰지 않는다)` (판정 권위를 ARCH에 넘기면 `AQ-`로)

### 1.3 밸런스 변수 (`BAL-xx`)
나중에 조정할 수 있어야 하는 값을 표로 쓴다. 값 자체는 기획 결정이고, 어디에 저장하는지는 ARCH가 정한다.

| BAL-ID | 이름 | 단위 | 초기값 | 허용 범위 | 쓰는 규칙 | 관련 설정·규칙 | 바꾸는 사람·시점 |
|---|---|---|---|---|---|---|---|
| BAL-01 | 라운드 제한 시간 | 초 | 15 | 5~60 | 라운드 행동 대기 | — | 개발자, 배포할 때 |

- 초기값 근거가 없으면 질문하거나 제안(`PRO-xx`)으로 낸다. 허용 범위도 근거(답·제안·채택)를 단다.
- 단위를 반드시 쓴다(초·밀리초가 섞이면 경계 실수가 생긴다).
- 다른 설정·규칙에 기대는 값(예: 등수별 점수의 개수는 매치 인원에 기댐)은 "관련 설정·규칙"에 적고, 그 설정이 바뀔 때의 규칙을 PM이 정한다.
- 기획 모드에서는 P1.5에서 `BAL 후보` 번호를 매겨 보여 주고, P3에서 이 표로 확정한다.
- "바꾸는 사람·시점"의 가장 단순한 선택지는 "개발자, 배포할 때"다. "운영자가 서비스 중에 바꾼다"를 고르면 운영 기능이 생기므로 TR-11(운영·관리자)을 판정 대상으로 올린다.
- "진행 중인 판에 바뀐 값을 적용하는가"를 반드시 정한다(가장 단순: 적용하지 않음, 판 시작 때의 값을 끝까지 씀).

### 1.4 P6 판정 AC (형식)
```
AC-12-3
Given 라운드 3이 "행동 대기"이고 A와 B가 아직 제출하지 않았다
When A가 정답을 제출하고, 1초 뒤 B가 정답을 제출한다
Then 규칙(PRO-04 채택: 먼저 맞힌 사람만 점수)에 따라 A만 점수를 얻는다
 And B의 제출은 "늦은 정답"으로 기록되고 점수는 그대로다
```
- 같은 입력이면 같은 결과가 나와야 하는 판정은 AC에 "같은 입력 → 같은 결과"를 적는다(결정성).
- 경계 AC를 쓴다: 제한 시간 만료 직전·직후 제출, 동시 제출, 이탈자의 제출.

### 1.5 P7 화면 (TR-09도 `해당`일 때)
최소 화면 후보: 로비(게임 찾기), 매칭 대기, 판 진행(HUD: 남은 시간·점수·상대 상태), 결과. 화면마다 연결 끊김·재접속 중 표시는 실시간 팩 1.4를 따른다.

## 2. ARCH

### 2.1 A2 결정 (카탈로그 "ARCH 결정"을 ADR로 쓸 때의 선택지)

**판정 권위**
| 옵션 | 맞는 경우 | 감수할 점 |
|---|---|---|
| 서버 권위(서버가 상태를 갖고 모든 판정) | 경쟁 게임, 조작 방지가 중요 | 서버 부담, 지연이 체감될 수 있음 |
| 클라이언트 계산 + 서버 검증 | 즉각 반응이 중요하고 검증 규칙이 단순 | 검증 규칙을 따로 유지, 불일치 처리 |
| 클라이언트 신뢰 | PM이 "조작해도 괜찮다"고 정한 경우만(협동·연습 등), 가장 단순 | 조작 가능. 이 옵션이면 조작 입력 거부 게이트는 빼고 그 이유를 적는다 |

**진행 방식**
| 옵션 | 맞는 경우 | 감수할 점 |
|---|---|---|
| 행동 단위 처리(행동이 올 때마다 판정) | 턴제, 행동 빈도가 낮음, 가장 단순 | 시간 만료는 별도 계기(TR-05) |
| 서버 주기 갱신(고정 간격으로 상태 계산) | 실시간 물리·이동 | 주기 실행 관리(TR-06), 부하 |

**게임 상태 저장**: 진행 중 판 상태를 메모리에만 둘지, 저장소에 둘지(재시작 시 진행 중 판을 살릴지 — PM 요구에 따름). 끝난 판의 결과·기록 저장 형식.
- 메모리 상태를 고르면: 실시간 팩의 순번(`seq`)은 판 상태의 메모리 버전으로 매기고, 재동기화 스냅샷도 같은 메모리에서 준다(실시간 팩 "순번 규칙"의 예외로 ADR에 적는다). 판 하나는 한 프로세스에서만 처리해야 하므로(프로세스 하나로 실행하거나 판을 프로세스에 고정), 실시간 팩 "연결 상태 저장과 전달" 결정과 같은 ADR로 묶는다.
- 연속 실시간이면 클라이언트 예측·보간은 FE 영역이다. 서버는 정한 갱신 주기로 상태를 보내고, 범위에 넣을지는 PM 요구를 따른다.

**판정 권위**: "조작해도 되는가"는 PM이 정하고(1.1 이탈·공정성), ARCH는 위 표에서 판정 위치를 정한다.

**밸런스 변수 위치**: 코드 상수 / 설정 파일 / 저장소 표. PM이 정한 "바꾸는 사람·시점"이 근거다(운영 중 바꿔야 하면 코드 상수는 맞지 않는다).

**난수**: 판정에 난수가 있으면 서버가 시드를 정하고, 같은 시드면 같은 결과가 나오게 한다(재현·테스트용). 도메인 메서드는 난수를 인자로 받는다.

### 2.2 A3·A4 설계 메모
- **판정은 순수 함수로 둔다**: 입력(현재 판 상태, 행동, 현재 시각, 난수원, 밸런스 변수) → 출력(새 상태, 일어난 일 목록). 저장·발행은 응용 계층이 한다.
- 밸런스 변수는 BAL-ID를 그대로 설정 키·컬럼 이름에 연결한다(A3 테이블 정의 또는 설정 문서). "진행 중인 판에 적용하지 않음"이면 판 시작 때 BAL 값을 판 상태에 복사해 끝까지 쓴다.
- 판 진행 중 행동은 TR-03이면 이벤트(EVT)로, 아니면 HTTP API로 명세한다. 행동마다 거부 사유(차례 아님, 시간 초과, 이미 제출 등)를 결과 종류로 정한다(A4 에러 모델 대응표).
- 끝난 판의 결과 기록은 TR-16(레이팅)과 같은 트랜잭션인지 정한다.

### 2.3 A5 실행 흐름
최소 SEQ: 판 시작(참가자 확인 → 초기 상태 → 알림), 행동 처리(검증 → 판정 → 저장 → 알림), 라운드·턴 시간 만료(TR-05), 이탈 처리, 종료 판정과 결과 확정.

### 2.4 A7 게이트·테스트
| 대상 | 확인 방법 |
|---|---|
| 규칙 | 판정 순수 함수에 규칙표의 입력을 넣어 결과 비교(규칙마다 한 케이스 이상) |
| 결정성 | 같은 시드·같은 입력으로 두 번 실행해 같은 결과 |
| 경계 | 시간 만료 직전·직후, 동시 제출을 고정 시각으로 재현 |
| 조작 | 차례가 아닌 행동, 범위 밖 값, 이미 끝난 판에 대한 행동이 거부되는지(클라이언트 신뢰 옵션이면 뺀다) |
| 밸런스 변경 | BAL 값을 바꿔도 진행 중 판에는 적용되지 않는지(PM 규칙대로) |
