# 팩: 매칭·대기열 (TR-04)

> 특성 카탈로그 TR-04가 `해당`일 때 PM·ARCH가 함께 읽는다(레지스트리 `SK-PACK`). 카탈로그 항목을 대신하지 않고, **어떻게 쓰는지**(질문 목록, 산출물 형식, 선택지)를 더한다.
> 이 팩의 예시(상태 이름, 인원, 시간)는 형식을 보여 줄 뿐 프로젝트 사실이 아니다. 값은 요구사항·제약·사용자 답변·ADR에서 가져온다.
> 함께 판정할 특성: 매칭 결과를 실시간으로 알리면 TR-03(실시간 팩), 준비 확인·대기 만료·조건 완화가 있으면 TR-05, 주기 실행을 쓰면 TR-06, 실력 점수를 쓰면 TR-16, 매치 뒤 게임이 이어지면 TR-10.
> 참가 방식이 **대기열(자동 매칭)**이면 1.2·2.1의 대기열 형식을, **로비(사용자가 방을 고름)**면 1.3·2.2의 로비 형식을 쓴다. 둘 다면 둘 다 쓴다.

## 1. PM

### 1.1 P2 확인 질문 (카탈로그 관점 행을 채울 때 빠짐없이 훑는다)
| 묶음 | 확인할 것 |
|---|---|
| 참가 방식 | 자동 매칭(대기열)인가, 사용자가 방을 고르는가(로비), 둘 다인가 |
| 매치 구성 | 매치당 인원, 팀 수·팀당 인원, 인원이 덜 차면 시작할 수 있는가 |
| 묶는 조건 | 실력·지역·지연·게임 모드 등 무엇을 맞추는가. 조건이 없으면 순서대로 묶는가 |
| 조건 완화 | 오래 기다리면 조건을 넓히는가. 최대 대기 시간과 그때의 처리(취소 / 조건 없이 매칭) |
| 파티 | 여러 명이 함께 대기열에 들어갈 수 있는가. 파티는 같은 팀으로 묶이는가 |
| 준비 확인 | 매칭 직후 참가자가 수락해야 하는가(없어도 된다). 있으면 제한 시간, 거절·무응답 시 나머지 사람의 처리(다시 대기열 앞쪽으로 / 처음부터) |
| 연결 끊김 | 대기 중·준비 확인 중·방 안에서 연결이 끊기면 대기 항목·참가를 유지하는가, 유예 뒤 빼는가 |
| 취소·이탈 | 대기 중 취소, 매칭 직후 이탈, 게임 중 이탈의 결과와 불이익 |
| 동시 참여 | 한 사람이 대기열 두 개에 동시에 있거나, 대기 중에 다른 방에 들어갈 수 있는가 |
| 공정성 | 먼저 들어온 사람이 먼저 매칭되는가. 같은 조건이면 순서를 지키는가 |
| 로비 규칙 (로비일 때) | 방 만들기·제목·공개 여부, 팀 선택, 방장 권한과 방장 이탈 시 처리, 시작 조건, 해산 조건 |
| 규모 | 동시 대기 인원·방 수, 목표 매칭 대기 시간 |

### 1.2 P3 대기열 상태 흐름 (형식, 대기열 방식일 때)
대기 항목과 매치를 따로 쓴다. 상태 이름은 예시다. "(준비 확인을 쓸 때)" 행은 P2 답이 "준비 확인 없음"이면 빼고, 매칭되면 바로 매치 확정으로 간다.

**대기 항목** (한 사람 또는 한 파티의 대기열 등록)
| 상태 | 들어오는 전이 (주체) | 나가는 전이 (주체) |
|---|---|---|
| 대기 중 | 등록 (사용자) / 재대기: 상대의 거절·무응답으로 매치 무산 (시스템, 준비 확인을 쓸 때) | 매칭됨 (시스템) / 취소 (사용자) / 대기 만료 (시간) / 연결 이탈 (시스템, 규칙에 따라) |
| 매칭됨 | 매칭 성사 (시스템) | 매치 확정 (시스템) / 재대기 (시스템) / 본인 거절·무응답 (사용자·시간) |
| 종료 | 확정·취소·만료·이탈 | — |

**매치**
| 상태 | 들어오는 전이 (주체) | 나가는 전이 (주체) |
|---|---|---|
| 준비 확인 중 (준비 확인을 쓸 때) | 매칭 성사 (시스템) | 전원 수락 (사용자) / 거절·시간 초과 (사용자·시간) |
| 확정 | 전원 수락 또는 매칭 성사 | 게임 시작 → 이후 상태는 TR-10 게임 상태 표로 넘긴다 |
| 무산 | 거절·시간 초과 | — (수락한 사람은 재대기, 규칙에 따름) |

**INV 예시**
- `INV-xx 한 사용자는 활성 대기 항목(대기 중·매칭됨)을 최대 1개 가진다`
- `INV-xx 한 사용자는 동시에 활성 매치(준비 확인 중·확정, 그리고 TR-10의 진행 중 게임) 하나에만 속한다`
- `INV-xx 확정된 매치의 인원은 매치 구성 인원과 같다`

### 1.3 P3 로비 상태 흐름 (형식, 로비 방식일 때)
| 상태 | 들어오는 전이 (주체) | 나가는 전이 (주체) |
|---|---|---|
| 모집 중 | 방 만들기 (사용자) / 인원 이탈 (사용자·시스템) | 가득 참 (시스템) / 시작 (방장) / 해산 (방장·시스템) |
| 가득 참 | 마지막 자리 참가 (사용자) | 인원 이탈 → 모집 중 / 시작 (방장) / 해산 |
| 시작됨 | 시작 (방장, 시작 조건 충족 시) | 이후 상태는 TR-10 게임 상태 표로 넘긴다 |
| 해산 | 방장 해산, 마지막 인원 이탈, 시작에 따른 해산 등 (규칙에 따름) | — |
- 방 정원·팀 정원은 경쟁 자원이므로 TR-02도 판정한다(참가·팀 변경의 동시 요청).
- 방장 이탈 시 방장 승계 / 해산 중 무엇인지 INV나 상태 표에 적는다.

### 1.4 P4 D-003에 넣을 규칙
매치 구성, 묶는 조건과 완화 규칙, 최대 대기 시간, 준비 확인 여부·제한 시간·거절 처리, 연결 끊김 처리, 파티 규칙, 이탈 불이익, (로비) 방장 권한·시작·해산 조건. 이 규칙들은 되돌리기 비용이 커서 결정 카드로 확인받는다.

### 1.5 P6 AC·NFR (형식)
```
AC-05-3
Given 매치 구성이 4명이고 대기 중인 사용자가 3명이다
When 네 번째 사용자가 대기열에 등록한다
Then 4명 모두의 대기 항목이 "매칭됨"이 되고, 하나의 매치가 만들어진다
 And (TR-03이면) 4명 모두 N초 안에 "매칭 성사" 이벤트를 받는다
```
- 대기 취소 AC, 이미 대기 중인 사용자의 중복 등록 거부 AC, 연결 끊김 AC를 각각 하나 이상 쓴다. 준비 확인을 쓰면 거절·시간 초과 AC도 쓴다.
- 로비면 참가·이탈·팀 변경·시작·해산 AC와 정원이 찬 방 참가 거부 AC를 쓴다.

**NFR 행 (해당하는 것만, 수치는 근거에서)**
| 영역 | 기준 형식 |
|---|---|
| 정합성 | 동시 등록·참가 M건 후 이중 배정 0, 정원 초과 0 |
| 대기 시간 | 대기 인원 충분 조건에서 매칭 대기 p95 N초 이하 |
| 공정성 | 같은 조건의 대기자는 등록 순서대로 매칭 |

## 2. ARCH

### 2.1 A2 결정: 대기열 방식 (카탈로그 "ARCH 결정"을 ADR로 쓸 때의 선택지)

**매칭 실행 방식**
| 옵션 | 맞는 경우 | 감수할 점 |
|---|---|---|
| 등록 요청 안에서 즉시 매칭 | 조건이 단순(순서대로·인원만), 규모가 작음, 가장 단순 | 등록 요청이 매칭 계산을 떠안음, 조건 완화·만료처럼 시간이 계기인 일은 별도 계기 필요(TR-05) |
| 주기 실행(앱 안 반복 작업) | 조건 완화·만료처럼 시간에 따라 다시 봐야 함 | 여러 프로세스면 중복 실행 방지 필요, 앱 수명주기와 함께 시작·정지, TR-06 판정 |
| 별도 작업자 프로세스 | 규모가 크거나 매칭 계산이 무거움 | 배포 단위 추가(TR-13), 프로세스 간 전달 |

가장 단순한 옵션(등록 요청 안에서 즉시)을 반드시 비교에 넣는다. 시간 전이(대기 만료·준비 확인 시간 초과·조건 완화)를 무엇이 부를지는 실시간 팩의 재접속 유예와 함께 **TR-05 실행 방식 ADR 하나**로 정한다.

**대기열 상태 저장 위치**
| 옵션 | 감수할 점 |
|---|---|
| 영속 저장소의 테이블 | 재시작에도 유지, 잠금으로 원자성 확보 가능. 조회 부하 |
| 공유 메모리 저장소 | 빠름, 여러 프로세스 공유. 의존성 추가(ADR), 영속 기록은 따로 |
| 한 프로세스 메모리 | 가장 빠르고 단순. 프로세스 하나로만 실행 가능, 재시작 시 대기열 소실 |
- 대기열을 휘발 상태로 둘지 영속 상태로 둘지는 P2 코어 관점("무엇을 영속 저장하는가")의 답을 따른다.

**배정의 원자성** (이중 배정 방지, TR-02 동시성 ADR과 묶을 수 있다). 매칭 실행 방식에 맞는 옵션을 고른다.
| 옵션 | 맞는 실행 방식 | 감수할 점 |
|---|---|---|
| 대기열 단위 잠금 하나: 대기열(모드·풀)을 나타내는 행 하나를 잠그고 그 안에서 후보 조회·배정 (한 프로세스 메모리면 프로세스 안 잠금 하나) | 즉시 매칭. 가장 단순 | 같은 대기열의 등록이 한 줄로 처리됨(규모가 커지면 병목) |
| 후보 행 잠금, 이미 잠긴 행은 건너뛰기 | 주기 실행·별도 작업자 (실행 주체가 여럿일 때 서로 다른 후보를 가져가게) | 즉시 매칭과 함께 쓰면 동시 등록끼리 서로의 행을 건너뛰어 아무도 매칭하지 않을 수 있다(다시 시도할 계기가 없음). 이 조합은 쓰지 않는다 |
| 조건부 갱신(상태가 "대기 중"일 때만 바꿈) 후 바뀐 행 수 확인 | 모두 | 일부만 성공했을 때 되돌림 처리 |
| 매칭을 한 실행 주체만 수행(단일 작성자) | 주기 실행 | 그 주체가 멈추면 매칭 정지, 감시 필요 |
- 여러 행을 잠글 때는 정해진 정렬 키(예: 등록 시각, 식별자) 순서로 잠근다(교착 방지).
- 저장소 제약으로 INV "활성 대기 항목 최대 1개"를 함께 막을지 정한다(A3 INV 보호 위치).

### 2.2 A2 결정: 로비 방식
- 참가·팀 변경·시작은 **방 행 잠금 후 인원·상태 확인**이 가장 단순하다(TR-02 동시성 ADR의 형식을 그대로 쓴다).
- 방 목록 조회와 방 상세의 갱신 방식(실시간 이벤트 / 주기 조회 / 수동 새로고침)은 TR-03 판정과 실시간 팩의 전송 방식 결정을 따른다.
- 시작·해산 뒤 방이 어떤 상태로 남는지(조회 가능 여부, 410 같은 구분 응답 여부)를 A4 오류 모델에 적는다.

### 2.3 A3·A4 설계 메모
- **매칭 계산은 순수 함수로 둔다**: 입력(대기 항목 목록, 현재 시각, 조건) → 출력(묶인 그룹 목록). 저장·잠금·알림은 응용 계층이 한다. 시각과 입력 순서를 고정해 결정적으로 테스트할 수 있다.
- 시간 전이(대기 만료, 준비 확인 시간 초과)도 현재 시각을 인자로 받는 도메인 메서드로 쓴다(예: `expire(now)`).
- 대기 항목에 필요한 값(예시): 사용자 또는 파티 식별자, 등록 시각, 묶는 조건 값, 상태, 매치 식별자(매칭 후). TR-03이면 대상 상태의 버전 값(실시간 팩 "순번 규칙").
- 매칭 결과를 알리는 인터페이스: TR-03이면 이벤트(EVT, 아직 방이 없는 대기자에게 보낼 곳은 실시간 팩 "연결 구조와 구독"에서 정한다), 아니면 상태 조회 API와 그 갱신 방식(PAGE).

### 2.4 A5 실행 흐름
최소 SEQ (대기열): 대기 등록(중복 등록 거부 포함), 매칭 성사(원자적 배정 → commit → 알림), 준비 확인 수락·거절·시간 초과(쓸 때), 대기 취소(매칭과 동시에 일어나는 경우 포함), 연결 끊김 처리, 매칭 후 이탈, **기동 시 남은 활성 대기 항목 정리**(휘발 상태와 영속 기록이 어긋나지 않게).
최소 SEQ (로비): 방 만들기, 참가(정원 확인), 팀 변경, 이탈(방장 이탈 포함), 시작, 해산.
- "취소와 매칭이 동시에 일어날 때" 어느 쪽이 이기는지 원자성 결정으로 정하고 SEQ에 적는다.

### 2.5 A7 게이트·테스트
| 대상 | 확인 방법 |
|---|---|
| 이중 배정·정원 초과 | 많은 사용자의 동시 등록·참가 후 활성 매치 소속 수, 방 인원 확인 |
| 매칭 정지 | 동시 등록 직후 대기자가 매치 구성 인원 이상 남아 있지 않은지 확인 |
| 매칭 규칙 | 순수 매칭 함수에 고정 입력·고정 시각을 넣어 결과 비교 |
| 조건 완화·만료 | 현재 시각을 주입해 대기 시간 경과를 대기 없이 재현(TR-05) |
| 공정성 | 같은 조건의 등록 순서와 매칭 순서 비교 |
| 취소 경쟁 | 취소와 매칭을 동시에 실행해 INV 유지 확인 |
| 기동 정리 | 남은 활성 대기 항목이 있는 상태로 기동해 정리 결과 확인 |
