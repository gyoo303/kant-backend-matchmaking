# 팩: 실시간 상호작용 (TR-03)

> 특성 카탈로그 TR-03이 `해당`(또는 `해당(대체)`)일 때 PM·ARCH가 함께 읽는다(레지스트리 `SK-PACK`). 카탈로그 항목을 대신하지 않고, **어떻게 쓰는지**(질문 목록, 산출물 형식, 선택지)를 더한다.
> 이 팩의 예시(이벤트 이름, 수치, 상태 이름, 주소)는 형식을 보여 줄 뿐 프로젝트 사실이 아니다. 수치와 이름은 요구사항·제약·사용자 답변·ADR에서 가져온다.
> 스택 이름(특정 프레임워크·라이브러리)은 쓰지 않는다. 스택별 주의 사항은 ARCH가 A6에서 `05-structure-conventions.md` "스택 주의" 절(IC-12)에 쓴다.

## 1. PM

### 1.1 P2 확인 질문 (카탈로그 관점 행을 채울 때 빠짐없이 훑는다)
| 묶음 | 확인할 것 |
|---|---|
| 무엇이 실시간인가 | 서버가 먼저 알려야 하는 변화 목록(누가 무엇을 하면 누구에게 무엇이 보이는가). 실시간이 아니어도 되는 것(새로고침으로 충분한 것) |
| 수신 대상 | 한 사람 / 같은 방·그룹 / 전체. 아직 방에 들어가지 않은 사람(예: 대기 중인 사람)에게 보낼 것이 있는가. 권한이 없는 사람에게 보이면 안 되는 이벤트 |
| 지연 | 사용자가 체감하는 허용 지연(예: p95 1초 이내). 지연이 넘으면 무엇이 문제인가 |
| 연결 수명주기 | 끊김을 언제 "이탈"로 볼 것인가(재접속 유예 시간). 유예 중 다른 사람에게 어떻게 보이는가. 끊기면 진행 중인 업무 상태(대기·참가·게임)는 어떻게 되는가 |
| 여러 기기·탭 | 같은 사용자가 두 곳에서 접속하면 둘 다 받는가, 나중 것이 이기는가 |
| 순서·누락·중복 | 이벤트 순서가 바뀌거나 빠지거나 두 번 오면 사용자에게 어떤 결과가 허용되는가 |
| 놓친 이벤트 | 끊겼다 돌아온 사용자는 놓친 변화를 어떻게 따라잡는가(최신 상태만 / 놓친 이벤트 전부) |
| 현재 상태 보기 | 처음 들어오거나 다시 연결한 사용자에게 지금 상태(대기·참가 상태 등)를 바로 보여 줘야 하는가(권장: 예). 예면 스토리로 쓴다. 아니오여도 재동기화용 상태 조회는 ARCH가 내부 계약으로 둘 수 있다(`AQ-`로 넘긴다) |
| 클라이언트 → 서버 | 클라이언트가 실시간으로 보내는 행동이 있는가. 빠른 반복을 막을지는 P2 코어 `보안/악용` 질문에 포함해 한 번만 묻는다 |
| 클라이언트 종류 | 브라우저인가, 별도 게임 클라이언트·앱인가 (인증 방식 선택지가 달라진다) |
| 규모 | 동시 접속 수, 방·그룹당 최대 인원, 1인당 초당 메시지 수 |

### 1.2 P3 연결·세션 상태 (형식)
연결 상태를 업무 규칙 수준으로 표에 쓴다. 상태 이름은 예시다.

| 상태 | 뜻 | 들어오는 전이 (주체) | 나가는 전이 (주체) | 다른 사람에게 보이는 모습 |
|---|---|---|---|---|
| 연결됨 | 이벤트를 받는 중 | 접속 성공 (사용자) | 연결 끊김 (시스템) | 온라인 |
| 재접속 대기 | 끊겼지만 유예 시간 안 | 연결 끊김 (시스템) | 재접속 (사용자) / 유예 만료 (시간) | 온라인 또는 "연결 불안정" |
| 이탈 | 유예 만료 | 유예 만료 (시간) | — | 오프라인 |

- 시간으로 일어나는 전이가 있으면 TR-05도 판정한다.
- 연결 상태와 업무 상태(예: 대기·매치 참가 상태)를 섞지 않는다. "이탈" 때 업무 상태가 어떻게 바뀌는지는 업무 상태 표에 따로 쓴다(예: 매칭 팩 1.1 "연결 끊김").

### 1.3 P6 이벤트 AC (형식)
HTTP 응답 대신 **누가, 어떤 이벤트를, 언제까지, 어떤 순서로** 받는지를 Then에 쓴다.

```
AC-07-2 (이벤트)
Given 회원 A와 B가 같은 방에 연결되어 있다
When A가 준비 완료를 보낸다
Then B는 2초 안에 "참가자 준비 상태 변경" 이벤트를 1번 받는다
 And 이벤트에는 A의 식별자와 준비 상태가 들어 있다
 And 방에 없는 회원 C는 이 이벤트를 받지 않는다
```
- 이벤트 이름은 PM이 업무 용어로 쓰고, 코드상 이름(`EVT-xx`의 이벤트 종류 값)은 ARCH가 확정한다.
- 각 이벤트 AC에 최소 하나는 "받으면 안 되는 사람" 조건을 넣는다.
- 재접속 AC를 하나 이상 쓴다(예: "유예 시간 안에 다시 연결하면 놓친 변화가 반영된 상태를 받는다").
- "N초 안에 받는다" AC는 통합 테스트로 확인할 수 있는 수준으로 쓴다. 부하 조건의 지연은 NFR로 따로 쓴다.

**NFR 행 (해당하는 것만, 수치는 근거에서)**
| 영역 | 기준 형식 |
|---|---|
| 지연 | 이벤트 발생부터 수신까지 p95 N초 이하 (측정 조건: 동시 접속 M명) |
| 규모 | 동시 연결 N개에서 지연 기준 유지 |
| 재접속 | 끊김 후 N초 안에 재접속하면 상태 복구 |
| 남용 | 1 연결당 초당 N개, 메시지 하나 N바이트를 넘으면 거부 |

### 1.4 P7 화면 (TR-09도 `해당`일 때)
- 연결 상태 표시(연결됨 / 재연결 중 / 끊김)와 그때 막아야 하는 조작.
- 재연결 후 화면이 최신 상태로 맞춰졌음을 사용자가 알 수 있는가.
- 다른 사람의 행동이 화면에 반영될 때 표시 방식(즉시 교체 / 알림 후 반영).

## 2. ARCH

### 2.1 A2 결정 (카탈로그 "ARCH 결정"을 ADR로 쓸 때의 선택지)

**전송 방식**
| 옵션 | 맞는 경우 | 감수할 점 |
|---|---|---|
| 주기 조회(폴링) | 지연 허용이 수 초 이상, 서버 → 클라이언트만 필요, 가장 단순 | 불필요한 요청, 지연 = 조회 주기 |
| 서버 전송 이벤트(단방향 스트림) | 서버 → 클라이언트만 필요, HTTP 위에서 동작, 재개 기능 내장(마지막 이벤트 ID) | 클라이언트 → 서버는 HTTP API, 브라우저 기본 API는 사용자 지정 헤더를 붙일 수 없음 |
| 양방향 지속 연결 | 양방향·저지연이 필요 | 연결 상태 관리, 여러 프로세스 간 전달, 프록시·로드밸런서 설정 |

가장 단순한 옵션(주기 조회)을 반드시 비교에 넣는다. 요구 지연과 방향(단방향/양방향)이 근거다.

**전송 방식별로 이 팩에서 쓰는 항목**
| 전송 방식 | 2.1에서 정할 것 | 2.2에서 쓸 것 |
|---|---|---|
| 주기 조회 | 조회 주기, 변화 판단 방법(버전 값 비교 등) | 조회 API(HTTP 표)와 응답의 버전 값만. 이벤트 표·봉투·연결 진입점은 쓰지 않는다 |
| 서버 전송 이벤트 | 연결 구조, 인증, 놓친 이벤트(재개 ID 활용) | 서버 → 클라이언트 EVT, 봉투, 연결 진입점. 클라이언트 → 서버는 HTTP API |
| 양방향 지속 연결 | 이 절 전체 | 2.2 전체 |

**연결 구조와 구독** (주기 조회가 아닐 때)
| 옵션 | 맞는 경우 | 감수할 점 |
|---|---|---|
| 사용자당 연결 하나 + 구독·해지 메시지 | 사용자가 여러 대상(대기열, 방, 개인 알림)의 이벤트를 받음 | 구독 메시지와 구독 권한 확인 필요, 봉투에 스트림 구분 필드 필요 |
| 대상별 연결(예: 방마다 연결 주소) | 한 번에 한 대상만 봄, 가장 단순 | 대상이 바뀌면 다시 연결, 대상이 정해지기 전(예: 대기 중)에 보낼 곳이 따로 필요 |

**지속 연결의 인증** (ADR-002의 인증 방식과 맞는 옵션을 고른다)
- 클라이언트가 브라우저면 지속 연결·서버 전송 이벤트의 브라우저 API는 사용자 지정 인증 헤더를 붙일 수 없다. 브라우저가 아닌 클라이언트(게임 클라이언트·앱)는 헤더를 붙일 수 있다.

| 옵션 | 감수할 점 |
|---|---|
| 연결 직전 일회용 접속 티켓을 HTTP로 발급받아 연결 주소에 담음 | 티켓 발급 API 하나 추가, 짧은 만료·일회 사용 처리 |
| 연결 후 첫 메시지로 인증 (양방향일 때) | 인증 전 연결을 일정 시간 안에 닫는 처리 |
| 쿠키 기반 세션 | 지속 연결은 동일 출처 정책을 받지 않으므로 연결 요청의 Origin을 허용 목록으로 검사, 쿠키 SameSite 설정, ADR-002가 헤더 토큰 방식이면 인증 방식이 둘이 됨 |
| (브라우저가 아닌 클라이언트) 연결 요청 헤더에 기존 토큰 | 브라우저 클라이언트를 함께 지원하면 다른 옵션도 필요 |
- 일반 인증 토큰을 연결 주소에 그대로 담는 방식은 로그에 남을 수 있어 피한다.
- **연결 중 인증 만료·무효화**: 연결이 열린 동안 인증이 만료되거나 로그아웃되면 어떻게 하는지 정한다(연결 종료 / 다음 메시지에서 거부 / 연결 시점만 확인).

**연결 상태 저장과 전달**
| 옵션 | 맞는 경우 | 감수할 점 |
|---|---|---|
| 한 프로세스 메모리 | 서버 프로세스 하나로 충분한 규모 | 프로세스를 늘리면 다른 프로세스의 연결로 전달 불가, 재시작 시 상태 소실 |
| 공유 저장소의 발행·구독 | 여러 프로세스·서버 | 의존성 추가(ADR, 허용 목록), 운영 부담 |
- 한 프로세스로 시작하면 "프로세스 하나로 실행한다"를 ADR 결과와 `06-quality-gates.md`의 실행 명령(IC-11)에 쓴다. 프로파일의 `실행` 제약과 어긋나면 사용자에게 프로파일 수정을 요청한다.

**놓친 이벤트 처리**
| 옵션 | 감수할 점 |
|---|---|
| 재접속 시 최신 상태 전체를 다시 받음(스냅샷) | 상태가 크면 비용, 중간 변화는 보이지 않음. 가장 단순 |
| 이벤트 순번 + 최근 이벤트 보관 후 재전송 (서버 전송 이벤트면 재개 ID 활용) | 보관 범위·저장 위치 결정, 범위를 넘으면 스냅샷으로 대체 |

**발행 실패**: 상태 변경이 commit된 뒤 이벤트 발행이 실패하면 응답은 성공으로 두고, 클라이언트는 순번 검사와 재동기화로 회복한다. 이것과 다르게 하려면(발행 보장 등) ADR로 근거를 쓴다.

**하트비트**: 프로토콜 수준 핑인지 앱 메시지인지 정한다. 브라우저 API는 프로토콜 핑을 직접 보낼 수 없으므로 클라이언트가 보내야 하면 앱 메시지로 한다.

### 2.2 A4 이벤트 명세 (`04-interfaces-api.md`의 별도 섹션)
HTTP API 표와 같은 수준으로 비워 두지 않는다. 2.1 "전송 방식별로 이 팩에서 쓰는 항목"에 해당하는 부분만 쓴다.

**연결 진입점**
| 항목 | 내용 |
|---|---|
| 주소 | 예: `/ws` (사용자당 연결) 또는 `/ws/rooms/{room_id}` (대상별 연결) |
| 인증 | 2.1에서 정한 방식, 실패 시 동작 |
| 구독 | (사용자당 연결이면) 구독·해지 메시지의 EVT-ID와 구독 권한 확인 |
| 연결 종료 사유 | 사유 코드와 뜻(인증 실패, 권한 없음, 대상 없음, 남용, 서버 종료 등)과 클라이언트가 할 일(재접속 / 로그인 / 중단) |
| 남용 제한 | 메시지 최대 크기(ARCH가 정하는 기술 한도), 1 연결당 빈도 제한(PM 답이 있을 때, 없으면 "제한 없음"), 넘었을 때 동작(오류 이벤트 / 종료 사유) |
| 하트비트 | 종류(2.1), 주기, 응답이 없을 때 끊는 기준 |

**공통 봉투** (모든 메시지에 같은 형식)
| 필드 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `type` | 문자열 | 예 | 이벤트 종류 값 (EVT 표의 종류) |
| `stream` | 문자열 | 서버 → 클라이언트에서 예 | 순번이 매겨지는 단위(예: `room:42`, `user:7`). 대상별 연결 하나에 스트림이 하나뿐이면 생략할 수 있다 |
| `seq` | 정수 | 순번 검사 대상 이벤트에서 예 | 스트림별 순번. 아래 "순번 규칙"을 따른다. 순번 검사에서 제외하는 이벤트에는 넣지 않는다 |
| `occurred_at` | 시각 | 예 | 서버 기준 발생 시각 |
| `payload` | 객체 | 예 | EVT별 스키마 |
| `request_id` | 문자열 | 요청자에게 보내는 확인 응답일 때 | 어떤 요청의 결과인지 연결 |
- 필드 이름 표기(snake_case 등)는 HTTP 응답과 같게 한다(IC-06).
- 오류는 별도 이벤트 종류로 보내고, 본문은 ADR-004 오류 형식과 같은 필드를 쓴다.

**순번 규칙**
- `seq`는 스트림 대상의 **상태 버전 값**이다. 상태를 바꾸는 같은 트랜잭션 안에서 1 올리고 함께 저장한다(A3 테이블 정의에 버전 컬럼으로 반영). 메모리 카운터로 매기지 않는다. 그래야 스냅샷(HTTP 조회)도 같은 값을 돌려줄 수 있다. 예외: 대상 상태 자체를 메모리에만 두기로 한 경우(게임 기획 팩 2.1 "게임 상태 저장")는 그 메모리 상태의 버전을 쓰고 스냅샷도 같은 메모리에서 준다.
- **상태를 바꾸지 않는 이벤트**(예: 저장하지 않는 참가자 간 메시지)는 버전을 올리지 않는다. 봉투에 `seq`를 넣지 않고, 순번 검사(누락 판단)와 동기화 계약의 "스냅샷 이하 버림"에서 제외한다고 이벤트 표의 순서·전달 칸에 적는다.
- **개인 스트림**(특정 사용자에게만 가는 이벤트)은 그 사용자의 어떤 상태(예: 대기 항목, 알림 목록)의 버전을 쓰는지 정한다. 버전을 매길 상태가 없으면 `seq`를 넣지 않고 순번 검사 대상이 아니라고 적는다.
- commit 순서와 발행 순서가 달라 클라이언트에 역순으로 도착할 수 있다. 클라이언트는 기다리던 번호보다 큰 번호를 받으면 잠시(정한 시간) 보관했다가, 빠진 번호가 오지 않으면 재동기화한다.

**이벤트 표**
| EVT-ID | 종류 값 | 방향 | 수신 대상 | 발생 조건 | payload 스키마 | 순서·전달 | 관련 US/AC |
|---|---|---|---|---|---|---|---|
| EVT-01 | `participant.ready_changed` | 서버 → 클라이언트 | 같은 방 구독자 전체 | 참가자 준비 상태 변경이 commit된 뒤 | `ReadyChangedPayload` | 방 스트림 순번, 최대 1회 전달 | US-07 / AC-07-2 |
| EVT-02 | `participant.set_ready` | 클라이언트 → 서버 | — | 사용자가 준비 버튼을 누름 | `SetReadyRequest` | 요청자에게 EVT-03(확인 응답, `request_id` 포함) 또는 오류 이벤트, 성공하면 전원에게 EVT-01 | US-07 / AC-07-1 |
| EVT-03 | `ack` | 서버 → 클라이언트 | 요청자 | 클라이언트 요청 처리 완료 | `AckPayload` | 요청당 1회 | — |
- **발생 조건**은 "commit된 뒤"처럼 저장과의 순서를 적는다. 확정 전에 보내면 되돌려진 변화가 보일 수 있다.
- payload 스키마는 HTTP 스키마 명세와 같은 표(`필드 | 타입 | 필수 | 검증 제약 | 설명`)로 쓴다.
- 클라이언트 → 서버 메시지와 구독에도 권한 표를 적용한다(권한 표에 EVT-ID 행 추가).

**클라이언트 동기화 계약** (화면이 있으면 PAGE와 함께)
1. 처음 들어올 때 HTTP API로 현재 상태(스냅샷)를 받는다. 스냅샷에 그 시점의 버전 값(`seq`)을 넣는다.
2. 연결 후 받은 순번 검사 대상 이벤트 중 스냅샷 `seq` 이하는 버린다(`seq`가 없는 이벤트는 그대로 반영한다).
3. 번호가 건너뛰면 "순번 규칙"대로 잠시 기다렸다가, 2.1에서 정한 방식(재전송 요청 / 스냅샷 다시 받기)으로 맞춘다.

### 2.3 A5 실행 흐름
최소 SEQ: 연결 수립(인증 → 구독·권한 확인), 클라이언트 메시지 처리(메시지 → 응용 서비스 → commit → 확인 응답·발행), 끊김·재접속(유예 처리 포함), 인증 무효화·만료 시 처리, 기동 시 남아 있는 연결 상태 정리.
- **트랜잭션과 세션**: 클라이언트 메시지 하나 = DB 세션·트랜잭션 하나다. 연결이 열려 있는 동안 DB 세션을 잡고 있지 않는다(연결 풀 고갈). 트랜잭션 경계(A5 코어 규칙)에 이 문장을 함께 쓴다.
- **오류 변환**: HTTP용 전역 예외 처리기는 지속 연결의 메시지 처리에 적용되지 않을 수 있다. 도메인 예외를 오류 이벤트·종료 사유로 바꾸는 위치를 따로 정한다(ADR-004 결과에 추가).
- **발행 위치**: 이벤트 발행은 응용 서비스가 commit한 뒤에 한다. 도메인 객체는 연결에 직접 보내지 않고 "무슨 일이 일어났는지"만 알려 준다. 그 표현 방식(행위 메서드의 반환값 / 도메인 객체가 모아 두는 목록)을 A4 도메인 시그니처에 확정한다.
- **연결 관리 위치**: 누가 어디에 연결·구독돼 있는지 관리하는 코드를 어느 계층·모듈에 둘지 ADR-001 모듈 구성에 포함한다.
- **시간 전이**: 재접속 유예 만료처럼 시간으로 일어나는 전이는 현재 시각을 인자로 받는 도메인 메서드로 쓰고, 그것을 언제 부를지는 TR-05 실행 방식 ADR 하나로 정한다(매칭 팩의 시간 전이와 같은 ADR). 주기 실행을 고르면 TR-06도 판정 대상이다.

### 2.4 A7 게이트·테스트
| 대상 | 확인 방법 |
|---|---|
| 연결 수립·인증 실패 | 테스트 클라이언트로 연결해 종료 사유 확인 |
| 이벤트 수신 대상 | 클라이언트 두 개 이상을 연결해 받는 사람·받지 않는 사람 확인 |
| 순서 | 연속 변경 후 받은 `seq`가 1씩 증가하고 스냅샷 값과 이어지는지 확인 |
| 재접속 | 끊고 다시 연결해 놓친 변화가 반영되는지 확인 |
| 남용 | 크기·빈도 상한을 넘는 메시지가 정한 대로 거부되는지 확인 |
| 시간 | 유예·하트비트는 현재 시각을 주입해 대기 없이 확인(TR-05) |
- 스택의 테스트 클라이언트가 지속 연결을 지원하는지 확인하고, 테스트 방법을 `06-quality-gates.md`에 확정한다(IC-11).
- 지연 NFR(p95)이 있으면 측정 방법(도구, 동시 접속 수, 측정 위치)을 `06-quality-gates.md`에 확정한다. 측정 환경을 "마련할 수 있다"는 기준: 프로파일의 실행 환경(예: 로컬 한 대)에서 NFR의 측정 조건(동시 접속 수 등)을 재현할 수 있다. 재현하려면 새 도구·서비스가 필요하면 ADR 대상이다. 측정 환경을 마련할 수 없으면 PM NFR과 설계가 어긋나는 경우이므로, handoff 전에 사용자에게 확인을 받는다(통합 테스트의 "N초 안에 받는다"로 확인 범위를 줄일지 등).

### 2.5 스택 주의에 쓸 것 (A6, IC-12)
- HTTP 요청용 미들웨어(로깅·인증 등)와 전역 예외 처리기가 지속 연결 요청·메시지에 적용되지 않을 수 있다. 연결 로그·인증·오류 변환을 어디서 하는지 확인한다.
- 여러 작업 프로세스로 실행하면 2.1 "연결 상태 저장과 전달" 결정과 맞는지 확인한다.
- 프록시·로드밸런서의 유휴 연결 시간 제한이 하트비트 주기보다 짧지 않은지 확인한다(TR-13이 `해당`일 때).
