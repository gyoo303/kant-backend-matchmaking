# 프로젝트 프로파일 템플릿

> 이 파일을 `docs/00-inputs/project-profile.md`(레지스트리 `IN-PROFILE`)로 복사해 사람이 채운다.
> PM·ARCH 에이전트는 프로파일을 읽기만 한다. 고칠 내용이 생기면 에이전트가 사용자에게 수정을 요청한다.
> 스킬 문서에는 프로젝트 사실(스택, 일정, 평가 기준 등)을 두지 않는다. 그런 사실은 모두 이 파일이나 이 파일이 가리키는 입력 문서에 둔다.
> 모든 절은 내용을 쓰거나, 해당이 없으면 "없음"이라고 쓴다(빈칸으로 두지 않는다). `(필수)` 절이 빈칸이면 PM·ARCH는 시작하지 않는다.
> `(예시)` 표시가 붙은 행은 형식 안내다. 복사한 뒤 지우고 실제 값을 쓴다. `(예시)` 표시가 하나라도 남아 있으면 PM·ARCH는 시작하지 않는다.

## 1. 개요 (필수)
- 프로젝트 이름:
- 한 줄 설명: (무엇을, 누구에게 제공하는가)
- 산출물 형태: API 서버 / 풀스택 웹 / 기획·설계 문서만 / 기타(직접 기술)
- 작업 모드: 새로 만들기 / 기존 결과물 변경 (변경이면 기준이 되는 저장소·브랜치·산출물 위치)

## 2. 입력 문서 (필수)
에이전트가 근거로 읽는 문서는 이 표에 있는 것뿐이다. 표에 없는 파일은 `docs/00-inputs/`에 있어도 읽지 않는다.

| ID | 경로 | 역할 | 읽는 단계 | 메모 |
|---|---|---|---|---|
| DOC-01 | `docs/00-inputs/requirements.md` | 요구사항 원문 | PM | (예시) |
| DOC-02 | `docs/00-inputs/evaluation.md` | 외부 평가 기준 | PM, ARCH | (예시, 없으면 행 삭제) |

- ID는 `DOC-xx`로 매긴다. 에이전트가 쓰는 항목 ID(`REQ-`, `CRT-` 등)와 검색 시 겹치지 않게 하기 위해서다.
- 역할은 다음 중 하나다.
  - `요구사항 원문`: PM이 P1에서 REQ-ID로 인덱싱한다. 하나 이상 필요하다.
  - `외부 평가 기준`: 과제 평가표, 계약 요구사항, 인수 기준처럼 산출물을 판정하는 외부 기준. §6에서 다루는 방식을 정한다.
  - `참고 자료`: 근거로 인용할 수 있지만 요구사항은 아니다. 인용할 때는 문서 ID를 쓴다.
  - `상류 산출물`: 앞선 트랙이나 기존 시스템의 산출물(API 명세, 스키마 등). 지켜야 하는 부분은 §3 제약 대장에 C-ID로 올린다.

## 3. 제약 대장 (필수)
프로젝트가 지켜야 하는 제약을 출처와 함께 적는다. 제약이 없는 분류는 행을 쓰지 않는다. 제약이 하나도 없으면 표 대신 "없음"이라고 쓴다.

| C-ID | 분류 | 내용 | 출처 | 변경 | 근거 위치 |
|---|---|---|---|---|---|
| C-01 | 스택 | (예시) 언어·프레임워크·DB 이름과 최소 버전 | 외부 평가 기준 | 고정 | DOC-02 §4 |
| C-02 | 범위 제외 | (예시) 실제 결제 연동은 하지 않는다. 결제가 필요하면 상태 변경으로 대신한다 | 사용자 | 고정 | — |
| C-03 | 구조 | (예시) 저장소 디렉토리 구조 | 조직 표준 | 협의 | (링크) |

- **분류**: `스택` · `구조`(저장소·디렉토리·계층) · `범위 포함`(반드시 들어갈 기능·도메인) · `범위 제외` · `화면`(화면 기술·필수 화면) · `보안` · `운영·배포` · `실행`(실행·검증 명령) · `제출`(제출물 형식) · `파이프라인`(쓰는 단계, 예: UX 단계 사용 여부) · `기타`
- **출처**: `사용자` · `외부 평가 기준` · `조직 표준` · `상류 산출물` · `기존 시스템`
- **변경**
  - `고정`: 결정 대상이 아니다. PM은 범위에서 빼거나 바꾸자고 제안하지 않고, ARCH는 ADR 옵션으로 비교하지 않는다. 바꾸려면 사람이 이 파일을 고친다.
  - `협의`: 바꿀 이유가 생기면 PM은 결정 카드(D-xx), ARCH는 ADR로 사용자 확인을 받는다.

## 4. 일정·팀 (필수)
- 기간: 시작일 ~ 종료일 (작업일 수)
- 팀: 인원과 역할 (에이전트만 쓰면 "에이전트 + 검토자 N명")
- 고정 일정: 중간 점검·발표·배포처럼 날짜가 정해진 일 (없으면 "없음")

## 5. 범위 등급 (선택)
요구사항이나 외부 기준이 범위를 등급으로 나누면 적는다(예: 필수 / 도전). 없으면 "없음"이라고 쓰고, PM은 MoSCoW만 쓴다.

| 등급 | 정의 | 순서 규칙 | 근거 |
|---|---|---|---|
| (예시) 필수 | 모두 완료해야 하는 범위 | 가장 먼저 | DOC-02 §5 |
| (예시) 도전 | 선택 과제 | 필수를 모두 마친 뒤에만 시작 | DOC-02 §5 |

## 6. 외부 평가 기준 처리 (선택)
§2에 `외부 평가 기준` 문서가 있을 때만 쓴다. 없으면 "없음".
- 대상 문서: DOC-xx
- 항목 범위: 문서의 어느 절·표가 평가 항목인가
- 전 항목 매핑 필수 여부: 예 / 아니오 (예이면 PM 추적 매트릭스에 빈 행이 있을 때 handoff하지 않는다)
- 사람이 담당하는 항목: 발표, 외부 게시처럼 에이전트 산출물이 아닌 것

## 7. 제출물·시연 (선택)
날짜가 정해진 외부 제출물(설계 문서 게시, 시연, 발표 등)과 형식. 없으면 "없음".

| 제출물 | 날짜 | 형식 요구 | 담당 |
|---|---|---|---|
| (예시) ERD·API 명세 게시 | YYYY-MM-DD | Mermaid ERD, Method·URI·입출력 표 | ARCH 산출물 → 사람이 게시 |

## 8. 허용 의존성 (선택)
ADR 없이 써도 되는 라이브러리·도구. 여기에 없는 의존성 추가는 ARCH가 ADR로 사용자 확인을 받는다. 없으면 "없음".

| 이름 | 용도 | 근거 |
|---|---|---|
| (예시) pytest | 테스트 실행 | 조직 표준 |
