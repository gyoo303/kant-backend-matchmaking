# 매치메이킹 시연용 웹 게임 요구사항 (가칭 '점프 5')

2026-10-27 · 팀 작성 · 레지스트리 ID: IN-REQ

> 기술 스택, 4계층 구조, 공통 산출물(README·노션·발표)은 발제 문서(`docs/00-inputs/kant-rubric.md`)를 따른다. 이 문서에는 이 Use Case에만 해당하는 내용을 적는다.

## 1. 개요

- **한 문장 정의**: 회원이 3 vs 3, 5 vs 5, 10 vs 10 모드 중 하나를 골라 대기열에 등록하면, 정원이 찬 순서대로 매치가 확정되고, 스페이스바 점프 5회를 먼저 채운 팀이 이기는 웹 게임.
- **목적**: 게임 자체는 최소화하고, 대기열 등록·취소·매치 확정·게임 결과로 이어지는 매칭 규칙을 도메인 객체가 스스로 검증하는 백엔드 서비스를 만든다.
- **대상 사용자**: 시연 현장에서 URL이나 QR 코드로 접속하는 참가자, 시연을 진행하는 운영자.
- **발제 Use Case 대응**:

  | 발제 예시 구조 | 이 프로젝트 |
  |---|---|
  | 정원이 있는 자원 | 모드별 대기열 (정원 6 / 10 / 20명) |
  | 신청 내역 | 대기 티켓 (회원이 대기열에 등록한 기록) |
  | 회원 | 회원 (플레이어, 운영자) |
  | 토큰 블랙리스트 | 토큰 블랙리스트 |

## 2. 액터

| 액터 | 설명 |
|---|---|
| 회원(플레이어) | 회원가입·로그인 후 대기열 등록, 취소, 게임 참여, 결과 확인, 매치 히스토리 조회 |
| 운영자 | 대시보드 모니터링, 테스트 봇 투입, 이벤트 로그 확인, 히스토리 다운로드. 운영자 계정은 초기 데이터로 만들고, 일반 회원가입으로는 운영자가 될 수 없다 |
| 테스트 봇 | 운영자가 투입하는 가상 플레이어. 회원과 같은 규칙으로 대기열에 등록되고 점프한다 |
| 비로그인 방문자 | 로비의 모드별 대기 인원과 매치 히스토리 목록만 볼 수 있다 |

## 3. 핵심 도메인과 규칙

규칙은 "어떤 요청을 거부하는가"로 적는다. 규칙 위반은 화면이 멈추지 않고 안내 문구로 거부된다.

### 3.1 회원
- 회원가입은 닉네임과 비밀번호로 한다. 가입 화면은 랜덤 닉네임(예: "용감한고양이42")을 추천하고, 회원이 바꿀 수 있다.
- 이미 쓰고 있는 닉네임으로는 가입할 수 없다.
- 비밀번호는 정해진 최소 길이보다 짧으면 거부한다.
- 로그인한 회원만 대기열에 등록할 수 있다.
- 어떤 응답에도 비밀번호(해시 포함)는 나오지 않는다.

### 3.2 대기열 (모드)
- 모드는 3 vs 3, 5 vs 5, 10 vs 10 세 가지이며, 정원은 각각 6, 10, 20명이다.
- 정원은 1명 이상이어야 하고, 현재 대기 인원은 0명 이상 정원 이하여야 한다.
- 정원이 차는 순간 대기 순서대로 매치가 확정되고, 그 인원은 대기열에서 빠진다.

### 3.3 대기 티켓
- 한 회원은 동시에 하나의 대기열에만 등록할 수 있다. 이미 대기 중이거나 게임 중인 회원의 등록은 거부한다.
- 대기 중인 티켓만 취소할 수 있다. 이미 매치가 확정되었거나 취소된 티켓의 취소는 거부한다.
- 다른 회원의 티켓은 취소할 수 없다.

### 3.4 매치
- 매치가 확정되면 대기 순서대로 두 팀에 번갈아 배정한다.
- 매치가 확정되면 바로 게임이 시작된다(수락 대기 없음).
- 게임 중인 매치에서, 그 매치의 참가자만 점프를 기록할 수 있다. 끝난 매치나 참가하지 않은 매치의 점프는 거부한다.
- 참가자 중 한 명이 점프 5회를 처음 채우면 그 참가자가 개인 승자, 그 팀이 승리 팀이 되고 매치가 끝난다.
- 승자는 매치당 한 명, 승리 팀은 하나다. 끝난 매치의 결과는 바뀌지 않는다.
- 매치에는 시작 시각과 종료 시각이 남고, 경기 소요 시간을 볼 수 있다.

### 3.5 토큰 블랙리스트
- 로그아웃한 토큰은 블랙리스트에 등록되고, 그 토큰으로 다시 요청하면 거부한다(401).

### 3.6 존재하지 않는 대상
- 없는 매치·모드·회원을 조회하면 "찾을 수 없음"으로 거부한다(404).

## 4. 상태 흐름

### 4.1 기본 흐름
`대기 없음` → (등록) → `대기 중` → (정원 충족) → `매칭 확정` → (즉시) → `게임 중` → (점프 5회 선착) → `게임 종료`

### 4.2 취소 흐름
`대기 중` → (본인이 취소) → `대기 없음`

### 4.3 연결 끊김 (도전 D, §7)
- 대기 중 일정 시간 응답이 없는 회원은 대기열에서 자동 제거된다.
- 게임 중 연결이 끊긴 회원이 다시 로그인하면 진행 중인 게임으로 돌아간다.

## 5. 화면

화면은 반응형 웹이며, 서버가 렌더링하는 페이지와 API 문서(Swagger)로 확인한다.

| 화면 | 발제 화면 대응 | 내용 |
|---|---|---|
| 로비 | 메인 | 로그인한 회원의 닉네임, 모드 선택(3 vs 3 / 5 vs 5 / 10 vs 10), 모드별 현재 대기 인원/정원 |
| 회원가입·로그인 | — | 추천 닉네임, 비밀번호 입력 |
| 대기 화면 | — | 매칭 경과 시간, 대기 현황(예: 4/6명), [매칭 취소] 버튼 |
| 게임 화면 | — | 내 점프 수와 팀별 점프 현황, 스페이스바 점프, 모바일용 하단 대형 [점프] 버튼 |
| 결과 화면 | — | 개인 승리 여부, 팀 승리 여부, 경기 소요 시간, [로비로] 버튼 |
| 매치 히스토리 목록 | 목록 | 끝난 매치 목록. 모드·상태로 필터, 종료 시각으로 정렬, 닉네임으로 검색, 페이지 나눔 |
| 운영자 대시보드 | 현황 대시보드 | 모드별 대기 인원/정원, 진행 중인 매치와 점프 현황, 이벤트 로그, [테스트 봇 투입] 버튼 |

- 대기 현황과 점프 현황은 새로 고치지 않아도 짧은 지연 안에 반영된다(목표 지연 시간은 기획 단계에서 정한다).
- 데이터가 없으면 빈 화면 대신 "아직 매치가 없습니다" 같은 안내를 보여 준다.

## 6. 운영 기능

- **테스트 봇 투입**: 운영자가 모드와 인원을 골라 봇을 대기열에 넣는다. 봇은 회원과 같은 규칙으로 등록되고 점프한다. 도전 A를 적용하기 전에는 봇을 한 명씩 순서대로 넣는다.
- **이벤트 로그**: 등록, 취소, 매치 확정, 게임 종료, 로그인·로그아웃이 시간순으로 남고 대시보드에서 볼 수 있다.
- **운영자 전용**: 대시보드, 봇 투입, 다운로드는 운영자만 쓸 수 있다. 회원이 요청하면 거부한다.
- **초기 데이터**: 서버를 시작하면 세 모드, 운영자 계정, 시연용 회원·봇 계정, 지난 매치 히스토리를 합쳐 20건 이상이 준비되어 있다.

## 7. 도전 과제 대응

필수 기능을 모두 마친 뒤 진행한다.

| 도전 | 이 프로젝트에서 할 일 |
|---|---|
| A. 동시성 제어 | 정원이 1명 남은 대기열에 여러 회원·봇이 동시에 등록하는 상황을 스크립트로 재현하고, 정원 초과·중복 대기·취소된 회원의 매치 참여(유령 플레이어)가 생기지 않게 막는다 |
| B. 후처리·스트리밍 | 게임이 끝나면 응답을 늦추지 않고 전적 집계와 종료 알림 로그를 남긴다. 운영자가 매치 히스토리와 이벤트 로그를 CSV로 내려받는다(대량 데이터에서도 메모리에 한 번에 올리지 않음) |
| C. 캐싱·배포 | 모드별 대기 인원 조회와 토큰 블랙리스트 확인에 캐시를 적용하고, 등록·취소·확정·로그아웃 때 캐시를 갱신한다. 환경변수를 분리하고 시연 환경에서 바로 실행할 수 있는 구성을 만든다 |
| D. 연결 끊김 처리 (팀 추가) | §4.3의 대기 타임아웃 자동 제거와 재로그인 시 진행 중 게임 복귀. 타임아웃 시간은 기획 단계에서 정한다 |

## 8. 범위 밖

- 발제 제외 범위: 외부 프론트엔드 프레임워크, 실제 결제, 상용 메일·SMS·메신저(Slack 등) 알림. 알림은 로그로 대신한다.
- 복잡한 게임 그래픽과 물리 엔진 (스페이스바 5회 점프 선착 규칙 유지)
- 플레이어 간 실시간 채팅
- 실력 기반 매치메이킹(MMR·Elo)
- 매치 수락·거절 단계
