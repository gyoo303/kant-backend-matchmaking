### D-020: 구현 코드는 KANT 백엔드 교안 수준으로   [APPROVED by user, 2026-10-28]
- 결과: 사용자 지시 — DB·BE·FE 구현 코드는 수강 중인 KANT 백엔드 교안(1~6장, 1년차 부트캠프 대상)과 그 예제 코드 수준으로 작성한다. 규칙 본문과 교안 기술 목록은 `docs/02-arch/05-structure-conventions.md` §8

  - B(교안에 없지만 조금 공부하면 이해 가능한 문법: `dataclass`, `StrEnum`, `Protocol`, pydantic-settings, 예외 계층 등): 유지·허용
  - C(인증·보안): 교안 6장 1강 설계를 따른다(D-021)
- 근거: 사용자 요청(2026-10-28), 교안 1~6장 검토 결과. 4계층·레포지토리 구조는 교안 7장(발제 §2·§4.1) 범위이므로 이 규칙과 충돌하지 않는다
- 적용: TKT-DB-M3-01~03·TKT-BE-M3-01~05 코드를 이 규칙으로 고쳤다(제약·인덱스 정리, `relationship`+`selectinload`, 파이썬 필터·슬라이싱, 블랙리스트 토큰 원문). 이후 모든 DB·BE·FE 티켓에 적용
- 감수할 점: 목록·이력 조회가 해당 행을 모두 읽은 뒤 파이썬에서 거르고 자른다(시연 규모 기준). 동시 가입 시 중복 아이디는 DB `unique`가 막아 500이 된다(순차 요청 기준, D-018)
- 되돌리기 비용: 중

### D-021: 인증·보안 설계를 교안 6장 1강으로   [APPROVED by user, 2026-10-28]
- 결과: ADR-002를 교안 6장 1강 기준으로 다시 썼다. 선택지는 모두 권장안 채택
  - 토큰: access(30분)·refresh(7일) 두 개, 페이로드 `sub`(아이디)·`exp`·`token_type`. pyjwt `jwt.encode`/`jwt.decode`, `OAuth2PasswordBearer`, `OAuth2PasswordRequestForm`, passlib bcrypt
  - **로그아웃**: 교안 구조(refresh·`/refresh`)를 따르되, access·refresh 두 토큰을 모두 블랙리스트에 넣고 인증 의존성도 블랙리스트를 확인한다 — 발제 §4.6·AC-10-2("로그아웃한 토큰은 즉시 401") 충족 (대안: 교안 그대로 refresh만 차단 → AC-10-2 미충족)
  - **블랙리스트 저장**: 교안처럼 토큰 원문을 저장하되 보관은 DB `token_blacklist` 테이블(5장) — 재시작 후에도 차단 유지 (대안: 메모리 `set`)
  - **화면 인증**: 쿠키를 쓰지 않는다. Authorization 헤더만 쓰고, 화면 JS가 토큰을 `localStorage`에 두고 API로 데이터를 채운다. 비로그인 이동(AC-11-3)도 JS가 한다 (대안: 화면용 쿠키만 예외 유지)
- 근거: 사용자 요청(2026-10-28), 교안 6장 1강, 발제 §4.6, AC-09~11. D-005의 "서버가 쿠키로 판단" 근거와 ARCH-Q-05 답을 대체한다
- 감수할 점: 토큰이 `localStorage`에 있어 XSS에 노출된다(템플릿 자동 이스케이프 유지로 완화). 서버가 화면 접근을 막지 못해 로그인 전 빈 화면 틀이 잠깐 보일 수 있다. 블랙리스트 행은 정리하지 않는다(시연 규모)
- 되돌리기 비용: 중 (화면 계약 PAGE·`api.js`)

## 자율 결정

사용자 확인 기준(범위·평가표·일정·보안·되돌리기 비용이 큰 결정)에 해당하지 않아 에이전트가 정한 결정이다. 사용자에게 묻지 않고 정했으므로, 팀원이 맥락을 알 수 있게 선택지·권장 이유·trade-off를 함께 적는다. 바꾸고 싶으면 해당 D-ID를 지정해 결정 카드로 다시 올린다.

### D-005 [자율] 비로그인 화면 접근 처리
- 결정: 비로그인 상태로 서비스 화면에 들어오면 로그인 화면으로 이동한다 — ASM-07, REQ-010
- 선택지: **A. 로그인 화면으로 303 리다이렉트 (권장·채택)** / B. 화면은 열고 "로그인이 필요합니다" 안내와 링크만 표시
- 권장 이유: 원문이 "나머지는 로그인해야 쓴다"고 정했고, 모든 화면이 회원 데이터(현재 참가 방·본인 기록)를 쓴다. 서버가 쿠키로 로그인 여부를 판단할 수 있어(ADR-002) 리다이렉트가 가장 단순하다.
- trade-off: A — 로그인 뒤 원래 가려던 화면으로 돌아가는 기능은 없다. B — 화면마다 비로그인 분기가 생기고 시연 흐름에는 쓸모가 없다.
- 변경(D-021, 2026-10-28): 쿠키를 쓰지 않으므로 서버 303 대신 화면 JS가 토큰이 없을 때 `/login`으로 이동한다. "로그인 화면으로 이동"이라는 결정 자체는 그대로다.

### D-006 [자율] 같은 방 반복 참가 요청
- 결정: 이미 참가 중인 같은 방에 다시 참가 요청하면 기존 참가를 유지하고 성공 응답한다(새 이용 기록 없음) — ASM-08, REQ-034
- 선택지: **A. 기존 참가 유지 + 200 (권장·채택)** / B. 400 "이미 참가 중입니다"로 거부
- 권장 이유: 원문은 "새 이용 기록을 만들지 않는다"고만 했고 거부하라고 하지 않았다. 버튼 두 번 클릭이나 응답 유실 뒤 재시도(REQ-106)에도 결과가 같아 안전하다.
- trade-off: A — 응답만으로는 "새로 참가"와 "이미 참가 중"을 구분할 수 없다(상세 응답으로 확인). B — 재시도할 때마다 오류 문구가 떠 사용자가 실패로 오해한다.

### D-007 [자율] 이용 이력 페이지 기본값
- 결정: 기본 1페이지·10건, 최대 50건(방 목록 REQ-083과 같음), 입장 시각 동률은 기록 식별자 내림차순 — ASM-09, REQ-055, REQ-117
- 선택지: **A. 방 목록과 같은 10건/50건 (권장·채택)** / B. 이력만 별도 기준(예: 기본 20건·최대 100건)
- 권장 이유: 같은 규칙을 쓰면 페이지 이동 부품·입력 검증·테스트를 재사용할 수 있다. 동률을 식별자 내림차순으로 두면 "최신순"과 방향이 같다.
- trade-off: A — 기록이 많은 회원은 페이지를 자주 넘겨야 한다. B — 페이지 규칙이 두 벌이 되어 검증·테스트가 늘어난다.

### D-008 [자율] 회원 탈퇴·정보 수정·로그인 무차별 대입 방어

- 권장 이유: 원문과 발제 어디에도 요구가 없다(근거 없는 기능 추가 금지). 13일 일정에서 필수 범위를 먼저 지킨다.
- trade-off: A — 실서비스 수준의 계정 관리·보안은 없다(시연용 한정). B — 탈퇴 회원의 참가·방장 처리 규칙이 새로 필요하다. C — 실패 기록 저장·해제 규칙과 테스트가 늘어난다.

### D-009 [자율] 삭제 방 보관 정보의 표시 범위

- trade-off: A — 누구와 함께 있었는지는 볼 수 없다. B — 타인 정보 비공개 규칙과 충돌하고 공개 범위 규칙이 새로 필요하다.

### D-010 [자율] 팀 이름
- 결정: 두 팀의 이름은 A팀·B팀 — ASM-14, REQ-036
- 선택지: **A. A팀·B팀 고정 (권장·채택)** / B. 레드·블루 같은 색 이름 고정 / C. 방장이 팀 이름을 정함
- 권장 이유: 원문은 "두 팀"만 정했다. 코드 식별자(`TeamSide.A`·`B`)와 화면 표기가 같아 혼동이 없고, 팀 이름 변경은 범위 밖이다.
- trade-off: A — 표현이 밋밋하다(화면 라벨은 FE가 바꿀 수 있음). B — 기능 차이는 없고 표기만 다르다. C — 입력·검증·표시 규칙이 추가된다.

### D-011 [자율] 닉네임 허용 문자

- 권장 이유: Q-04 답변은 길이만 정했다. 공백·특수문자·이모지를 막으면 화면 깨짐과 비슷한 닉네임으로 인한 혼동을 줄이고, 검증 규칙이 정규식 하나로 끝난다.
- trade-off: A — 밑줄·하이픈 같은 기호가 들어간 닉네임은 쓸 수 없다. B — 공백뿐인 닉네임·표시 깨짐 같은 예외 규칙을 따로 만들어야 한다.

### D-013 [자율] 성공 응답 코드

### D-014 [자율] 시드 구성과 시드 비밀번호

### D-015 [자율][ARCH] 방장 아님·참가자 아님의 응답 코드

### D-016 [자율][ARCH] 해산된 방 상세 조회 응답
- 결정: 게임 시작으로 해산된 방의 상세 조회는 410, 참가자 없음으로 삭제된 방과 없는 방은 404 — ARCH-Q-04, REQ-094, AC-07-4·5

- 권장 이유: 원문이 "해산"과 "접근 불가"를 구분하는 응답 계약을 요구한다(REQ-094). 화면 폴링 JS가 상태 코드만 보고 분기할 수 있어 문구 파싱이 필요 없다.
- trade-off: A — 410이라는 덜 흔한 코드를 팀에 설명해야 한다. B — 문구를 바꾸면 화면 분기가 깨진다. C — 삭제된 방이 정상 응답처럼 보여 다른 API 규칙과 어긋난다.

### D-017 [자율][ARCH] API와 화면의 경로 구분

- 권장 이유: 화면 `/rooms/{id}`와 API `/rooms/{id}`가 겹친다. 사용자가 보는 브라우저 주소는 짧게 두고 API만 구분하는 편이 단순하다.
- trade-off: A — API 주소가 PM 초안의 `/rooms` 예시와 달라진다. B — 브라우저 주소가 길어진다. C — 라우터가 복잡해지고 Swagger 문서가 헷갈린다.

### D-022 [자율][ARCH] GATE-08 검사 명령을 ORM 모델 이름으로 좁힘
- 결정: GATE-08 명령을 `Model`로 끝나는 모든 import 대신 ORM 모델 이름 4개(`UserModel`·`TokenBlacklistModel`·`RoomModel`·`ParticipationModel`)와 `infrastructure.models` 경로로 찾게 바꾼다 — `06-quality-gates.md` GATE-08, RISK-02, BE 브리핑(TKT-BE-M3-04)·QA 브리핑(M3~M7)의 오탐 보고
- 선택지: **A. 모델 이름 + 경로로 좁힘 (권장·채택)** / B. `infrastructure.models` 경로만 검사 / C. 기존 명령 유지, `BaseModel`은 매번 사람이 제외
- 권장 이유: pydantic `BaseModel` 오탐이 사라져 "출력 0줄" 기준이 실제로 쓸 수 있게 되고, `models.RoomModel`처럼 import 줄에 이름이 없는 사용도 잡는다.
- trade-off: A — 모델 클래스를 추가하면 명령에도 이름을 넣어야 한다. B — 단순하지만 다른 경로로 들여온 모델 이름은 놓친다. C — 문서 변경은 없지만 매번 실패로 나와 진짜 위반을 놓치기 쉽다.
