# ADR-004: 422 입력 검증 에러 형식
- 상태: Accepted (user, 2026-10-28)
- 관련 계층: [레이어]
- 근거: NFR-02("모든 오류 응답이 한 형식"), REQ-062, EV-05, RC-14

## 맥락
FastAPI 기본 422는 `detail`이 오류 객체 배열이다. PM NFR-02는 모든 오류를 `{"detail": ...}` 한 형식으로 요구하고, 화면 JS는 `detail`을 문구로 바로 보여 준다(US-15~17).

## 검토한 옵션
| 옵션 | 장점 | 단점 | AI 부채 영향(D2~D4) | 평가표 영향 | 되돌리기 비용 |
|---|---|---|---|---|---|
| A. FastAPI 기본 유지(`detail`이 배열) | 코드 0줄 | 화면 JS가 형식 두 개를 처리, NFR-02 위반 | 중 | 위험 | 낮음 |
| B. 전역 `RequestValidationError` 핸들러로 `{"detail": "<필드>: <메시지>; ..."}` 문자열로 변환, 상태 422 유지 | 형식 하나, JS 단순 | 필드별 구조 정보는 문자열에만 남음 | 낮음 | 충족 | 낮음 |

## 계층 관점 설명
[레이어] 변환은 `src/main.py`의 전역 핸들러에서만 한다. 라우터·서비스는 422를 직접 만들지 않는다. 메시지는 앞에서부터 최대 3개 오류를 `loc`의 마지막 요소와 `msg`로 이어 붙인다.

## 결정 / 추천
결정: B — 모든 오류가 같은 모양이라 화면·테스트가 단순해진다.
