# ADR-012: 화면 갱신을 자동 조회(폴링)에서 수동 새로고침으로
- 상태: Accepted (user, 2026-10-31) — D-026
- 관련 계층: [모듈 협력 구조] [어플리케이션]
- 근거: D-026, D-016, D-020, D-021, REQ-089·092·094·096·097, AC-15-2·5·6, AC-16-1·3~6, NFR-08, RISK-11, EV-08

## 맥락
KANT 튜터가 화면 폴링을 쓰지 말라고 피드백했고, PM이 D-026으로 자동 조회를 Won't로 바꿨다. 이전 설계는 폴링 유틸이 1초마다 목록·상세를 조회했다. 이제 화면이 언제 조회하는지와 해산(410) 신호를 어디서 받는지를 다시 정해야 한다. DB·API 계약(410/404 구분, D-016)은 바꾸지 않는다.

## 계층 관점 설명
- [모듈 협력 구조] 해산 신호는 여전히 API-ROOM-03의 410 하나다. 받는 시점만 "1초마다"에서 "진입·[새로고침]·변경 요청 실패 직후"로 바뀐다. 해산된 방에 변경 요청을 보내면 서버는 400(`RoomDeletedError`)을 준다. 그래서 화면은 실패 문구를 보인 뒤 상세를 한 번 다시 조회하고, 그 결과가 410이면 해산 안내와 함께 목록으로 간다(AC-16-4).
- [어플리케이션] 서버·DB 설계는 그대로다. 화면 쪽은 `src/static/js/rooms.js`와 템플릿 2개(`rooms/list.html`, `rooms/detail.html`의 [새로고침] 버튼)만 관여하고, 폴링 유틸 파일은 두지 않는다.

## 결정 / 추천
A — PM AC의 [새로고침]을 그대로 구현하면서 교안 밖 비동기 JS를 없앤다.

## 결과
- 좋아지는 점: 화면 JS가 `fetch`·DOM 조작만으로 끝난다(D-020). 콘솔 로그로 시연 요청을 하나씩 보여 줄 수 있다. 화면 점검 항목이 "버튼을 누르면 바뀐다"로 단순해진다.
- 감수할 점: 해산이 다른 참가자 화면에 바로 보이지 않는다(REQ-093 해석, D-026). 오래된 화면에서 보낸 요청은 서버가 400으로 거부한다(정합성은 서버 재검사가 지킴).
- 후속 작업: TKT-FE-M5-01·03·04, TKT-QA-M5-01 (410 `Cache-Control: no-store`는 TKT-BE-M3-05·TKT-QA-M3-01)
