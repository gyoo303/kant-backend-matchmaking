# ADR-013: 동시 쓰기 정합성과 응답 시간 상한 — 방 행 잠금 + 대기 상한 + 빠른 거절
- 상태: Accepted (user, 2026-11-10) — 7단계 부하 테스트 검증 대기
- 관련 계층: [레이어] [모듈 협력 구조] [인프라]
- 근거: D-032, D-033, D-034, DRV-C-01·07, DRV-Q-01·02, RISK-03·04, REQ-098~107, AC-18-*, CR-01~13, VC-01~07, DC-01~16, `docs/03-concurrency/01~05`
- 대체: ADR-009

## 맥락
- 같은 방에 참가 요청이 몰리면 정합성이 깨진다. 기준선 측정(`loadtest/baseline-report-2026-11-09.md`)에서 빈자리 3개인 방에 100명이 동시에 참가하자 **4인 방에 7~10명**이 들어갔고, 팀 정원 초과와 `join_order` 중복이 생겼다. 5xx는 0건이라 위반이 **조용히** 저장됐다.
- 원인은 잠금 없는 읽기 → 도메인 검사 → 저장(check-then-act)이다. 요청들이 같은 스냅샷을 읽고 각자 "빈자리 있음"으로 판단한다. `participations`에는 `(room_id, join_order)` unique가 없어 DB도 막지 못한다.
- 긴급 요구사항(VOC-11, D-033): 몰림 상황에서도 화면이 멈춘 것처럼 보이면 안 된다. 클릭부터 **5초 안에 결론**이 나야 하고, 목표 규모(60 TPS)를 넘어도 지켜야 한다. 지금은 커넥션 풀 대기 상한이 30초라, 풀이 고갈되면 목록 조회까지 30초 동안 응답이 없다.
- 제약: 스택 고정(PostgreSQL만, Redis·브로커 없음), 서버 1대·워커 여러 개 가능, 도메인 규칙은 `rooms/domain`에 남아야 한다(계층 격리가 품질 1순위).
- 도메인 특성: 경합 단위는 방 하나(집합 루트)이고, 규칙(정원·팀 배정·순번·방장 위임·해산)이 컬럼 하나로 표현되지 않는다. 트랜잭션은 짧다(요청 1건 약 19ms, 외부 호출 없음). 팀 변경은 `rooms` 행을 바꾸지 않는다. 한 회원 한 방은 방에 걸치지 않는 규칙이다.
- 목표: 이 PC 기준 60 TPS(처리량 한계 약 105 TPS의 57%), 핫스팟에서 성공 정확히 빈자리 수, 서버 4초 안에 결론, 5xx 0건.

## 계층 관점 설명
[레이어] 도메인 객체(`Room`·`Participation`)와 도메인 예외는 바뀌지 않는다. 도메인 계약 `RoomRepository`에 `find_by_id_for_update(room_id)`만 추가한다. "바빠서 거절"은 도메인 규칙 위반이 아니므로 공통 예외(`src/exceptions.py`, `NotFoundError`·`GoneError`와 같은 방식)로 두고, 전역 핸들러가 409로 내보낸다. DB 오류(`IntegrityError`, `55P03` lock_not_available, 풀 `TimeoutError`)는 인프라·부트스트랩만 안다.

[모듈 협력 구조] 응용 서비스의 쓰기 동작 다섯 개(참가·팀 변경·나가기·게임 시작·제목 변경)는 `_get_room_for_update`로 방을 읽는다. 참가는 아래 순서를 지킨다.
1. 빠른 거절: 잠금 없이 방을 읽어 이미 찼거나 삭제됐으면 기존 도메인 예외(400). 판단은 도메인 속성(`is_full`·`is_active`)을 쓴다
2. 방 행 잠금: 저장소가 `SET LOCAL lock_timeout`을 걸고 `SELECT … FOR UPDATE`로 방·팀·참가자를 읽는다. 2초를 넘으면 바빠서 거절(409)
3. **잠금 뒤에** 현재 참가를 읽는다 — 같은 회원의 같은 방 중복 요청이 순차 요청과 같은 결과(변화 없음, D-006)가 된다
4. 도메인 메서드 → `save`(flush) → 상세 조회 → `get_db`의 commit에서 잠금 해제

방 생성은 잠글 방이 없으므로, 한 회원 한 방은 `participations.user_id` unique가 마지막 방어선이다. 저장소 `save()`가 flush에서 해당 제약의 `IntegrityError`를 `AlreadyParticipatingError`(400)로 바꾼다. `(room_id, join_order)` unique는 안전망이며 위반을 변환하지 않는다(생기면 버그 신호, 500).

[인프라] 지연 예산은 서버 4초 = 커넥션 풀 대기 1초(`db_pool_timeout`, 앱 전체) + 방 잠금 대기 2초(`db_lock_timeout_ms`, 쓰기 트랜잭션) + 처리 여유 1초. 클라이언트 시간 제한(5초, ADR-014)보다 짧아서 서버가 항상 먼저 결론을 낸다. 두 값은 ADR-003 방식의 설정으로 둔다. 잠금은 DB에 있으므로 워커·서버 수와 관계없이 성립한다. 새 unique 제약은 마이그레이션 도구가 없어(DRV-C-04) 새 DB에만 생기므로 개발·측정 DB를 다시 만든다.

## 결정 / 추천
결정: A — 도메인 규칙은 그대로 두고, 같은 방 쓰기는 방 행 잠금으로 줄 세우며, 대기 구간마다 상한을 두어 넘는 요청은 409로 빨리 거절한다. 세부 결정은 `docs/03-concurrency/05-decision.md` AD-01~08.

블로그 예시(콘서트 좌석)는 조건부 UPDATE를 골랐지만, 그 이유("선점만 짧게 끝내고 결제를 분리")는 이 도메인에 해당하지 않는다. 트랜잭션이 원래 짧고 규칙이 집합 전체에 걸쳐 있어, 조건부 UPDATE는 계층 격리만 깨고 잠금 시간은 줄이지 못한다.

## 결과
- 좋아지는 점: 동시 요청에서도 정원·팀 정원·한 회원 한 방·해산 1회가 지켜진다(AC-18-1~5). 조용한 위반이 사라지고, 위반 가능성은 안전망 제약으로 드러난다. 어떤 부하에서도 서버가 4초 안에 결론을 낸다. 지금 500인 "같은 회원 다른 방 동시 참가"가 400이 된다
- 감수할 점: 같은 방 요청은 차례로 처리되어 핫스팟에서 대기 중 커넥션을 쥔다(VC-05로 확인). 과부하 때는 빈자리가 있어도 2초 안에 차례가 오지 않으면 409. 풀 대기 1초는 앱 전체 설정이라 과부하 때 조회도 409가 날 수 있다. 새 쓰기 동작에서 잠금 조회를 잊으면 깨진다 → 컨벤션("방을 바꾸는 서비스 메서드는 `_get_room_for_update`로 읽는다")과 검사 게이트 추가
- 다시 검토할 조건: VC-05·VC-06을 넘으면 지연 예산 값을 먼저 조정하고, 그래도 넘으면 옵션 B를 다시 검토한다. 목표 규모에서 409가 나오면 `lock_timeout`·`pool_timeout`·풀 크기를 다시 본다. DB를 바꾸거나 쓰기를 여러 DB로 나누면 다시 검토한다
- 후속 작업: 저장소·서비스·예외·핸들러·설정·모델 구현, AC-18-1~5 통합 테스트, 측정 스크립트 s4~s6, 컨벤션·게이트 갱신, 7단계 부하 테스트 보고서
