# ADR-014: 지연 중 화면 피드백 — 즉시 로딩 + 3초 지연 안내 + 5초 시간 제한
- 상태: Accepted (user, 2026-11-10) — 7단계 화면 체크리스트 검증 대기
- 관련 계층: [레이어] [모듈 협력 구조]
- 근거: D-033, D-034, ADR-012(수동 조회), ADR-013(서버 4초 상한·409), DRV-C-05, REQ-106, REQ-128, VOC-11, CQ-08~12, CR-11·12, VC-08, DC-14~16, `docs/03-concurrency/05-decision.md` AD-09·10

## 맥락
- 긴급 요구사항(VOC-11): 사용자가 몰려 참가 요청이 대량으로 겹쳐도 화면이 멈췄다고 느끼면 안 되고, 처리 중임을 알려야 한다. 고객 답변으로 수치와 문구가 정해졌다 — 로딩은 **즉시**, **3초**에 지연 안내, **5초** 안에 결론. 처리하지 못한 요청은 "입장하지 못했습니다. 다시 시도해 주세요", 결과를 모르면 "입장 결과를 확인하지 못했습니다."
- 지금 화면: 목록의 참가는 누른 버튼 하나만 비활성화하고 로딩 표시가 없다(`rooms.js` `joinRoom`). 다른 방 버튼은 계속 눌려 같은 회원의 중복 요청이 생긴다. 공통 요청 함수(`api.js` `sendOnce`)의 `fetch`에는 시간 제한이 없다.
- 클라이언트가 포기해도 서버는 계속 처리한다(DC-16). 서버가 클라이언트보다 먼저 결론을 내는 것은 ADR-013(서버 4초)이 보장하고, 이 ADR은 화면 쪽 5초와 표시를 정한다.
- 제약: 외부 프론트엔드 프레임워크 없이 순수 JS(REQ-128), 자동 조회·폴링·실시간 푸시 금지(DRV-C-05, ADR-012).

## 계층 관점 설명
[레이어] 화면 JS(presentation의 정적 파일)만 바뀐다. 서버 계층·API 계약은 ADR-013에서 정한 409 하나가 늘어날 뿐이다. 화면은 문구 문자열이 아니라 **상태 코드**로 분기한다(D-016과 같은 원칙).

[모듈 협력 구조] 역할을 두 곳으로 나눈다.
- `api.js` `apiRequest`: 사용자 동작 하나 전체(401 → 재발급 → 재요청 포함)에 5초 시간 제한을 건다. 시간 초과·통신 실패는 "결과 모름"으로 구분해 돌려준다(현재 `status: 0`과 구분 가능하게). 모든 쓰기 동작이 이 함수를 거치므로 같은 상한을 얻는다.
- `rooms.js`: 화면 상태를 맡는다. 클릭 즉시(요청 전) 로딩 문구, 3초 타이머로 지연 안내, 처리 중 참가·방 만들기 버튼 일괄 비활성화(목록 화면에 상세 화면 `detailBusy`와 같은 방식 도입), 결론이 나면 타이머 정리·버튼 복구·문구 표시.

응답 → 문구:

| 서버 응답 | 참가 버튼 (목록·상세) | 그 밖의 쓰기 동작 |
|---|---|---|
| 200 | 방 상세로 이동 | 기존 동작 |
| 400 (사유 있는 거절) | 서버가 준 사유 문구 | 서버가 준 사유 문구 |
| 409 (바빠서 거절) | "입장하지 못했습니다. 다시 시도해 주세요" | "처리하지 못했습니다. 다시 시도해 주세요" |
| 시간 초과(5초)·통신 실패 | "입장 결과를 확인하지 못했습니다." | "처리 결과를 확인하지 못했습니다." |
| 처리 중 | 즉시 "입장 중…", 3초 뒤 "사람이 많아 처리가 늦어지고 있습니다" | 즉시 "처리 중…", 3초 뒤 같은 지연 안내 |

참가 버튼 문구는 고객 답변(CQ-11·12)이다. 그 밖의 동작 문구와 지연 안내 문구는 같은 구조로 맞춘 기본값이며, 고객 확인 전까지 바꿀 수 있다.

결과 모름 뒤에는 자동으로 다시 조회하지 않는다. 실제로 입장됐다면 사용자가 목록 [새로고침]을 누를 때 기존 "현재 참가 방" 표시(`renderCurrentRoom`)에 나타난다.

## 결정 / 추천
결정: A — 공통 요청 함수에 5초 시간 제한을 두고, 화면은 즉시 로딩·3초 지연 안내·버튼 일괄 비활성화·상태 코드별 문구로 "멈추지 않았음"을 알린다.

블로그 예시의 Waiting Room은 "대기 상태와 순번을 보여 주며 화면을 살려 두는" 방식이었다. 이 프로젝트는 대기열이 필요 없고(CQ-04) 순번을 실시간으로 알릴 수 없으므로(DRV-C-05), 서버의 대기 상한(ADR-013)과 화면의 로컬 피드백(이 ADR)으로 같은 목표를 이룬다.

## 검증 기준 (7단계, VC-08 체크리스트)
| # | 확인 항목 | 기대 |
|---|---|---|
| 1 | 참가 버튼 클릭 직후 | 요청 전에 로딩이 보인다 |
| 2 | 처리 중 | 화면의 모든 참가·방 만들기 버튼이 비활성화된다 (목록·상세) |
| 3 | 3초 경과 | 지연 안내로 바뀐다 |
| 4 | 서버 409 | "입장하지 못했습니다. 다시 시도해 주세요", 버튼 다시 활성화 |
| 5 | 5초 시간 초과·통신 실패 | "입장 결과를 확인하지 못했습니다.", 버튼 다시 활성화 |
| 6 | 사유 있는 거절 | 기존 사유 문구 |
| 7 | 결과 모름 뒤 목록 [새로고침] | 실제로 입장됐다면 "현재 참가 방"에 표시 |
| 8 | 토큰 만료 → 재발급 → 재요청 | 재발급 시간을 포함해 5초 안에 결론 |

재현 방법: 서버 지연은 psql에서 방 행 잠금을 쥐고(`BEGIN; SELECT … FROM rooms WHERE id = … FOR UPDATE;`) 만든다. 운영 코드에 테스트용 지연을 넣지 않는다. 클라이언트 5초 시간 초과는 브라우저 개발자 도구의 네트워크 속도 제한으로 확인한다.

## 결과
- 좋아지는 점: 어떤 부하에서도 사용자는 즉시 반응을 보고 5초 안에 결론을 받는다. 같은 회원의 화면 내 중복 요청이 사라진다. 모든 쓰기 동작이 같은 시간 제한을 얻는다
- 감수할 점: 네트워크 단절 등으로 결과를 모르는 경우는 남고, 사용자가 [새로고침]으로 확인해야 한다. 여러 탭에서의 중복 요청은 화면이 막지 못한다(서버가 ADR-013으로 방어). 평소처럼 빠른 요청(약 20ms)에서도 로딩 문구가 잠깐 바뀐다
- 다시 검토할 조건: 고객이 결과 모름을 화면이 스스로 확인하기를 원하면(옵션 D) 자동 조회 금지(DRV-C-05) 결정을 먼저 다시 연다. 실시간 푸시가 허용되면 대기 순번 안내를 다시 검토한다
- 후속 작업: `api.js`·`rooms.js`(필요 시 템플릿) 구현, VC-08 체크리스트 확인, 지연 안내·그 밖의 동작 문구 고객 확인
