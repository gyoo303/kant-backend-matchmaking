# ADR-015: 진입 단계 동시 처리 상한 — 처리 중 요청 150개를 넘으면 즉시 409
- 상태: Accepted (user, 2026-11-10) — 7단계 2차 측정으로 검증
- 관련 계층: [레이어] [인프라]
- 근거: D-033, D-034, D-037, ADR-013(서버 대기 상한), VC-02, VC-06, `loadtest/adr013-report-2026-11-10.md` §5·§6

## 맥락
- ADR-013은 서버 대기 구간마다 상한을 두었다(커넥션 풀 대기 1초, 방 잠금 대기 2초). 두 상한은 요청이 **DB 연결을 기다리기 시작한 뒤**에만 걸린다.
- 7단계 1차 측정의 과부하(s6: 처리 한계를 넘는 속도 + 핫스팟 300명)에서 요청은 그보다 앞 단계(이벤트 루프 차례, 요청 읽기, 접속 대기열)에서 쌓였다. 이 단계에는 상한이 없다. 그래서 409로 빨리 거절된 요청은 254건이고, 5초 시간 초과는 3,278건이었다. 시간 초과의 5~7%는 서버가 늦게 처리해 "결과 모름 + 실제로는 입장"이 되었다. VC-06(max 4초)은 불합격이었다.
- 제약: 기술 스택 변경 불가(Redis·별도 게이트웨이 없음), uvicorn 워커 1개.

## 검토한 옵션
| 옵션 | 장점 | 단점 | 되돌리기 비용 |
|---|---|---|---|
| A. (채택) 앱 맨 앞 순수 ASGI 미들웨어가 `/api` 처리 중 요청 수를 세고, 상한에 닿으면 일을 시작하지 않고 즉시 409 | 대기가 쌓이기 전에 결론이 남, 거절 비용이 가장 작음, 다시 눌러도 안전(일을 시작하지 않음) | 상한 값을 측정으로 정해야 함, 워커가 늘면 워커마다 따로 셈 | 낮음 |
| B. 미들웨어가 상한에서 짧게 기다렸다가(예: 0.5초) 자리가 나면 처리 | 순간 몰림을 조금 더 흡수 | 대기 상한이 하나 더 늘어 지연 예산이 복잡해짐 | 낮음 |
| C. uvicorn `--limit-concurrency` | 코드 없음 | 503을 돌려줘 D-034(409)·VC-02(5xx 0건)와 어긋남, 화면 문구 분기가 깨짐 | 낮음 |
| D. 상한 없이 VC-06을 목표 규모로만 한정 | 변경 없음 | 처리 한계를 넘으면 화면 5초 시간 초과와 "결과 모름"이 대량 발생 | 없음 |

## 결정
- A를 채택한다. 상한은 **150**이고 `.env` `MAX_INFLIGHT_REQUESTS`로 바꿀 수 있다.
- 상한 값의 범위는 echo를 끈 조건의 측정에서 계산했다(1차 보고서 §7).
  - 아래 한계는 목표 규모(s5)에서 동시에 처리 중인 요청 수의 최댓값이다. 핫스팟 100건 + 배경 60 TPS × 0.285초 ≈ 117이므로, 상한이 이보다 작으면 목표 규모에서도 409가 생긴다.
  - 위 한계는 4초 × 처리 한계 ÷ (max/p50 비율)로 계산한다. 4 × 118 ÷ 2.6 ≈ 180이므로, 상한이 이보다 크면 과부하에서 4초를 넘는다.
- 응답은 409이고 본문은 `ServiceBusyError`와 같은 문구다. 화면은 이미 409를 "입장하지 못했습니다. 다시 시도해 주세요"로 보여 주므로 바뀌지 않는다(ADR-014).
- `/api`로 시작하는 경로만 센다. 화면(HTML)과 정적 파일은 세지 않는다.
- 위치는 로깅 미들웨어보다 바깥, CORS보다 안쪽이다. 거절된 요청은 무거운 로깅을 거치지 않는다. 대신 거절 로그는 1초에 한 줄(`inflight limit reached: rejected=N`)로 묶어 남긴다. 상한의 절반을 넘는 새 최댓값은 `inflight peak=N`으로 남겨, 다음에 상한 값을 정할 근거로 쓴다.

## 계층 관점 설명
[레이어] 도메인·응용 서비스·저장소는 바뀌지 않는다. 진입 단계(presentation 바깥, ASGI)에서 요청을 받기 전에 거절한다. [인프라] 카운터는 프로세스 메모리에 있다. 워커 1개라 이벤트 루프 하나가 세므로 잠금이 필요 없다.

## 결과
- 검증: 7단계 2차 측정 s5(목표 규모 409 0건), s6(과부하 max 4초 이하, 5초 시간 초과 감소). 단위 테스트는 `tests/unit/test_inflight_limit.py`.
- 감수할 점:
  - 과부하 때는 빈자리가 있어도 거절될 수 있다(ADR-013과 같은 성격).
  - 상한은 순간 동시 처리 수만 본다. 그보다 앞의 OS 접속 대기열과 부하 발생기 쪽 지연은 줄이지 못한다.
- 다시 검토할 조건:
  - 워커 수나 처리 한계가 바뀌면 상한을 다시 계산한다.
  - 목표 규모 측정에서 `inflight peak`가 상한의 90%를 넘으면 상한 또는 지연 예산을 다시 본다.
