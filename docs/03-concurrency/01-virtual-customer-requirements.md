# 01. 가상 고객 요구사항 (동시 참가 정합성, 1단계)

- 목적: 도전 A(동시 요청 무결성, D-018·ADR-009)를 "가상 고객의 요구"에서 출발해 설계·검증한다. 진행 순서는 D-032의 7단계를 따른다.
- 입력: `01-pm/01-requirements-inventory.md`(REQ-098~107, REQ-129), `01-pm/06-acceptance-criteria.md`(AC-18-*), `02-arch/01-drivers.md`(DRV-C-01·05·07, RISK-03·04)
- ⚠️ 이 문서의 고객·발언·답변은 **학습용 가상 시나리오**다. 수치는 실제 데이터가 아닌 가정이며, 2단계에서 PC 사양에 맞게 다시 환산한다.
- ID 규칙: `VOC-xx` 고객 발언, `CQ-xx` 되묻기, `CR-xx` 정리된 요구사항, `HA-xx` 숨은 전제

## 1. 가상 고객

| 항목 | 내용 |
|---|---|
| 고객 | 캐주얼 2vs2 게임 운영사 (가칭 "파티업") 서비스 운영 담당자 |
| 서비스 | 지금의 2vs2 공개 방 매치메이킹 (방 생성·참가·팀 변경·게임 시작) |
| 고민 | 이벤트 공지 직후 참가 요청이 몰릴 때 "4명 방에 5명", "오류 화면" 같은 문제가 걱정된다 |
| 운영 여건 | 개발·운영 인력이 적다. 서버 한 대, 지금 기술 스택 그대로 |

## 4. 모호한 요구사항 되묻기 (CQ)

| ID | 모호한 말 | 되물은 질문 | 고객 답변 (가정) | 정리 |
|---|---|---|---|---|
| CQ-01 | "한꺼번에" (VOC-01) | 이벤트 때 최대 몇 명이 들어오나요? 언제 가장 몰리나요? | "지난 이벤트 때 공지 후 5분간 동시 접속이 1,000명쯤이었어요. 참가 시도는 처음 1분에 대부분 몰렸고요." | 규모: 동시 접속 약 1,000명, 피크 구간 1분. **2단계에서 이 PC 기준 600명(목표 60 TPS)으로 축소** (`02-criteria.md` §3) |
| CQ-02 | "제일 많이 몰리는" (VOC-06) | 방 하나에 동시에 몇 명까지 누를까요? | "정확히는 모르지만, 인기 방에는 수십 명이 동시에 누르는 것 같아요." | 핫스팟: 빈자리 1~3개인 방에 최대 100명 동시 참가로 가정 |
| CQ-03 | "금방" (VOC-05) | 결과를 몇 초 안에 받아야 하나요? | "1초 안이면 좋고, 2~3초까지는 참아요. 멈춘 것처럼만 안 보이면 됩니다." | 응답 시간 목표는 2단계에서 수치로 정함 |
| CQ-04 | 실패한 사람의 다음 행동 | 못 들어간 사람을 서버가 대기시키거나 자동으로 다른 방에 넣어야 하나요? | "아니요. 본인이 다른 방을 고르거나 새로 만들면 돼요." | 대기열·자동 배정 불필요 (REQ-120과 일치). 실패는 즉시 거부 응답 |
| CQ-05 | 공정성 | 먼저 누른 사람이 반드시 먼저 들어가야 하나요? | "누른 순서까지 정확할 필요는 없어요. 들어간 사람과 못 들어간 사람이 확실하면 됩니다." | 엄격한 선착순 보장 불필요. 성공·실패가 확정적이면 됨 |
| CQ-06 | "오류 화면" (VOC-04) | 몰릴 때 일부 요청이 오류(500)로 끝나는 것은 어디까지 괜찮나요? | "0건이었으면 좋겠어요." | 5xx 0건. 거부는 모두 사유가 있는 400 |
| CQ-07 | 참가 외 동작 (VOC-07) | 팀 변경·나가기·시작도 몰리나요? | "그건 방 안 4명끼리라 많이 몰리진 않아요. 다만 이상한 상태가 되면 안 돼요." | 참가는 정합성과 성능 둘 다, 나머지 동작은 정합성만 보장 |

|---|---|---|---|---|

| CR-02 | 핵심 규칙 | 한 회원은 동시 요청 상황에서도 현재 참가가 1건이다 (참가·생성 모두) | VOC-03 | REQ-099, AC-18-2, RISK-04 |

| CR-06 | 품질 (핫스팟) | 한 방에 최대 100명이 동시에 참가해도 CR-01·CR-04를 지키고, 성공 인원은 빈자리 수와 같다 | VOC-06, CQ-02 | AC-18-1 확장 |
| CR-07 | 기능 | 실패한 사용자는 대기시키지 않고 즉시 거부한다. 선착순 순서는 보장하지 않는다 | CQ-04, CQ-05 | REQ-120 |

| CR-09 | 제약 | 실시간 푸시(WebSocket·SSE)와 자동 조회(폴링)를 쓰지 않는다 | VOC-09 | DRV-C-05 |

## 6. 숨은 전제 (HA) — 고객이 말하지 않았지만 아키텍트가 찾은 것

| ID | 숨은 전제 | 왜 중요한가 | 다음 단계로 넘길 질문 |
|---|---|---|---|
| HA-01 | 응답이 늦으면 사용자는 버튼을 다시 누른다 (같은 요청 재전송) | 재전송이 두 번째 참가나 500을 만들면 안 된다. 같은 방 재참가는 이미 "변화 없음"(D-006) | 동시에 도착한 같은 회원의 중복 요청도 멱등한가? |
| HA-02 | 인기 방 하나의 몰림이 다른 방·목록 조회까지 느리게 만들면 안 된다 | 잠금을 기다리는 요청이 커넥션 풀(20개)을 붙잡으면 서비스 전체가 멈춘다. 고객의 "멈춰 보이면 안 된다"(CQ-03)는 사실 **가용성** 요구다 | 핫스팟 경합이 커넥션 풀을 고갈시키지 않는가? |
| HA-03 | DB 제약 위반도 사용자에게는 "규칙 위반"이다 | 지금은 `participations.user_id` unique 위반·`join_order` 충돌이 500으로 나간다(ADR-009 감수할 점) | 제약 위반을 어느 계층에서 도메인 예외로 바꾸는가? |
| HA-04 | 이벤트 직후에는 참가뿐 아니라 로그인·목록 조회도 함께 몰린다 | 로그인(bcrypt)은 CPU를 많이 써서 같은 서버의 참가 처리량을 깎는다 | 부하 테스트에서 로그인을 측정 구간에서 뺄 것인가? (범위는 2단계에서 결정) |
| HA-05 | 서버 1대여도 uvicorn 워커가 여러 개일 수 있다 | 프로세스 메모리 안의 잠금(`asyncio.Lock`)은 워커 간에 효과가 없다 | 검증은 워커 1개와 여러 개 중 어떤 구성으로 할 것인가? |

## 7. 범위

- **포함:** 참가(정합성 + 성능), 방 생성의 한 회원 한 방(정합성), 팀 변경·나가기·게임 시작의 동시 요청 정합성(AC-18-3~5)
- **제외:** 대기열·자동 매칭(CR-07), 실시간 푸시(CR-09), 로그인 처리량 개선(HA-04는 측정 조건으로만 다룸), 다중 서버 확장

## 8. 다음 단계 (2단계)로 넘기는 입력

> 2단계 결과: `02-criteria.md` — 목표 60 TPS (동시 접속 600명 기준), 검증 기준 VC-01~05

- 규모: 동시 접속 약 1,000명, 피크 1분 (CQ-01) → 목표 TPS 환산
- 응답 시간: "1초 이내 선호, 2~3초 한계" (CQ-03) → p95/p99 기준
- 핫스팟: 한 방 100명 동시 (CQ-02) → 시나리오 정의
- 정합성·오류: CR-01~04 → 위반 0건, 5xx 0건 판정 기준
- PC 사양 측정과 기준선(잠금 없는 현재 코드) 측정 필요
