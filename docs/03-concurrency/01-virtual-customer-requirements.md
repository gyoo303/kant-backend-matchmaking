# 01. 가상 고객 요구사항 (동시 참가 정합성, 1단계)

- 목적: 도전 A(동시 요청 무결성, D-018·ADR-009)를 "가상 고객의 요구"에서 출발해 설계·검증한다. 진행 순서는 D-032의 7단계를 따른다.
- 입력: `01-pm/01-requirements-inventory.md`(REQ-098~107, REQ-129), `01-pm/06-acceptance-criteria.md`(AC-18-*), `02-arch/01-drivers.md`(DRV-C-01·05·07, RISK-03·04)
- ⚠️ 이 문서의 고객·발언·답변은 **학습용 가상 시나리오**다. 수치는 실제 데이터가 아닌 가정이며, 2단계에서 PC 사양에 맞게 다시 환산한다.
- ID 규칙: `VOC-xx` 고객 발언, `CQ-xx` 되묻기, `CR-xx` 정리된 요구사항, `HA-xx` 숨은 전제

## 6. 숨은 전제 (HA) — 고객이 말하지 않았지만 아키텍트가 찾은 것

| ID | 숨은 전제 | 왜 중요한가 | 다음 단계로 넘길 질문 |
|---|---|---|---|
| HA-01 | 응답이 늦으면 사용자는 버튼을 다시 누른다 (같은 요청 재전송) → **CR-12로 승격** | 재전송이 두 번째 참가나 500을 만들면 안 된다. 같은 방 재참가는 이미 "변화 없음"(D-006) | 동시에 도착한 같은 회원의 중복 요청도 멱등한가? |
| HA-02 | 인기 방 하나의 몰림이 다른 방·목록 조회까지 느리게 만들면 안 된다 → **CR-13으로 승격** | 잠금을 기다리는 요청이 커넥션 풀(20개)을 붙잡으면 서비스 전체가 멈춘다. 고객의 "멈춰 보이면 안 된다"(CQ-03)는 사실 **가용성** 요구다 | 핫스팟 경합이 커넥션 풀을 고갈시키지 않는가? |
| HA-03 | DB 제약 위반도 사용자에게는 "규칙 위반"이다 | 지금은 `participations.user_id` unique 위반·`join_order` 충돌이 500으로 나간다(ADR-009 감수할 점) | 제약 위반을 어느 계층에서 도메인 예외로 바꾸는가? |
| HA-04 | 이벤트 직후에는 참가뿐 아니라 로그인·목록 조회도 함께 몰린다 | 로그인(bcrypt)은 CPU를 많이 써서 같은 서버의 참가 처리량을 깎는다 | 부하 테스트에서 로그인을 측정 구간에서 뺄 것인가? (범위는 2단계에서 결정) |
| HA-05 | 서버 1대여도 uvicorn 워커가 여러 개일 수 있다 | 프로세스 메모리 안의 잠금(`asyncio.Lock`)은 워커 간에 효과가 없다 | 검증은 워커 1개와 여러 개 중 어떤 구성으로 할 것인가? |

## 7. 범위

- **포함:** 참가(정합성 + 성능), 방 생성의 한 회원 한 방(정합성), 팀 변경·나가기·게임 시작의 동시 요청 정합성(AC-18-3~5)
- **포함 (긴급 추가):** 화면 피드백(CR-11, 화면 JS), 중복 요청(CR-12), 목표를 넘는 부하에서의 응답 시간 상한과 빠른 거절(CR-13)
- **제외:** 대기열·자동 매칭(CR-07), 실시간 푸시(CR-09), 로그인 처리량 개선(HA-04는 측정 조건으로만 다룸), 다중 서버 확장, 결과 모름 이후의 자동 확인 조회(폴링 금지 DRV-C-05 — 사용자가 목록에서 확인)
