## 3. 목표 TPS 환산

| 단계 | 고객 수치 (1단계 가정) | 이 PC 기준 (채택) |
|---|---|---|
| 피크 동시 접속 | 1,000명 | **600명** |
| 피크 1분 안에 참가 시도 비율 | 80% | 80% |
| 1인당 시도 횟수 (실패 후 다른 방 재시도 포함) | 1.5회 | 1.5회 |
| 평균 TPS = 접속 × 비율 × 횟수 ÷ 60초 | 20 TPS | 12 TPS |
| 몰림 배수 (피크 초 ÷ 평균) | ×5 | ×5 |
| **목표 TPS** | 100 TPS | **60 TPS** |
| 처리량 한계 대비 | 95% (여유 없음) | **57%** (60~70% 이내) |

고객 수치 100 TPS는 C(≈105)의 95%라 여유가 없어서, 동시 접속을 600명으로 줄여 목표를 60 TPS로 잡았다.

- VC-03의 p95·p99 한계는 고객 답변("1초 안이면 좋고, 2~3초까지는 참는다", CQ-03)에서 정했다. 기준선(p95 22ms)과 차이가 커서, 7단계에서는 **기준선 대비 증가폭도 함께 기록**해 대안의 비용을 비교한다.
- 공정성(선착순)은 기준에 넣지 않는다(CQ-05).
- VC-03(평소 목표, p95 ≤ 500ms)과 VC-06(최악의 경우 상한, max ≤ 4초)은 의미가 다르다. 3초(CQ-09)는 목표 응답 시간이 아니라 화면이 지연 안내로 바뀌는 시점이다.
- 7단계부터 부하 발생기 시간 제한을 30초에서 **5초**로 바꿔 실제 클라이언트와 맞춘다. 시간 초과는 "결과 모름"으로 따로 센다.

### 4.1 VC-08 화면 체크리스트

| # | 확인 항목 | 기대 |
|---|---|---|
| 1 | 참가 버튼 클릭 직후 | 요청을 보내기 전에 처리 중 표시(로딩)가 보인다 |
| 2 | 처리 중 | 화면의 모든 참가·방 만들기 버튼이 비활성화된다 (목록·상세 모두) |
| 3 | 3초 경과 | 지연 안내로 바뀐다 |
| 4 | 서버가 바빠서 거절 | "입장하지 못했습니다. 다시 시도해 주세요"가 보이고 버튼이 다시 활성화된다 |
| 5 | 5초 경과(클라이언트 시간 초과) 또는 통신 실패 | "입장 결과를 확인하지 못했습니다."가 보이고 버튼이 다시 활성화된다 |
| 6 | 사유 있는 거절 (꽉 참 등) | 기존 사유 문구가 보인다 |
| 7 | 결과 모름 뒤 목록 [새로고침] | 실제로 입장됐다면 "현재 참가 방"에 표시된다 |
| 8 | 토큰 만료 후 재발급·재요청 | 재발급 시간까지 포함해 5초 안에 결론 |

- 재현 방법: 서버 쪽 지연은 psql에서 방 행 잠금을 쥐고 있는 방식(`BEGIN; SELECT … FROM rooms WHERE id = … FOR UPDATE;`)으로 만든다. 운영 코드에 테스트용 지연을 넣지 않는다. 클라이언트 5초 시간 초과는 브라우저 개발자 도구의 네트워크 속도 제한으로 확인한다.

## 5. 다음 단계 (3단계)로 넘기는 사실

- 정합성 위반은 지금 **500 없이 조용히** 일어난다 → 제약이 없는 곳(`join_order`, 정원·팀 정원)은 DB가 막아 주지 않는다.
- 처리량 한계는 워커 1개 기준 ≈105 TPS이고 목표는 60 TPS → 대안이 처리량을 약 40% 넘게 깎으면 VC-04를 어긴다.
- 핫스팟 100명은 거의 동시에(약 0.5초 안) 도착한다 → 잠금 대기가 생기면 그 시간만큼 커넥션을 붙잡는다(VC-05).
- 처리 한계를 넘으면(s1 c=200) max가 13.9초까지 늘어난다 → 지금 구조로는 VC-06(4초 상한)을 지킬 수 없다. 대기 시간에 상한을 두고 넘으면 빨리 거절해야 한다.
- 7단계에 추가할 측정 시나리오: s4(중복 요청), s5(핫스팟 + 60 TPS 동시), s6(과부하 120 TPS + 핫스팟 300명).
