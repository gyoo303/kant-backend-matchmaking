# 03. 문제 도메인의 특성 (동시 참가 정합성, 3단계)

- 입력: `01-virtual-customer-requirements.md`(CR·HA), `02-criteria.md`(VC, 기준선), `loadtest/baseline-report-2026-11-09.md`
- 코드 기준: `src/rooms/application/service.py`, `src/rooms/domain/room.py`, `src/rooms/infrastructure/repositories.py`·`models.py`, `src/database.py`
- 목적: 대안을 고르기 전에 "이 도메인에서 경합이 어떤 모양으로 생기는가"를 정리하고, 4단계에서 답할 설계 질문(DQ)을 뽑는다
- ID 규칙: `DC-xx` 도메인 특성, `DQ-xx` 설계 질문

## 1. 지금 참가 요청이 처리되는 모습

`POST /api/rooms/{id}/participants` 한 건은 요청 하나 = 세션 하나 = 트랜잭션 하나(D-029)로 처리된다. 격리 수준은 PostgreSQL 기본값 READ COMMITTED이고, 잠금은 없다.

| 순서 | 하는 일 | SQL (코드 기준 추정) |
|---|---|---|
| 1 | 인증: 회원 조회, 블랙리스트 확인 | SELECT 2 |
| 2 | `find_current_participation(user_id)` — 이 회원의 현재 참가 | SELECT 1~2 |
| 3 | `find_by_id(room_id)` — 방 + 팀 + 참가자 로딩 (**잠금 없음**) | SELECT 3 |
| 4 | `room.join()` — 도메인이 정원·한 방·삭제 여부 검사 후 `last_join_order + 1`, 팀 배정 | (파이썬) |
| 5 | `save(room)` — 방을 다시 읽고 참가 행 INSERT, `rooms.last_join_order` UPDATE, flush | SELECT 3 + INSERT 1 + UPDATE 1 |
| 6 | `get_room_detail` — 응답용 상세 (참가자 닉네임은 회원별 `session.get`) | SELECT 2~5 |
| 7 | `get_db`가 commit | COMMIT |

- 순차 요청 1건이 약 **19ms**다(기준선 S1 c=1). SQL 왕복이 15번 안팎이라, 대부분이 앱 ↔ DB 왕복 시간이다.
- 트랜잭션은 1번의 첫 SELECT부터 7번의 commit까지 열려 있다. 3번에서 잠금을 잡는다면, **잠금을 쥐고 있는 시간은 4~7번(대략 요청 시간의 절반, 약 10ms)**이다.

### 핫스팟에서 정합성이 깨지는 과정

```
요청 A: [3] 방 읽기 (참가자 1명, last_join_order=1) ─ [4] 빈자리 있음 → join_order=2 ─ [5] INSERT, UPDATE last=2 ─ commit
요청 B: [3] 방 읽기 (참가자 1명, last_join_order=1) ─ [4] 빈자리 있음 → join_order=2 ─ [5] INSERT, UPDATE last=2 ─ commit
```

- 두 요청이 **같은 스냅샷**을 읽고 각자 "빈자리 있음"으로 판단한다. 이것이 lost update(check-then-act 경쟁)다.
- `participations` PK는 `(room_id, user_id)`라 서로 다른 회원의 INSERT는 충돌하지 않는다. `(room_id, join_order)` unique도 없어서 `join_order`가 겹쳐도 저장된다.
- `rooms` UPDATE는 READ COMMITTED에서 행 잠금을 잠깐 잡지만, 뒤에 온 요청은 앞 요청의 commit을 기다린 뒤 **자기 값으로 덮어쓴다**. 정원 검사는 이미 끝난 뒤라 막지 못한다.
- 그래서 기준선 S2에서 4인 방에 7~10명이 들어갔고, 5xx는 0건이었다(조용한 위반).

## 2. 도메인 특성 (DC)

| ID | 특성 | 근거 | 설계에 주는 의미 |
|---|---|---|---|
| DC-01 | **경합 단위는 방(집합 루트) 하나다.** 정원 4명, 팀 정원 2명, `join_order` 증가, 방장 위임, 해산 1회가 모두 `Room` 집합 안의 규칙이다 | `room.py`, INV-02~08 | 방 하나를 단위로 줄 세우거나 충돌을 찾으면 집합 안의 규칙이 모두 지켜진다 |
| DC-02 | **규칙이 컬럼 하나로 표현되지 않는다.** 팀 배정(A가 차면 B), 방장 위임(가장 먼저 들어온 사람), 해산 시 전원 종료는 여러 행을 함께 봐야 한다 | `Room.join`, `leave`, `start_game` | 조건부 UPDATE 한 문장이나 CHECK 제약으로 옮기면 규칙이 SQL로 새어 나가 계층 격리(DRV-Q-01)를 깬다 |
| DC-03 | **방 행이 바뀌지 않는 변경도 있다.** 팀 변경은 `participations.team_id`만 바꾸고 `rooms` 행은 그대로다 | `save()` 2번 케이스 | `rooms` UPDATE 충돌에 기대는 방식은 팀 변경 경합(AC-18-3)을 놓친다. 방 단위 직렬화나 버전은 **모든 변경에서** 방 행을 거쳐야 한다 |
| DC-04 | **방에 걸치지 않는 규칙이 하나 있다.** "한 회원 한 방"은 여러 방에 걸친 규칙이고, 방 생성은 잠글 방 행이 아직 없다 | REQ-099, `Room.create` | 방 단위 제어로는 막을 수 없다. 이미 있는 `participations.user_id` unique가 마지막 방어선이고, 위반(`IntegrityError`)을 400으로 바꿔야 한다(지금은 500) |
| DC-05 | **경합은 좁고 짧고 뾰족하다.** 자리는 방마다 3개뿐이라 핫스팟은 빈자리 3개가 차는 순간 끝난다. 100명이 약 0.5초 안에 도착한다 | 기준선 S2 (0.65~0.67s) | 경합 시간은 짧지만 동시 대기 인원은 많다. 대기가 길어지면 그동안 커넥션을 붙잡는다 |
| DC-06 | **핫스팟 요청의 대부분(97%)은 거절된다.** 성공 3건, 나머지 97건은 "방이 꽉 참" | VC-01 기대값 | 거절될 요청까지 같은 줄에 세우면 비용이 커진다. "가득 찬 방은 빨리 거절"할 여지가 있다 |
| DC-07 | **방끼리는 서로 독립이다.** 다른 방 참가는 같은 데이터를 건드리지 않는다 | 기준선 S1·S3 위반 0건 | 전역 잠금(테이블 잠금, 단일 큐)은 불필요한 직렬화다. 방 단위로 나눠야 처리량(VC-04)을 지킨다 |
| DC-08 | **트랜잭션 안에 외부 호출이 없고 짧다.** 결제처럼 몇 분씩 붙잡는 단계가 없다(약 19ms) | §1 | 잠금을 잡아도 오래 쥐지 않는다. 다만 상세 조회(6번)까지 트랜잭션 안이라 잠금 시간이 필요 이상으로 길다 |
| DC-09 | **공정성(선착순)은 필요 없다.** 들어간 사람과 못 들어간 사람이 확실하면 된다 | CQ-05 | 잠금 획득 순서를 보장하지 않아도 된다. 대기열이 없어도 된다(CQ-04) |
| DC-10 | **실패는 즉시 거절로 끝나고, 재시도는 사용자 몫이다.** 같은 방 재참가는 변화 없음(멱등) | CQ-04, D-006 | 서버 쪽 자동 재시도는 요구사항이 아니다. 재시도를 넣는다면 내부 구현용이고, 결과는 여전히 400으로 끝나야 한다 |
| DC-11 | **읽기가 훨씬 많지만 정확할 필요는 없다.** 목록·상세는 [새로고침] 때만 읽고(ADR-012), 잠시 낡아도 된다. 판단은 쓰기 요청 안에서 다시 한다 | REQ-107, ADR-012 | 조회 경로에는 잠금이 필요 없다. 정합성 제어는 쓰기 경로(참가·생성·팀 변경·나가기·시작)에만 둔다 |
| DC-12 | **충돌하는 동작 쌍이 정해져 있다.** 아래 §3 표 | AC-18-1~5 | 대안은 참가만이 아니라 다섯 가지 쓰기 동작 모두에 같은 방식으로 적용되어야 한다 |
| DC-13 | **커넥션 풀은 앱 전체가 함께 쓴다(최대 20).** 핫스팟 100명이 한 방에서 기다리면 다른 방 요청도 풀을 기다린다 | `config.py`, HA-02 | 대기하는 방식(DB 잠금 대기 / 앱 재시도 / 즉시 실패)이 VC-05(가용성)를 좌우한다 |

## 3. 같은 방에서 충돌하는 동작 쌍 (DC-12)

| 먼저 \ 동시에 | 참가 | 팀 변경 | 나가기 | 게임 시작 |
|---|---|---|---|---|
| **참가** | 정원·팀 정원 초과, `join_order` 중복 (AC-18-1) | 팀 정원 초과 | 삭제된 방에 참가자 남음 (REQ-104) | 해산된 방에 참가자 남음 (REQ-102) |
| **팀 변경** | | 같은 팀으로 동시 이동 → 팀 정원 초과 (AC-18-3) | 나간 사람의 팀 변경 | 시작 검사(2vs2)와 실제 구성 불일치 |
| **나가기** | | | 방장 동시 퇴장 → 없는 사람에게 위임 (REQ-103) | 해산과 퇴장 동시 (AC-18-5) |
| **게임 시작** | | | | 해산 2번 (AC-18-4) |

한 회원이 **서로 다른 방**에 동시에 참가·생성하는 경우(AC-18-2)는 이 표 밖이다(DC-04).

## 4. 블로그 예시(콘서트 좌석)와 비교

| 관점 | 콘서트 좌석 선점 | 2vs2 방 참가 (이 프로젝트) |
|---|---|---|
| 경합 자원 | 좌석 1개 (몇백 석이 동시에 인기) | 방 1개의 빈자리 1~3개 (방은 많고 서로 독립) |
| 규칙의 모양 | "좌석 주인이 없으면 차지" — 컬럼 하나로 표현 | 정원·팀 배정·순번·위임 — 집합 전체를 봐야 함 (DC-02) |
| 붙잡는 시간 | 선점 후 결제까지 몇 분 | 요청 하나 약 19ms, 외부 호출 없음 (DC-08) |
| 블로그의 선택 | 조건부 UPDATE (한 문장으로 선점 판단) | 같은 선택은 DC-02·DC-03 때문에 그대로 맞지 않음 → 4단계에서 비교 |
| 공통점 | 타협 불가 정합성, PostgreSQL 유지 제약, 대부분의 요청은 실패로 끝남 | 같음 (CR-01, CR-08, DC-06) |

## 5. 4단계로 넘기는 설계 질문 (DQ)

| ID | 설계 질문 | 관련 특성·기준 |
|---|---|---|
| DQ-01 | 같은 방에 대한 쓰기 요청을 **어떻게 줄 세우거나 충돌을 감지**할 것인가? (잠금 / 버전 / 조건부 갱신 / 격리 수준 / advisory lock …) | DC-01~03, DC-07, VC-01, VC-04 |
| DQ-02 | 방 단위 제어로 막을 수 없는 **한 회원 한 방**과 **방 생성**을 어떻게 지킬 것인가? DB 제약 위반을 **어느 계층에서 400으로** 바꿀 것인가? | DC-04, VC-02, HA-03 |
| DQ-03 | 핫스팟 대기가 **커넥션 풀을 고갈시켜 다른 방까지 느려지지 않게** 하려면? (대기 시간 상한, 빠른 거절, 트랜잭션 단축) | DC-05, DC-06, DC-13, VC-05 |
| DQ-04 | 도메인 규칙을 도메인 객체에 둔 채(계층 격리) 정합성 제어를 **어느 계층에 둘 것인가**? | DC-02, DRV-Q-01 |
| DQ-05 | 조용한 위반을 다시 만들지 않도록 **DB에 어떤 안전망 제약**을 더할 것인가? (예: `(room_id, join_order)` unique) | §1, VC-01 |

## 6. 대안 비교 전에 확인된 제약

- 스택 고정: PostgreSQL만 쓴다. Redis·메시지 브로커 없음 (CR-08)
- 서버 1대, 다만 uvicorn 워커가 여러 개일 수 있다 → 프로세스 메모리 안의 잠금(`asyncio.Lock`)은 해결책이 될 수 없다 (HA-05)
- 실시간 푸시·폴링 없음 (CR-09) → 대기열 순번을 사용자에게 알려 주는 방식은 쓸 수 없다
- 계층 격리가 품질 속성 1순위 (DRV-Q-01) → 도메인 규칙은 `rooms/domain`에 남아야 한다
