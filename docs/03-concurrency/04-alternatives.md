## 2. DQ-01 — 같은 방의 쓰기 요청을 어떻게 줄 세우거나 충돌을 감지할 것인가

### 2.1 대안

**A. 비관적 잠금 — 방 행 `SELECT … FOR UPDATE`**
- 쓰기 동작 다섯 개(참가·팀 변경·나가기·게임 시작·제목 변경)가 방을 읽을 때 `rooms` 행을 잠그고 읽는다. 같은 방 요청은 앞 요청이 commit할 때까지 기다린다.
- 기다린 뒤 읽으면 앞 요청이 commit한 최신 상태를 보므로, 도메인 검사(`room.join()` 등)가 그대로 유효하다.
- 팀 변경처럼 `rooms` 행을 바꾸지 않는 동작도 "읽을 때 잠금"이라 함께 막힌다(DC-03 해결).
- **잠금 뒤에 읽어야 하는 것**: 지금 서비스는 `find_current_participation`을 방 조회보다 **먼저** 부른다. 같은 회원이 같은 방에 두 번 동시에 요청하면 둘 다 "현재 참가 없음"을 읽고, 두 번째는 PK `(room_id, user_id)` 위반이 된다. 잠금을 잡은 **뒤에** 현재 참가를 읽어야 순차 요청과 같은 결과("변화 없음", D-006)가 나온다.
- 핫스팟 추정: 잠금을 쥔 구간(도메인 검사 → save → 상세 조회 → commit)은 성공 요청 약 10ms, 거절 요청은 save·상세 조회가 없어 더 짧다(약 3~5ms). 100명이면 마지막 요청은 약 0.3~0.6초 기다린다.
- 위험: 기다리는 동안 **커넥션을 쥐고 있다.** 핫스팟 대기 인원(최대 100)이 풀(20)보다 많아, 그동안 다른 방 요청은 풀이 빌 때까지 기다린다(E5).

**A′. 비관적 잠금 + 즉시 실패 (`FOR UPDATE NOWAIT`)**
- 잠금을 못 잡으면 기다리지 않고 바로 실패한다. 커넥션을 오래 쥐지 않는다.
- 하지만 100명이 동시에 오면 처음 1명만 잡고 나머지는 "잠시 후 다시"로 거절된다. **빈자리가 남았는데 거절**되므로 VC-01(성공 정확히 3건)을 어긴다. 고객의 "들어간 사람과 못 들어간 사람이 확실하면 된다"(CQ-05)와도 맞지 않는다.

**A″. 비관적 잠금 + 대기 상한 (`SET LOCAL lock_timeout`)**
- A와 같되, 잠금을 일정 시간(예: 2초) 넘게 기다리면 실패시킨다. 평소에는 A와 똑같이 동작하고, 비정상적으로 긴 대기만 끊는다.
- A의 안전장치로 쓸 수 있다. 실패를 어떤 응답으로 바꿀지(400 "잠시 후 다시" 등)를 정해야 한다(E6).

**B. 낙관적 잠금 — `rooms.version` + 충돌 시 재시도**
- 방을 저장할 때 `UPDATE rooms … WHERE id = :id AND version = :읽은값`으로 버전을 올린다. 0행이면 누군가 먼저 바꾼 것이므로 실패(SQLAlchemy `version_id_col` → `StaleDataError`).
- DC-03 때문에 팀 변경처럼 `rooms` 행이 그대로인 동작도 **버전을 강제로 올려야** 한다.
- 대기가 없어 커넥션을 오래 쥐지 않는다(E5 유리).
- 핫스팟: 100명이 같은 버전을 읽으면 1명만 성공한다.
  - **재시도 없이**: 99명이 거절되고 빈자리 2개가 남는다 → VC-01 위반(A′와 같은 문제).
  - **재시도하면**: 한 판에 1명씩만 성공하므로 빈자리 3개를 채우는 데 최소 3판, 그동안 실패한 요청이 모두 다시 읽고 다시 검사한다. 100명 기준 대략 100 + 99 + 98 ≈ 300번의 "읽고 검사하고 저장 시도"가 생긴다. 이후 방이 차면 나머지는 정상적으로 "꽉 참"으로 거절된다.
- 재시도는 트랜잭션을 다시 시작해야 한다. 지금 트랜잭션 경계는 `get_db`(요청 하나 = 트랜잭션 하나, D-029)라서, 서비스 안에서 재시도하려면 savepoint나 트랜잭션 경계 변경이 필요하다(E7).

**C. 원자적 조건부 UPDATE (블로그의 선택)**
- `rooms`에 현재 인원·팀별 인원 카운터를 두고 `UPDATE rooms SET current_count = current_count + 1, last_join_order = last_join_order + 1 WHERE id = :id AND deleted_at IS NULL AND current_count < 4 RETURNING …`처럼 한 문장으로 자리를 차지한다.
- 정원 하나는 깔끔하게 지킨다. 하지만 팀 배정(A가 차면 B), 팀 변경, 방장 위임, 해산 시 전원 종료는 같은 방식으로 옮기기 어렵다. 옮기면 **도메인 규칙이 SQL에 중복되거나 새어 나간다(E3 탈락, DC-02).** 카운터와 실제 참가 행이 어긋날 위험(비정규화)도 생긴다.
- 덤으로 알아 둘 점: 이 UPDATE도 행 잠금을 잡고 **commit까지 쥔다.** 요청 하나 = 트랜잭션 하나 구조에서는 잠금 시간이 A와 크게 다르지 않다. 블로그 예시가 빨랐던 이유는 "선점만 짧게 끝내고 결제를 분리"했기 때문이고, 이 프로젝트의 트랜잭션은 원래 짧다(DC-08).

**D. 격리 수준 SERIALIZABLE + 재시도**
- PostgreSQL SSI가 읽기-쓰기 충돌을 감지해 한쪽을 `40001`(serialization failure)로 실패시킨다. 코드 변경은 격리 수준 설정과 재시도뿐이다.
- 핫스팟에서는 B와 같은 재시도 폭증이 생긴다. 게다가 SSI는 충돌을 페이지·관계 단위로 넓게 잡을 수 있어, **서로 다른 방의 요청끼리도** 거짓 충돌이 날 수 있다 → 분산 부하 처리량(E4)이 떨어질 위험이 있다.
- 재시도 경계 문제(트랜잭션 재시작)는 B와 같다. 동작을 예측·설명하기 어렵다(E7).

**E. PostgreSQL advisory lock — `pg_advisory_xact_lock(방 키)`**
- 행 대신 "방 번호"라는 숫자 키로 잠근다. 동작은 A와 같다(기다림, commit 때 해제).
- 행이 없어도 잠글 수 있어서 **회원 번호로도 잠글 수 있다**(DQ-02에 쓸 수 있음).
- 하지만 잠금이 테이블·행과 묶여 있지 않아, "어떤 키로 잠그는지"가 코드 관례에만 있다. 방 번호와 회원 번호 키가 겹치지 않게 두 칸짜리 키(`pg_advisory_xact_lock(종류, 번호)`)를 써야 한다. ORM 밖의 SQL이 들어간다(E7).

**F. Redis 분산 락 — 탈락.** 스택 제약 위반(CR-08, E2).

**G. 앱 프로세스 안의 잠금(`asyncio.Lock`, 방별 큐) — 탈락.** uvicorn 워커가 여러 개면 워커끼리 효과가 없다(HA-05, E2). 워커 1개에서는 동작하지만 "실행 설정에 따라 정합성이 달라지는" 구조는 받아들일 수 없다.

**H. DB 제약만으로 막기 (unique·CHECK·트리거) — 단독으로는 탈락.**
- `(room_id, join_order)` unique를 추가하면 같은 순번을 받은 동시 요청 중 하나가 실패한다. 하지만 `join_order`는 재입장마다 계속 커지므로 "4명 초과"를 막지는 못한다.
- 정원·팀 정원은 여러 행에 걸친 조건이라 CHECK로 표현할 수 없다. 트리거로 옮기면 규칙이 DB로 새어 나간다(E3).
- → **해결책이 아니라 안전망**으로 DQ-05에서 다룬다.

## 3. DQ-02 — 한 회원 한 방·방 생성, 제약 위반을 어디서 400으로 바꿀 것인가

| 대안 | 얻는 것 | 치르는 것 |
|---|---|---|
| **2-1. 기존 `participations.user_id` unique + 저장소에서 `IntegrityError` → `AlreadyParticipatingError` 변환** | 이미 있는 제약을 그대로 쓴다. DB가 마지막 방어선. 변환은 저장소 `save()`의 flush 한 곳 | 어떤 제약이 깨졌는지(회원 중복 / 순번 중복) 제약 이름으로 구분해야 한다 |
| 2-2. 회원 행 잠금 (`users … FOR UPDATE`) | 같은 회원 요청을 줄 세움 | `rooms`가 `auth` 테이블을 잠근다 → 기능 간 결합(ADR-001) 증가, 모든 요청에 잠금 하나 추가 |
| 2-3. advisory lock (회원 번호 키) | 행 없이 회원 단위 직렬화, 방 생성에도 적용 | E의 단점(관례 의존, ORM 밖 SQL). 제약이 이미 막아 주므로 얻는 것이 적다 |

- 변환 위치: DB 오류는 인프라만 알아야 하고(계층 격리), 도메인 예외(`AlreadyParticipatingError`)는 이미 `rooms/domain`에 있다. 저장소가 잡아 도메인 예외로 바꾸면 서비스·라우터는 바뀌지 않는다. 전역 예외 핸들러가 400으로 내보낸다(CONV-05).
- 같은 회원의 같은 방 중복 요청은 DQ-01의 "잠금 뒤에 현재 참가 읽기"로 순차 요청과 같은 결과가 된다(PK 위반까지 가지 않음).

## 4. DQ-03 — 핫스팟 대기가 커넥션 풀을 고갈시키지 않게 하려면

| 대안 | 얻는 것 | 치르는 것 |
|---|---|---|
| 3-1. 대기 상한 `SET LOCAL lock_timeout` (A″) | 비정상적으로 긴 대기를 끊어 커넥션을 돌려준다 | 시간 초과를 어떤 응답으로 줄지 정해야 함. 상한을 너무 짧게 잡으면 A′처럼 빈자리를 남기고 거절 |
| 3-2. 가득 찬 방 빠른 거절 (잠금 없는 사전 확인) | 방이 찬 뒤 도착한 요청은 잠금 줄에 서지 않는다(DC-06) | 핫스팟은 0.5초 안에 몰려서, 방이 차기 **전에** 도착한 요청에는 효과가 없다. 조회가 한 번 늘어난다. 판단은 결국 잠금 뒤에 다시 해야 함 |
| 3-3. 잠금 쥐는 시간 줄이기 | 상세 조회(응답용)를 잠금 구간 밖으로 빼면 성공 요청의 잠금 시간이 줄어든다 | 지금은 commit이 `get_db` 끝에 있어(D-029) 상세 조회가 트랜잭션 안이다. 바꾸려면 트랜잭션 경계 규칙을 손대야 함 |
| 3-4. 커넥션 풀 키우기 | 다른 방 요청이 풀을 기다리는 일이 줄어든다 | 대기가 DB 쪽으로 옮겨갈 뿐이다. DB `max_connections=100` 한계 |
| 3-5. 아무것도 안 함 | 가장 단순 | VC-05 측정에서 다른 방 p95가 얼마나 늘어나는지에 달림 |

- 기준선 추정으로는 핫스팟 100명의 잠금 대기가 0.3~0.6초에 끝난다. **VC-05를 넘는지는 측정해 봐야 안다.** 7단계에서 핫스팟(s2)과 고정 속도 부하(s3)를 동시에 돌리는 시나리오(s5)로 확인한다.
- **긴급 요구사항 반영(2026-11-10):** 3-1(대기 상한)은 측정 결과와 관계없이 **필수**로 바뀐다(E9). 풀 대기 상한도 30초 → 1초로 줄인다(§7 DQ-06). 3-2(빠른 거절)는 잠금 줄을 줄여 꼬리 지연을 낮추므로 **권장**으로 올린다. 3-4(풀 키우기)는 여전히 효과가 작다.

## 5. DQ-04 — 정합성 제어를 어느 계층에 둘 것인가

| 대안 | 얻는 것 | 치르는 것 |
|---|---|---|
| **4-1. 응용 서비스가 "잠금 조회"를 고르고, 저장소가 구현** (`RoomRepository.find_by_id_for_update`) | 도메인 코드 무변경. 어떤 동작이 잠그는지 서비스에서 보인다. 계약은 도메인 `RoomRepository`에 메서드 하나 추가 | 새 쓰기 동작을 만들 때 잠금 조회를 잊으면 깨진다 → 컨벤션·게이트로 검사(ADR-006의 CONV-08·GATE-07 아이디어) |
| 4-2. 저장소의 `find_by_id`가 항상 잠금 | 잊을 위험 없음 | 조회 전용 경로에서도 잠그게 될 위험. 이름과 동작이 어긋남 |
| 4-3. 도메인에 버전 필드 (낙관적 B 선택 시) | 도메인이 동시성을 명시적으로 표현 | 도메인이 저장 방식(버전)을 알게 됨. B에서도 버전은 ORM(`version_id_col`)에만 둘 수 있으므로 필요 없음 |

## 6. DQ-05 — 조용한 위반을 막는 DB 안전망

| 대안 | 얻는 것 | 치르는 것 |
|---|---|---|
| **5-1. `participations (room_id, join_order)` unique 추가** | 제어가 빠진 경로에서 같은 순번이 생기면 조용히 저장되지 않고 오류가 된다. 기준선의 "join_order 중복"이 사라진다 | 정원 초과 자체는 못 막는다(순번이 다르면 통과). 마이그레이션 도구가 없어(DRV-C-04) `create_all`로 새 DB에만 생긴다 → 기존 개발 DB는 다시 만들어야 함 |
| 5-2. 안전망 없음 | 변경 없음 | 제어가 빠진 경로가 생기면 다시 조용히 깨진다 |

## 7. DQ-06 — 서버가 4초 안에 결론을 내게 하려면 (긴급 추가)

지연 예산(`03-domain-characteristics.md` §2.1): 풀 대기 1초 + 잠금 대기 2초 + 처리 여유 1초 = 서버 4초 < 클라이언트 5초.

| 대안 | 얻는 것 | 치르는 것 | 판정 |
|---|---|---|---|
| 6-1. `SET LOCAL lock_timeout = '2s'` (쓰기 트랜잭션) | 잠금 대기 상한. 넘으면 PostgreSQL이 `55P03`(lock_not_available)로 실패 → 저장소가 "바빠서 거절" 도메인 예외로 변환 | 거절 응답 정의 필요. 2초 안에 차례가 오지 않은 요청은 빈자리가 있어도 거절될 수 있음(과부하 때만) | **필수** |
| 6-2. `db_pool_timeout` 30초 → 1초 | 풀 고갈 시 무한정 기다리지 않음 → 목록 조회까지 멈추는 일 방지 | 앱 전체 설정이라 조회 요청도 1초 넘게 풀을 못 받으면 실패. 그 실패도 "바빠서 거절"로 바꿔야 함(`TimeoutError` 변환) | **필수** |
| 6-3. 가득 찬 방 빠른 거절 (3-2) | 방이 찬 뒤 도착한 요청이 잠금 줄에 서지 않아 꼬리 지연 감소 | 조회 1번 추가, 판단은 잠금 뒤 다시 | **권장** |
| 6-4. `statement_timeout` | 쿼리 하나가 오래 걸리는 경우까지 상한 | 쿼리가 짧아(약 1ms) 효과가 작고, 설정 하나가 늘어남 | 선택 (넣지 않음) |
| 6-5. 서버 전체 요청 시간 제한(미들웨어 `asyncio.timeout`) | 어떤 경로든 4초에서 강제 종료 | 처리 도중 취소되면 트랜잭션 정리·응답 형식이 복잡해짐. 6-1·6-2로 대기 구간이 모두 묶이므로 불필요 | 넣지 않음 |

### "바빠서 거절" 응답 형식 — 5단계에서 결정

화면은 이 응답을 다른 거절과 구분해 "입장하지 못했습니다. 다시 시도해 주세요"를 보여 줘야 한다(CQ-12). 5xx는 쓸 수 없다(VC-02).

| 후보 | 얻는 것 | 치르는 것 |
|---|---|---|
| 409 Conflict | "다른 요청과 충돌" 의미가 잠금 대기 초과와 맞음 | 풀 대기 초과(서버가 바쁨)와는 의미가 덜 맞음. 새 상태 코드를 핸들러·화면에 추가 |
| 429 Too Many Requests | "지금은 처리할 수 없으니 다시 시도"와 의미가 가장 가까움. `Retry-After` 헤더 사용 가능 | 보통 "한 사용자가 너무 많이 보냄"으로 읽혀 오해 소지. 새 상태 코드 추가 |
| 400 + 전용 사유 문구 | D-015 관례(거절은 400) 유지, 핸들러 변경 최소 | 화면이 문구 문자열로 구분해야 함(문구 바뀌면 분기 깨짐, D-016에서 피했던 방식) |

## 8. DQ-07 — 중복 요청 (긴급 추가)

| 위치 | 대안 | 판정 |
|---|---|---|
| 화면 | 7-1. 요청 하나가 처리되는 동안 **화면의 참가·방 만들기 버튼을 모두 비활성화**(상세 화면 `detailBusy`와 같은 방식을 목록 화면에도). 결론이 나면 다시 활성화 | **채택** |
| 화면 | 7-2. 누른 버튼만 비활성화 (현재) | 다른 방 버튼으로 중복 요청이 생김 → 불충분 |
| 서버 | 7-3. DQ-01 "잠금 뒤에 현재 참가 읽기"(같은 방 중복 → 변화 없음 200) + DQ-02 unique 위반 400 변환(다른 방 중복 → 이미 참가 중) | **채택** — 여러 탭은 화면이 못 막으므로 서버가 최종 방어선 |
| 서버 | 7-4. Idempotency-Key 헤더 + 처리 결과 저장 | 7-3으로 결과가 이미 하나로 확정되므로 얻는 것이 적고, 저장 테이블·만료 규칙이 늘어남 → 넣지 않음 |

## 9. DQ-08 — 화면 피드백 (긴급 추가)

| 대안 | 내용 | 판정 |
|---|---|---|
| 8-1. 로딩만 | 버튼 안 표시 + "입장 중…" 문구 | 3초 안내·5초 결론을 못 지킴 → 불충분 |
| **8-2. 로딩 + 3초 지연 안내 + 5초 클라이언트 시간 제한** | 클릭 즉시(요청 전) 로딩, 3초 타이머로 지연 안내, `AbortController`로 5초에 중단 → "입장 결과를 확인하지 못했습니다." | **채택** |
| 8-3. 화면 전체 오버레이 | 확실히 눈에 띔 | 무겁고, 목록·상세 화면 구조를 더 바꿔야 함 |

- 시간 제한은 `apiRequest` 한 번 호출 전체(토큰 재발급 후 재요청 포함)에 건다(CQ-10). 공통 함수에 두므로 다른 쓰기 동작도 같은 동작을 얻는다(CR-11).
- 결과 모름 뒤에는 자동으로 다시 조회하지 않는다(DRV-C-05). 실제로 입장됐는지는 사용자가 목록 [새로고침]에서 "현재 참가 방"으로 확인한다(CQ-11).
- 계층: 화면 JS(presentation의 정적 파일)만 바뀌고, 서버 계층 구조와는 독립이다. 응답 형식(§7)이 정해져야 문구 분기를 확정할 수 있다.

## 10. 정리 — 5단계에 올릴 후보

탈락: A(E9 — 잠금 대기 상한 없음, A″로 대체), A′(빈자리 남기고 거절), C(계층 격리 위반), F·G(제약 위반), H(단독으로는 불충분).

| 후보 | 구성 | 강점 | 약점 / 확인할 것 |
|---|---|---|---|
| **후보 1 (유력)** | **A″ 방 행 `FOR UPDATE`(잠금 뒤 읽기) + `lock_timeout` 2초** + 6-2 풀 대기 1초 + 6-3 가득 찬 방 빠른 거절 + 2-1 제약 위반 400 변환 + 4-1 서비스·저장소 배치 + 5-1 순번 unique + 7-1 버튼 일괄 비활성화 + 8-2 화면 피드백 | 도메인 무변경, 다섯 가지 쓰기 동작을 같은 방식으로 보호, 대기 구간마다 상한이 있어 4초 결론을 설정으로 보장, 동작이 예측 가능 | 핫스팟 대기 중 커넥션 점유(VC-05)와 과부하 때 바빠서 거절 비율(VC-06b)은 **측정 필요**. 바빠서 거절 응답 형식(§7)은 5단계 결정 |
| 후보 2 | B 낙관적 잠금 + 재시도(횟수·시간 상한) + 6-2 + 2-1 + 5-1 + 7-1 + 8-2 | 대기 없음 → 커넥션 점유 없음 | 핫스팟 재시도 낭비, 재시도 상한에 걸리면 빈자리를 남기고 거절(E1·E9 충돌), 트랜잭션 경계(D-029) 변경, 팀 변경 시 버전 강제 증가 |
| 후보 3 | D SERIALIZABLE + 재시도(상한) + 6-2 + 2-1 + 7-1 + 8-2 | 코드 변경이 가장 적음 | 서로 다른 방 사이 거짓 충돌로 VC-04 위험, 후보 2와 같은 E1·E9 충돌, 동작을 설명하기 어려움 |

- 후보 1은 블로그 판단 기준("타협 불가 정합성 1순위 + 기존 PostgreSQL 유지")에 이 도메인의 특성(DC-02 규칙이 집합 전체, DC-08 짧은 트랜잭션)을 더했을 때 가장 맞는다. 긴급 요구사항(E9)으로 재시도 계열 후보(2·3)와의 차이가 더 커졌다.
- 블로그가 조건부 UPDATE를 고른 이유("선점만 짧게, 결제 분리")는 이 프로젝트에 해당하지 않는다. 트랜잭션이 원래 짧고, 규칙이 컬럼 하나가 아니기 때문이다.
- 블로그의 Waiting Room에 해당하는 고객 요구("화면이 멈춘 것처럼 보이지 않게")는 대기열 대신 **대기 상한 + 빠른 거절 + 화면 피드백**으로 푼다. 대기열은 CQ-04로 불필요하고, 순번 안내는 실시간 푸시 금지(CR-09)로 쓸 수 없다.
- 후보 1의 측정 항목(VC-05, VC-06, VC-06a·b)은 추정만으로 판단하지 않는다. 7단계에서 s4~s6을 추가해 재고, 기준을 넘으면 4단계로 돌아와 지연 예산 값이나 후보 2를 다시 검토한다.
