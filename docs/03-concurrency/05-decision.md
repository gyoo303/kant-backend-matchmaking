# 05. Architecture Decision (동시 참가 정합성, 5단계)

- 입력: `04-alternatives.md` §10 후보, `02-criteria.md` VC-01~08, `03-domain-characteristics.md` §2.1 지연 예산
- 결정: **후보 1 채택** — 방 행 비관적 잠금(잠금 뒤 읽기) + 대기 구간마다 상한 + 빠른 거절 + DB 안전망 + 화면 피드백. "바빠서 거절"은 **409 Conflict** (사용자 결정, 2026-11-10, D-034)
- 다음 단계: 6단계에서 ADR로 남기고, 7단계에서 VC-01~08로 검증한다. 이 문서의 수치(2초·1초 등)는 7단계 측정으로 조정할 수 있다.
- ID 규칙: `AD-xx` 결정 항목

## 1. 결정 요약

| ID | 설계 질문 | 결정 | 버린 대안 (이유) |
|---|---|---|---|
| AD-01 | DQ-01 같은 방 쓰기 요청 제어 | **방 행 `SELECT … FOR UPDATE`**. 다섯 가지 쓰기 동작(참가·팀 변경·나가기·게임 시작·제목 변경)이 모두 잠금 조회로 방을 읽는다. **잠금을 잡은 뒤에** 현재 참가를 읽는다 | A′ NOWAIT(빈자리 남기고 거절), B 낙관적+재시도(재시도 상한과 정합성 충돌, 트랜잭션 경계 변경), C 조건부 UPDATE(규칙이 SQL로), D SERIALIZABLE(거짓 충돌·예측 어려움), E advisory lock(관례 의존), F Redis·G 프로세스 잠금(제약 위반) |
| AD-02 | DQ-06 잠금 대기 상한 | 잠금 조회 직전 `SET LOCAL lock_timeout = '2s'`. 넘으면 PostgreSQL `55P03` → 저장소가 "바빠서 거절"로 변환 | 상한 없음(E9 탈락), `statement_timeout`(효과 작음), 요청 전체 시간 제한 미들웨어(취소 처리 복잡) |
| AD-03 | DQ-06 커넥션 풀 대기 상한 | `db_pool_timeout` 30초 → **1초**. 넘으면 SQLAlchemy `TimeoutError` → 전역 핸들러가 "바빠서 거절"로 변환 | 풀 키우기(대기가 DB로 옮겨갈 뿐) |
| AD-04 | DQ-06 바빠서 거절 응답 | **409 Conflict** + `{"detail": "<사유 문구>"}`. 새 공통 예외(예: `ServiceBusyError`)와 핸들러 하나 추가. 화면은 상태 코드 409로 구분 | 429(한 사용자의 과다 요청으로 읽힘), 400 + 문구(문자열 분기, D-016에서 피한 방식), 503(VC-02 수정 필요) |
| AD-05 | DQ-03 가득 찬 방 빠른 거절 | 참가는 잠금 **전에** 잠금 없이 방을 한 번 읽어, 이미 찼거나 삭제된 방이면 바로 기존 도메인 예외(400)로 거절. 판단은 도메인 속성(`is_full`, `is_active`)을 그대로 쓰고, 통과하면 잠금 뒤에 다시 검사 | 사전 확인 없음(찬 뒤 도착한 요청까지 잠금 줄에 섬) |
| AD-06 | DQ-02 한 회원 한 방·방 생성 | 기존 `participations.user_id` unique를 마지막 방어선으로 쓰고, 저장소 `save()`의 flush에서 `IntegrityError`(해당 제약) → `AlreadyParticipatingError`(400)로 변환 | 회원 행 잠금(기능 간 결합), advisory lock(얻는 것 적음) |
| AD-07 | DQ-05 DB 안전망 | `participations (room_id, join_order)` unique 추가(`uq_participations_room_join_order`). 위반은 **변환하지 않는다** — 잠금이 있으면 생길 수 없으므로, 생기면 버그로 드러나야 한다(500) | 안전망 없음(조용한 위반 재발 가능) |
| AD-08 | DQ-04 제어의 위치 | 도메인 계약 `RoomRepository`에 `find_by_id_for_update` 추가, 응용 서비스가 쓰기 동작에서 고른다. 도메인 객체(`Room`·`Participation`)는 바뀌지 않는다 | `find_by_id`가 항상 잠금(조회 경로까지 잠김), 도메인 버전 필드(불필요) |
| AD-09 | DQ-07 중복 요청 | 화면: 요청 하나가 처리되는 동안 화면의 참가·방 만들기 버튼 **모두** 비활성화. 서버: AD-01(잠금 뒤 읽기) + AD-06으로 결과 하나로 확정 | 누른 버튼만 비활성화(현재), Idempotency-Key(얻는 것 적음) |
| AD-10 | DQ-08 화면 피드백 | `apiRequest` 한 번 전체(토큰 재발급 포함)에 **5초** 시간 제한(`AbortController`). 클릭 **즉시** 로딩, **3초**에 지연 안내, 결론별 문구(아래 §3). 결과 모름 뒤 자동 재조회 없음 | 로딩만(상한 없음), 전체 오버레이(무거움) |

## 2. 지연 예산 (확정)

| 구간 | 상한 | 넘으면 | 응답 |
|---|---|---|---|
| 커넥션 풀 대기 | 1초 (AD-03) | 바빠서 거절 | 409 |
| 방 잠금 대기 | 2초 (AD-02) | 바빠서 거절 | 409 |
| 처리 여유 | 약 1초 | — | — |
| **서버 합계** | **4초** | | VC-06 |
| 클라이언트 시간 제한 | 5초 (AD-10) | 결과 모름 | 화면 문구 |
| 지연 안내 | 3초 | 표시 변경 | 화면 문구 |

## 3. 응답 → 화면 문구

| 서버 응답 | 참가 버튼 (목록·상세) | 그 밖의 쓰기 동작 (방 만들기·팀 변경·나가기·게임 시작·제목 변경) |
|---|---|---|
| 200 | 방 상세로 이동 | 기존 동작 |
| 400 (사유 있는 거절) | 서버가 준 사유 문구 | 서버가 준 사유 문구 |
| **409 (바빠서 거절)** | **"입장하지 못했습니다. 다시 시도해 주세요"** | "처리하지 못했습니다. 다시 시도해 주세요" |
| 시간 초과(5초)·통신 실패 | **"입장 결과를 확인하지 못했습니다."** | "처리 결과를 확인하지 못했습니다." |
| 처리 중 | 즉시 "입장 중…", 3초 뒤 "사람이 많아 처리가 늦어지고 있습니다" | 즉시 "처리 중…", 3초 뒤 같은 지연 안내 |

- 참가 버튼 문구는 고객 답변(CQ-11·12)이고, 그 밖의 동작 문구는 같은 구조로 맞춘 기본값이다. 지연 안내 문구는 기본값이며 고객 확인 전까지 바꿀 수 있다.

## 4. 요청 흐름 (참가)

```
[화면] 클릭 → 즉시 로딩 + 모든 참가·생성 버튼 비활성화 → 3초 타이머 → 5초 AbortController
  │
[서버] 인증 ─ (풀 대기 ≤ 1초, 넘으면 409)
  ├─ ① 빠른 거절: 잠금 없이 방 읽기 → 찼거나 삭제됐으면 400 (AD-05)
  ├─ ② SET LOCAL lock_timeout = '2s' → 방 행 FOR UPDATE (넘으면 409) (AD-01·02)
  ├─ ③ 잠금 뒤 현재 참가 읽기 (AD-01)
  ├─ ④ room.join() — 도메인 검사 그대로
  ├─ ⑤ save() — flush, user_id unique 위반 → 400 (AD-06)
  ├─ ⑥ 상세 조회 → commit (잠금 해제)
  │
[화면] 200 이동 / 400 사유 / 409 다시 시도 / 시간 초과 결과 모름 → 버튼 다시 활성화
```

다른 쓰기 동작은 ①(빠른 거절)이 없고 ②~⑥이 같다. 방 생성은 잠글 방이 없으므로 ⑤의 unique 변환만 적용된다.

## 5. 계층별 변경 범위 (구현 계획)

| 계층 | 위치 | 변경 |
|---|---|---|
| 도메인 | `rooms/domain/repository.py` | 계약 `find_by_id_for_update(room_id)` 추가. `Room`·`Participation`·도메인 예외는 **변경 없음** |
| 공통 | `src/exceptions.py` | "바빠서 거절" 공통 예외 추가 (`NotFoundError`·`GoneError`와 같은 방식) |
| 응용 | `rooms/application/service.py` | 쓰기 동작 다섯 개가 `_get_room_for_update` 사용. `join_room`은 빠른 거절 → 잠금 → 현재 참가 읽기 순서로 변경 |
| 인프라 | `rooms/infrastructure/repositories.py` | `find_by_id_for_update`(`SET LOCAL lock_timeout` + `with_for_update()`), `55P03` → 바빠서 거절, `save()`의 `IntegrityError`(user_id 제약) → `AlreadyParticipatingError` |
| 인프라 | `rooms/infrastructure/models.py` | `UniqueConstraint("room_id", "join_order", name="uq_participations_room_join_order")`, user_id unique에 이름 부여(변환 시 제약 이름으로 구분) |
| 설정 | `src/config.py`, `.env.example` | `db_pool_timeout` 기본값 30 → 1, `db_lock_timeout_ms = 2000` 추가 (ADR-003 방식) |
| 부트스트랩 | `src/bootstrap/error_handlers.py` | 바빠서 거절 예외 → 409, SQLAlchemy 풀 `TimeoutError` → 409 |
| 화면 | `static/js/api.js` | `apiRequest`에 5초 `AbortController`(재발급 포함 전체), 시간 초과를 결과 모름으로 구분 |
| 화면 | `static/js/rooms.js` (+ 템플릿 필요 시) | 즉시 로딩·3초 지연 안내, 처리 중 버튼 일괄 비활성화(목록), 409·결과 모름 문구 분기(목록·상세) |
| 테스트 | `tests/` | 단위: 서비스 호출 순서(잠금 뒤 읽기), 오류 변환. 통합: AC-18-1~5 동시 요청(실제 DB) |
| 측정 | `loadtest/bench_join.py` | 시간 제한 5초, s4(중복 요청)·s5(핫스팟 + 60 TPS)·s6(과부하) 추가, 409 집계 |
| 문서 | ADR, 컨벤션·게이트 | 새 ADR(6단계), ADR-009 Superseded, "쓰기 동작은 잠금 조회" 컨벤션과 검사 게이트 |

- 마이그레이션 도구가 없으므로(DRV-C-04) 새 unique 제약은 `create_all`로 새 DB에만 생긴다. 개발·측정 DB는 다시 만든다.

## 6. 감수하는 것 (trade-off)

| 얻는 것 | 치르는 것 |
|---|---|
| 정합성: 도메인 규칙이 그대로 유효하고, 다섯 가지 쓰기 동작이 같은 방식으로 보호된다 | 같은 방 요청은 차례로 처리된다. 핫스팟에서는 대기하는 동안 커넥션을 쥔다(VC-05로 측정) |
| 응답 시간 상한: 어떤 부하에서도 서버 4초 안에 결론 | 과부하 때는 빈자리가 있어도 2초 안에 차례가 오지 않은 요청이 409로 거절될 수 있다 |
| 화면이 멈춘 것처럼 보이지 않는다 | 풀 대기 1초는 앱 전체 설정이라, 과부하 때 목록 조회도 409가 날 수 있다 |
| 조용한 위반 대신 큰 소리 나는 실패(안전망) | `(room_id, join_order)` 위반이 생기면 500 — 의도한 동작(버그 신호) |
| 결과 모름이 드물어진다(서버가 먼저 끝남) | 네트워크 단절 때는 여전히 결과 모름. 자동 확인 없이 사용자가 [새로고침]으로 확인 |
| 새 쓰기 동작도 같은 패턴으로 보호 가능 | 새 쓰기 동작에서 잠금 조회를 잊으면 깨진다 → 컨벤션·게이트로 검사 |

## 7. 다시 검토할 조건

- 7단계에서 VC-05(핫스팟 중 다른 방 p95) 또는 VC-06(max 4초)을 넘으면: 지연 예산 값을 먼저 조정하고, 그래도 넘으면 후보 2(낙관적 잠금)를 다시 검토한다.
- 목표 규모(s5)에서 409가 1건이라도 나오면(VC-06b): `lock_timeout`·`pool_timeout` 값 또는 커넥션 풀 크기를 다시 본다.
- 서버를 여러 대로 늘려도 이 결정은 유지된다(잠금이 DB에 있으므로). DB를 바꾸거나 읽기 복제본으로 쓰기를 나누면 다시 검토한다.
