### 이해 가이드
- 데이터 흐름: 두 화면은 로그인 없이 연다(`require_login` false) → 회원가입은 `apiRequest("POST", "/api/auth/signup")`, 로그인은 `loginWithPassword()`(OAuth2 form) → 실패하면 `errorMessage()` 문구를 안내 영역에 쓰고 비밀번호만 지운다 → 가입 성공은 `/login`, 로그인 성공은 두 토큰 저장 후 `/`로 이동.
- 만료로 들어오면(`/login?expired=1`) 서버가 넘긴 `notice`가 처음부터 보인다(PAGE-02).
- 먼저 읽을 파일: `src/templates/auth/signup.html`, `src/templates/auth/login.html`, (공통) `src/static/js/api.js`

### 구현 중 자율 결정

#### 화면 스크립트 위치
- 결정: 제출 처리 코드를 각 템플릿의 `{% block scripts %}` 안 `<script>`에 둔다 — HANDOFF TKT-FE-M5-02 산출(템플릿 2개뿐, JS 파일 없음)
- 선택지: **A. 템플릿 안 스크립트 (권장·채택)** / B. `auth.js` 파일을 새로 만듦
- 권장 이유: 화면마다 10여 줄이고, 산출 목록 밖 파일을 만들지 않는다. 공통 동작은 이미 `api.js`에 있다.
- trade-off: A — 같은 패턴(버튼 잠금·문구 표시·비밀번호 지우기)이 두 템플릿에 비슷하게 있다. B — 중복은 줄지만 산출 밖 파일이 생긴다.

#### 입력 검증 위치
- 결정: 형식 규칙(길이·문자)은 화면에서 검사하지 않고 `required`만 둔다. 규칙 안내 문구만 보인다 — `04-interfaces-api.md` §5.1("형식 규칙은 도메인이 검사해 400"), 07-screens §4(규칙 안내)
- 선택지: **A. 서버 검사에 맡김 (권장·채택)** / B. HTML `pattern`·`minlength`로 화면에서도 검사
- 권장 이유: 규칙이 한 곳(도메인)에만 있어 문구·기준이 어긋나지 않고, 서버 문구가 그대로 보인다(AC-17-1).
- trade-off: A — 잘못된 입력도 한 번은 서버에 간다. B — 빨리 막지만 규칙이 두 곳에 생기고 브라우저 기본 문구가 섞인다.
