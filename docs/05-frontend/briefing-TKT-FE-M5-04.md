### 구현 중 자율 결정

#### 방장의 게임 시작 성공 후 이동 주소
- 결정: 방장은 안내 없이 `/`로 이동한다. 해산 안내(`/?notice=dissolved`)는 다른 참가자가 다음 조회에서 410을 받았을 때만 — `07-screens.md` SCR-04 상태별(방장 "SCR-03으로 이동" / 다른 참가자 "SCR-03으로 이동 + 해산 안내"), AC-16-3·4
- 선택지: **A. 방장은 `/` (권장·채택)** / B. 방장도 `/?notice=dissolved`
- 권장 이유: 화면 명세가 두 경우를 나눠 적었고, 방장은 직접 누른 결과라 안내가 없어도 알 수 있다.
- trade-off: A — 방장은 해산 문구를 보지 못한다. B — 명세에 없는 안내가 방장에게도 뜬다.

#### 404를 받으면 조회를 멈춤
- 결정: 404면 폴링을 멈추고 방 영역을 숨긴 뒤 "방을 찾을 수 없습니다"를 보인다 — AC-16-7, PAGE-04
- 선택지: **A. 멈춤 (권장·채택)** / B. 계속 조회
- 권장 이유: 없는 방은 다시 생기지 않으므로 계속 조회하면 요청만 늘어난다.
- trade-off: A — 일시적인 404도 새로고침해야 다시 본다. B — 1초마다 의미 없는 404 요청이 쌓인다.

#### 변경 요청 응답으로 바로 다시 그림
- 결정: 제목 변경·팀 이동·참가 성공 시 응답(`RoomDetailResponse`)으로 즉시 다시 그리고, 요청 중에는 `detailBusy`로 버튼을 막는다(폴링이 다시 그려도 막힘 유지) — API-ROOM-04·05·06 응답 형식
- 선택지: **A. 응답으로 즉시 반영 (권장·채택)** / B. 다음 폴링을 기다림
- 권장 이유: API가 바뀐 상세를 돌려주므로 추가 요청 없이 바로 보여 줄 수 있다.
- trade-off: A — 변경 직전에 출발한 조회 응답이 1초 이내 잠깐 옛 값을 보일 수 있다(다음 조회가 바로잡음). B — 누른 뒤 최대 1초 반응이 없다.

#### 상세에서 참가 성공 후 같은 화면 유지
- 결정: 비참가자가 상세에서 [참가]를 누르면 이동하지 않고 같은 화면을 참가자 보기로 바꾼다 — 사용자 확인 ①은 목록 화면의 참가에 대한 것이고, 상세 화면은 이미 그 방이다
- 선택지: **A. 그대로 유지 (권장·채택)** / B. 새로고침
- 권장 이유: 이미 목적지 화면이고 응답으로 바로 그릴 수 있다.
- trade-off: A — 없음에 가깝다. B — 불필요한 화면 다시 읽기.

#### 팀 정원 2를 JS 상수로 둠
- 결정: `TEAM_SIZE = 2`를 `rooms.js`에 두고 빈자리 수·게임 시작 활성에 쓴다 — API 응답에 팀별 정원 필드가 없음(`capacity`=4만 있음), 도메인 규칙 2vs2 고정
- 선택지: **A. 상수 2 (권장·채택)** / B. `capacity / 2`로 계산
- 권장 이유: 2vs2 고정이 도메인 규칙이고, 읽는 사람이 바로 이해한다.
- trade-off: A — 정원이 바뀌면 JS도 고쳐야 한다. B — 계산식이 규칙을 숨긴다.

#### hidden 속성을 바깥 div에 둠
- 결정: 방장·참가자·비참가자 버튼 묶음은 `.form-row`를 안쪽 div에 두고 `hidden`은 바깥 div에 건다 — 공통 `.form-row { display: flex }`가 `hidden` 속성을 덮어 버튼이 보이는 문제를 확인함
- 선택지: **A. 내 템플릿에서 감싸기 (권장·채택)** / B. 공통 CSS에 `[hidden] { display: none; }` 추가
- 권장 이유: 공통 파일(`app.css`)은 이 티켓 산출이 아니어서 스킬 규칙대로 내 영역에서 감싸는 배치로 해결했다.
- trade-off: A — div가 한 겹 늘어난다. B — 한 줄로 전체 화면이 안전해지지만 공통 파일 수정이다(아래 알려진 위험).
