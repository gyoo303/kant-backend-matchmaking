## 0. 사용 방법

**준비물**
- ERD 도구 하나
  - dbdiagram.io (글로 그림, 답안 붙여 넣기 쉬움)
  - ERDCloud (한국어, 여러 명 동시 편집)
  - draw.io (자유 그리기)
- 기획 문서 근거: `docs/01-pm/`

**진행 방식**
1. 단계 1~6을 순서대로 진행해요.
2. 각 단계의 **❓ 질문**을 팀이 토론해요.
3. 결정을 ERD 도구에 바로 그려요.
4. 막히면 **💡 힌트**를 열어요.
5. **✅ 단계 정리**는 그 단계를 끝낸 뒤 열어요.
6. 마지막에 §9 참고 답안과 비교해요.

**규칙**

## 1. 설계 재료 (기획 요약)

### 1.1 한 문장 정의

> 로그인한 회원이 2vs2(4명 고정) 공개 방을
> 만들거나 찾아 참가하고, 방 안에서 팀을
> 바꾼 뒤, 방장이 '게임 시작'을 누르면
> 결과 판정 없이 방이 해산되는 서비스.

### 1.2 기획이 정한 "저장 정보"

요구사항 원문에 저장할 정보가 직접 적혀 있어요.
ERD의 가장 중요한 근거예요.

| REQ | 저장 정보 (원문) |
|---|---|
| 021 | 로그인 식별 정보, 닉네임, 비밀번호 해시 |
| 032 | 제목, 고정 정원, 현재 방장, 생성 시각, 삭제 시각, 삭제 사유 |
| 040 | 방, 회원, 입장 순서, 현재 팀, 입장 시각, 퇴장 시각 |
| 053 | 방 제목·정원·생성/삭제 시각, 회원별 입장·퇴장 시각 보존 |
| 059 | 로그아웃한 토큰은 블랙리스트에 등록 |

### 1.3 용어집 (`03-domain.md` §3)

| 용어 | 뜻 |
|---|---|
| 회원 | 아이디·닉네임·비밀번호 해시를 가진 사용자 |
| 방 | 정원 4명 고정 2vs2 공개 방 |
| 방장 | 방의 현재 참가자 중 한 명 |
| 팀 | A·B 두 팀, 팀당 2명 |
| 참가 (이용 기록) | 한 회원이 한 방에 한 번 입장한 기록 |
| 입장 순서 | 그 방에 들어온 순서 (화면 비공개) |
| 소프트 삭제 | 행을 남기고 삭제 시각·사유만 기록 |
| 삭제 사유 | 게임 시작 / 참가자 없음 |
| 보관 정보 | 삭제된 방 정보 + 본인 이용 기록 |

### 1.4 기억할 규칙 (불변 규칙 일부)

- INV-01 정원 4명, 팀당 2명 고정
- INV-04 한 회원은 동시에 한 방에만
- INV-05 방장은 그 방의 현재 참가자
- INV-07 삭제된 방만 삭제 시각·사유를 가짐
- INV-09 게임 결과(승패)는 저장하지 않음
- INV-10 이용 기록은 지우지 않음
- INV-11 재입장하면 새 입장 순서

## 2. 단계 1 — 엔티티 찾기 (15분)

**방법**: §1의 문장에서 **명사**에 밑줄을 긋고,
"따로 저장하고 여러 개 생기는가?"를 물어요.

**❓ 질문 1-1**
아래 명사 중 **테이블**이 될 것은?

- [ ] 회원
- [ ] 방
- [ ] 방장
- [ ] 팀
- [ ] 참가(이용 기록)
- [ ] 입장 순서
- [ ] 게임
- [ ] 게임 결과
- [ ] 토큰 블랙리스트
- [ ] 삭제 사유

<details>
<summary>💡 힌트</summary>

- "방장"은 사람 종류일까, 방 안의 **역할**일까?
- "팀"은 A·B 두 값뿐이에요. 따로 행을 만들 만큼 정보가 있나요?
- "게임"·"게임 결과"는 REQ-001·051을 확인해요.

</details>

**❓ 질문 1-2**
회원과 방은 **여러 명 ↔ 여러 방**이에요.
(한 회원이 시간이 지나며 여러 방에 들어가고,
한 방에 여러 회원이 들어와요.)
이 관계를 표현할 테이블은?

<details>
<summary>✅ 단계 1 정리</summary>

- 테이블: **회원, 방, 참가, 토큰 블랙리스트**
- 방장 → 방의 **속성**(누가 방장인지)
- 팀 → 참가의 **속성**(A 또는 B) — 처음 설계 기준. 이 저장소는 튜터 피드백 뒤 팀을 별도 테이블로 바꿨어요(§9, D-023·ADR-010). 둘 다 가능한 답이에요
- 입장 순서 → 참가의 **속성**
- 삭제 사유 → 방의 **속성**
- 게임·게임 결과 → **없음** (REQ-001, INV-09)
- 회원 ↔ 방 N:M → **참가**가 연결 테이블

</details>

| 기호 | 뜻 |
|---|---|

| `o\|` | 없거나 하나 |
| `\|<` | 하나 이상 |
| `o<` | 없거나 여러 개 |

**❓ 질문 3-3**
방장 회원이 탈퇴하면? (탈퇴 기능은 없어요 — D-008)

## 5. 단계 4 — 상태를 어떻게 표현할까 (20분)

방과 참가는 시간이 지나며 상태가 바뀌어요.

**방의 상태** (`03-domain.md` §5.1)

| 상태 | 언제 |
|---|---|
| 활성 | 만든 뒤 |
| 삭제됨(참가자 없음) | 마지막 사람이 나감 |
| 삭제됨(게임 시작) | 방장이 게임 시작 |

**참가의 상태** (§5.2)

| 상태 | 언제 |
|---|---|
| 참가 중 | 입장 |
| 종료 | 나가기 또는 게임 시작 |

**❓ 질문 4-1**
"삭제됨"을 어떻게 저장할까?

- A: 행을 진짜로 지움 (`DELETE`)
- B: `is_deleted` 참/거짓 컬럼
- C: `deleted_at`(시각) + `delete_reason`(사유)

<details>
<summary>💡 힌트</summary>

- REQ-044: "이용 이력은 보존한다"
- REQ-053: "삭제 시각을 보존한다"
- REQ-066: 소프트 삭제 = 행을 남기고 시각·사유 기록
- B만 쓰면 "언제, 왜"를 어디에 적을까요?

</details>

**❓ 질문 4-2**
"지금 참가 중"과 "지난 이용 기록"을
**테이블 하나**로 할까, **두 개**로 나눌까?

- A: 참가 테이블 하나 (퇴장 시각이 비면 참가 중)
- B: 현재 참가 테이블 + 이용 이력 테이블

<details>
<summary>💡 힌트</summary>

- B라면 나가기 때 행을 옮겨야 해요(지우고 넣기).
- REQ-071: 업무 하나는 모두 저장되거나 모두 취소.
  옮기는 작업이 많을수록 실수할 곳이 늘어요.
- 내 기록 화면(SCR-05)은 "참가 중"과 "지난 기록"을
  한 목록에 보여 줘요(REQ-054).

</details>

**❓ 질문 4-3**
게임 시작 결과(승패)를 저장할 컬럼이 필요할까?

<details>
<summary>✅ 단계 4 정리</summary>

- 방 삭제: **C** — `deleted_at` + `delete_reason`
  - 활성 = `deleted_at`이 비어 있음
  - 둘 다 비거나 둘 다 차 있어야 함(INV-07)
- 참가: **A** — 테이블 하나, `left_at`이 비면 참가 중
- 승패 컬럼: **없음** (INV-09)

</details>

## 6. 단계 5 — 규칙은 어디서 지킬까 (15분)

규칙을 지키는 곳은 두 군데예요.

| 어디 | 예 |
|---|---|
| DB 제약 | NOT NULL, FK, UNIQUE |
| 코드(도메인 클래스) | `Room.join()`이 정원 검사 |

**❓ 질문 5-1**
아래 규칙을 DB와 코드 중 어디서 지킬까?
(둘 다도 가능)

| 규칙 | DB / 코드 |
|---|---|
| 아이디 중복 금지 | |
| 방 제목 1~20자 | |
| 정원 4명 | |
| 팀당 2명 | |
| 한 회원 한 방 | |
| 방장은 현재 참가자 | |
| 퇴장 시각 ≥ 입장 시각 | |

<details>
<summary>💡 힌트</summary>

- "다른 행을 세어야 아는 규칙"은 DB 제약 하나로
  표현하기 어려워요. (팀당 2명 = 참가 행 세기)
- 이 프로젝트 규칙(D-020): 도메인이 이미 검사하는
  규칙을 DB에 **또** 넣지 않는다. DB에는
  NOT NULL·FK·UNIQUE(아이디·닉네임)만 둔다.

</details>

<details>
<summary>✅ 단계 5 정리</summary>

| 규칙 | 지키는 곳 |
|---|---|
| 아이디 중복 금지 | DB `unique` + 코드에서 먼저 확인 |
| 방 제목 1~20자 | 코드(`RoomTitle`), DB는 길이 20 |
| 정원 4명 | 코드(`Room.CAPACITY`) |
| 팀당 2명 | 코드(`Room.change_team`) |
| 한 회원 한 방 | 코드 (동시 요청 방어는 도전 A) |
| 방장은 현재 참가자 | 코드(`Room.leave` 위임) |
| 퇴장 ≥ 입장 | 코드(`Participation.end`) |

</details>

## 7. 단계 6 — 화면·시나리오로 검증 (20분)

그린 ERD로 **화면에 필요한 데이터**를
얻을 수 있는지 하나씩 확인해요.
"어느 테이블에서, 어떤 조건으로?"를 말로 설명해 봐요.

### 7.1 화면 체크

**SCR-03 공개 방 목록**
- [ ] 삭제되지 않은 방만 (REQ-079)
- [ ] 방마다 현재 인원 / 정원 (REQ-087)
- [ ] 제목 부분 검색 (REQ-080)
- [ ] 빈자리 있는 방만 보기 (REQ-081)
- [ ] 생성 시각 최신순·오래된순 (REQ-082)
- [ ] 목록 위 "내가 참가 중인 방" 링크 (REQ-076)

**SCR-04 방 상세**
- [ ] 제목, 현재 인원, 정원 (REQ-075)
- [ ] 방장 표시
- [ ] 참가자 **닉네임**과 팀 (닉네임은 어디에?)
- [ ] 입장 순서는 화면에 **안** 나감 (REQ-045)

**SCR-05 내 기록**
- [ ] 내 기록만, 입장 시각 최신순 (REQ-055)
- [ ] 기록마다 방 제목
- [ ] 참가 중 / 종료 구분 (REQ-054)
- [ ] 방이 삭제됐는지 표시

**SCR-06 보관 정보**
- [ ] 삭제된 방의 제목·정원·생성/삭제 시각
- [ ] **내** 입장·퇴장 기록만 (REQ-056·057)
- [ ] 참가한 적 없으면 볼 수 없음

### 7.2 시나리오 따라가기

ERD 위에서 행이 어떻게 바뀌는지 손으로 따라가요.

**시나리오 1 — 방장이 나감**
1. 회원1이 방 생성 → 어떤 행이 생기나?
2. 회원2·3 참가 → 입장 순서는?
3. 회원1(방장) 나가기 → 바뀌는 컬럼은?
4. 새 방장은 누구? 근거 컬럼은?

**시나리오 2 — 재입장**
1. 회원2가 나감 → 참가 행은 지워지나?
2. 회원2가 같은 방에 다시 참가
3. 행은 몇 개? 입장 순서는 몇 번?

**시나리오 3 — 게임 시작**
1. A팀 2명·B팀 2명, 방장이 시작
2. 방 행에서 바뀌는 컬럼 2개는?
3. 참가 행 4개에서 바뀌는 컬럼은?
4. 새로 생기는 행이 있나? (INV-09)

**시나리오 4 — 로그아웃**
1. 회원1 로그아웃 → 어느 테이블에 행이 생기나?
2. 회원1의 참가 상태는 바뀌나? (REQ-038)

<details>
<summary>✅ 단계 6 정리</summary>

- 현재 인원: 참가 중(`left_at` 빈) 행을 방별로 셈
- 닉네임: 참가.회원 id → 회원 테이블에서 읽음
- 방장 위임: 남은 참가 중 행에서 입장 순서가
  가장 작은 사람 → 방.방장 회원 id 변경
- 재입장: 행 2개(옛 기록 + 새 기록),
  새 입장 순서 = 방.마지막 입장 순서 + 1
- 게임 시작: 방 `deleted_at`·`delete_reason`,
  참가 4행 `left_at` 채움, 새 행 없음
- 로그아웃: 블랙리스트에만 행 추가, 참가는 그대로

</details>

## 8. 자주 하는 실수 체크

- [ ] 방장을 별도 테이블로 만들었다 (팀은 테이블로 뺄 수도 있어요 — §9, ADR-010)
- [ ] 게임·결과 테이블을 만들었다 (INV-09)
- [ ] 현재 인원 컬럼을 저장해서 숫자가 어긋날 위험
- [ ] 나가기 때 참가 행을 **지움** (INV-10 위반)
- [ ] `is_deleted`만 두고 삭제 시각·사유가 없음
- [ ] 참가 테이블에 닉네임을 복사해 둠
  (닉네임은 회원 테이블 한 곳에만)
- [ ] 비밀번호 원문 컬럼
- [ ] 입장 순서를 회원 가입 순서로 착각 (REQ-045)
- [ ] FK를 1쪽 테이블에 둠

## 9. 참고 답안 (실제 프로젝트 설계)

> 팀이 먼저 끝까지 설계한 뒤에 열어요.
> 이 프로젝트 ARCH 단계가 확정한 설계예요
> (`docs/02-arch/03-db-schema.md`).
> 팀 결론과 달라도 괜찮아요. 다른 점을 토론해요.

<details>
<summary>📋 DBML (dbdiagram.io에 붙여 넣기)</summary>

```dbml
Table users {
  id integer [pk, increment]
  login_id varchar(20) [unique, not null, note: '4~20자 영문 소문자·숫자']
  nickname varchar(12) [unique, not null]
  hashed_password varchar(255) [not null, note: 'bcrypt 해시만']
  created_at timestamptz [not null, default: `now()`]
}

Table rooms {
  id integer [pk, increment]
  title varchar(20) [not null]
  capacity integer [not null, default: 4]
  host_user_id integer [not null, ref: > users.id]
  last_join_order integer [not null, default: 0, note: '재입장 번호용']
  created_at timestamptz [not null]
  deleted_at timestamptz [null, note: '비면 활성 방']
  delete_reason varchar(20) [null, note: 'GAME_STARTED / EMPTY']
}

Table teams {
  id integer [pk, increment]
  room_id integer [not null, ref: > rooms.id]
  side varchar(1) [not null, note: 'A / B, 방마다 두 행']
}

Table participations {
  id integer [pk, increment]
  room_id integer [not null, ref: > rooms.id]
  user_id integer [not null, ref: > users.id]
  join_order integer [not null, note: '방 안 입장 순서']
  team_id integer [not null, ref: > teams.id, note: '같은 방의 팀']
  joined_at timestamptz [not null]
  left_at timestamptz [null, note: '비면 참가 중']
}

Table token_blacklist {
  id integer [pk, increment]
  token varchar(500) [not null, note: '로그아웃한 토큰 원문']
  created_at timestamptz [not null, default: `now()`]

  indexes {
    token
  }
}
```

</details>

<details>
<summary>🗣️ 실제 설계에서 고른 이유</summary>

- **참가 테이블 하나** — 현재 참가와 이력을
  같은 행으로 관리(ARCH-Q-03). 나가기는 `left_at`만 채움.
- **`last_join_order`를 방에 둠** — 재입장 번호를
  `MAX` 계산 대신 방의 숫자 +1로 정함.
  방을 저장할 때 함께 바뀌어 단순해요.
- **`capacity` 컬럼** — 정원은 늘 4지만
  REQ-032·053이 "고정 정원 저장"을 요구해서 둠.
- **현재 인원은 컬럼 없음** — 참가 중 행을 셈.
- **팀 테이블(튜터 피드백, D-023·ADR-010)** — 처음에는
  참가의 `team` 값(A/B)이었지만, 팀을 엔티티로 보고
  `teams`로 뺐어요. 팀 정원 2명은 컬럼이 아니라
  도메인 `Team.CAPACITY`. 참가는 `room_id`도 유지해요
  (이력·현재 방 조회가 단순).
- **블랙리스트는 회원과 FK 없음** — 토큰 문자열로만 확인.
- **CHECK 제약은 두지 않음** — 제목 길이·팀 편 값·
  삭제 상태는 도메인 클래스가 검사(D-020).
- **한 회원 한 방 DB 보장** — 부분 유니크 인덱스는
  도전 A에서 추가(D-018).

</details>
