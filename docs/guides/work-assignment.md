## 1. 작업량을 매긴 기준

티켓마다 **작업량 점수**를 매겼어요. 1점은 1년차 수강생이 교안을 보며 **약 2시간** 걸리는 양이에요(코드 작성 + 스스로 확인 + 브리핑 작성 포함).

| 점수 | 난이도 | 예시 |
|---|---|---|
| 1 | 하 | 설정 파일 하나, 임시 코드 삭제 |
| 2 | 하~중 | 모델 2개와 간단한 레포지토리, 화면 1~2개 |
| 3 | 중 | 서비스 클래스 하나, 테스트 묶음 하나 |
| 4 | 중~상 | API 11개 라우터, 동작이 많은 화면, 순수 도메인 클래스 묶음 |
| 5 | 상 | 집계·조회가 많은 레포지토리 |

- 큰 티켓 두 개는 둘로 나눴어요(`a`·`b`). 선행 관계가 한 줄로 이어지는 M3에서 한 사람만 바쁘고 나머지가 기다리는 일을 줄이기 위해서예요.
  - `TKT-BE-M3-01a` auth 도메인(`User`, `TokenBlacklist`, auth 예외, `PasswordHasher`) / `TKT-BE-M3-01b` rooms 도메인(`Room`, `Participation`, 값 객체, rooms 예외, 읽기 모델)
  - `TKT-QA-M3-01a` 도메인 단위 테스트 / `TKT-QA-M3-01b` rooms API 통합 테스트·`conftest.py`
- 필수 합계 **70점**(1인 평균 14점 ≈ 28시간), 도전 합계 **14점**이에요.
- 도전(M6) 티켓은 필수가 모두 끝난 뒤 **팀이 하기로 정했을 때만** 진행해요(D-018).

## 4. 일차별 진행표

`→`는 같은 날 앞 작업이 끝나야 시작하는 작업이에요. **(미리)** 는 선행 티켓이 끝나기 전에 명세(`docs/02-arch/04-interfaces-api.md`)만 보고 먼저 시작해도 되는 작업이에요.

| 일차 | A 인증 | B 방 도메인 | C DB·조회 | D API·웹 공통 | E 품질·목록 화면 |
|---|---|---|---|---|---|
| 3 | 개발 환경(uv, PostgreSQL) | **BE-M2-01** 골격 | → **DB-M2-01** | 개발 환경, 교안 2·3장 복습 | 개발 환경, 테스트 DB 준비 |
| 4 | **BE-M3-01a** auth 도메인 | **BE-M3-01b** rooms 도메인 | 교안 5장 복습, ERD 확인 | 스키마 초안(미리) | 단위 테스트 틀(미리) |
| 5 | **DB-M3-01** | BE-M3-01b 마무리 | → **DB-M3-02** 시작 | 스키마 초안(미리) | **QA-M3-01a** 단위 테스트 |
| 6 | **BE-M4-01** 시작(미리) | **BE-M3-02** | DB-M3-02 → **DB-M3-03** | **BE-M3-04** 시작 | QA-M3-01a 마무리 |
| 7 | BE-M4-01 계속 | **BE-M3-05** | **BE-M3-03** | BE-M3-04 마무리 | → **QA-M3-01b** |
| 8 | BE-M4-01 → **BE-M4-02** → **BE-M4-03** | 코드 리뷰(A), 버그 수정 | 코드 리뷰(B), 버그 수정 | → **QA-M4-01**, 미들웨어(미리) | QA-M3-01b 마무리 |
| 9 | 교안 3장 2강 복습, 화면 준비 | 화면 준비 | 화면 준비 | **BE-M5-01** → **FE-M5-01** | 화면 준비 |
| 10 | **FE-M5-02** | → **FE-M5-04** (FE-M5-03 다음) | **FE-M5-05** | 화면 지원, 버그 수정 | **FE-M5-03** → **QA-M5-01** |
| 11 | (도전) **BE-M6-02** | (도전) **BE-M6-00** | (도전) **DB-M6-01** | (도전) **BE-M6-01** | QA-M5-01 마무리, (도전) **QA-M6-01·02** |
| 12 | **FE-M7-01** README | PPT | **QA-M7-01** | PPT | 버그 확인 |
| 13 | 리허설·발표 | 리허설·발표 | 시드 재기동 확인 | 리허설·발표 | 리허설·발표 |

**일정이 몰리는 곳과 대처**

- **8일차 A**: 인증 티켓 3개가 이어져 있어요. A는 5일차에 `DB-M3-01`을 끝내면 6일차부터 `BE-M4-01`을 미리 시작해요(선행 중 `BE-M3-05`는 `main.py` 등록에만 필요해요).
- **9일차 D**: `BE-M5-01`과 `FE-M5-01`이 이어져 있어요. D는 8일차에 로깅 미들웨어·CORS(인증과 무관한 부분)를 미리 만들어 둬요.
- **10일차**: `FE-M5-01`(공통 `api.js`)이 끝나야 화면 4개가 시작돼요. D가 9일차 안에 끝내는 것이 팀 전체 일정의 핵심이에요. `QA-M5-01`은 11일차로 넘어가도 돼요(도전은 선택이므로).
- **도전(11일차)**: HANDOFF는 A → B → C 순서로 적혀 있지만, 도전 A(B·C·E)와 도전 B·C(D·A)는 서로 다른 파일이라 사람이 하면 **동시에** 진행할 수 있어요.

## 5. 코드 리뷰 짝

자기 코드를 자기가 테스트하면 놓치는 게 많아요. 다른 사람이 쓴 계층을 리뷰하고 테스트하도록 짝을 정했어요.

| 작성자 | 리뷰·테스트 담당 | 이유 |
|---|---|---|
| A (인증) | D | D가 인증 통합 테스트(QA-M4-01)를 쓴다 |
| B (방 도메인·서비스) | E | E가 도메인 단위 테스트와 rooms API 테스트를 쓴다 |
| C (DB·조회) | B | B의 서비스가 C의 레포지토리를 호출한다 |
| D (라우터·화면 공통) | A | A의 로그인 화면이 D의 `api.js`를 쓴다 |
| E (테스트·목록 화면) | C | C가 최종 통합 점검(QA-M7-01)을 한다 |

## 6. 진행 규칙

1. **티켓 하나 = 브랜치 하나 = PR 하나.** 브랜치 이름 예: `feat/TKT-BE-M3-02`. 커밋 메시지 예: `feat(be): RoomApplicationService 방 변경 흐름 (TKT-BE-M3-02)` (CONV-13)
2. **시작 전 확인**: `node scripts/check-handoff.mjs <단계> --ticket <티켓>`이 `READY`인지 봐요. 나눈 티켓(`a`·`b`)은 원래 티켓 ID로 확인해요.
3. **교안 수준으로**: 교안 1~6장에 나온 방법으로 써요. 기준은 `docs/02-arch/05-structure-conventions.md` §8이에요(D-020).
4. **막히면 30분 규칙**: 30분 넘게 막히면 리뷰 짝에게 먼저 물어보고, 그래도 안 되면 팀 채널에 올려요.
5. **끝나면 브리핑**: 내가 만든 것, 확인한 방법, 바꾼 것을 브리핑(`docs/03-db/`, `docs/04-backend/` 등)에 적어요. 다음 담당자는 코드보다 브리핑을 먼저 봐요.
6. **매일 마지막 15분**: 오늘 끝낸 티켓, 내일 할 티켓, 막힌 점을 공유해요. 이 표의 일차와 다르면 표를 고쳐요.
