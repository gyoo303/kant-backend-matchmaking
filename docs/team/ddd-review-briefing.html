오늘은 멀티미디어 아카이브 예제 코드를 DDD 관점에서 본 결과를 공유합니다. 출발점은 "main.py에 핵심 규칙 판단이 너무 많이 들어가 있는 것 같다"는 의문이었고, 결론부터 말하면 그 의문이 맞습니다.

한 줄 결론

지금은 DDD라기보다
“똑똑한 DTO + 두꺼운 컨트롤러”

엔티티에 상태 전이를 넣은 출발점은 좋지만, 규칙은 main.py에 흩어져 있고 불변식은 우회할 수 있습니다.

엔티티가 상태 전이 메서드를 가진 건 좋은 출발입니다. 하지만 세 가지 문제가 있습니다. 첫째, 파일명·MIME·ID·저장 경로 규칙이 main.py에 흩어져 있습니다. 둘째, 변환 파이프라인 같은 유스케이스 흐름을 라우터 파일이 쥐고 있습니다. 셋째, 엔티티 불변식을 생성자와 public 속성으로 우회할 수 있습니다.

MAIN.PY 들여다보기

main.py의 코드가 전부 문제는 아닙니다

여기 있어도 되는 것

표현 계층의 관심사

  • HTTP 상태 코드 매핑
  • Content-Disposition 등 응답 헤더
  • StreamingResponse 스트리밍
  • 요청 파싱(UploadFile)

옮겨야 하는 것

도메인 규칙과 유스케이스 흐름

  • 파일명 정제, MIME 기본값
  • ID 발급과 저장 경로 규칙
  • 변환 파이프라인 상태 조율
  • 실패 처리(로그 한 줄로 덮음)
main.py가 두꺼운 것 자체가 문제는 아닙니다. HTTP 상태 코드, 헤더, 스트리밍은 원래 API 계층에 있어야 합니다. 문제는 그 사이에 도메인 규칙과 애플리케이션 흐름이 섞여 있다는 점입니다.

빠진 상태 전이

변환이 실패하면 자산은 영원히 PROCESSING에 멈춥니다

PENDING

PROCESSING

COMPLETED

지금: FAILED 상태가 없음

except ValueError가 로그만 남기고 끝나서, 클라이언트는 PROCESSING만 계속 보게 됩니다.

바꿀 방향: mark_as_failed()

“변환은 끝나거나 실패한다”는 규칙을 엔티티가 직접 표현하게 합니다.

실패한 자산의 상태가 갱신되지 않는 건 단순한 누락이 아니라 도메인 규칙이 모델에 없다는 신호입니다. "변환은 언젠가 끝나거나 실패한다"는 규칙을 엔티티가 FAILED 상태와 mark_as_failed 메서드로 표현해야 합니다. 그래야 클라이언트도 실패를 알 수 있습니다.

엔티티의 불변식을 우회하는 길이 열려 있습니다

생성자로 status를 받음

status="COMPLETED"로 만들면 전이 규칙을 건너뜁니다. 새 자산은 항상 PENDING이어야 합니다.

속성이 전부 public

asset.status = "아무거나"가 막히지 않습니다. 상태가 문자열이라 오타도 못 잡습니다.

to_dict()가 도메인에

직렬화는 표현 계층의 일입니다. 스키마의 from_attributes로 변환하면 됩니다.

datetime.now() 직접 호출

타임존이 없고 테스트하기 어렵습니다. UTC를 쓰거나 시각을 주입받습니다.

예외가 전부 ValueError

API가 “잘못된 입력”과 “서버 오류”를 구분하지 못합니다.

해결 방향

AssetStatus Enum, 읽기 전용 프로퍼티, 복원용 팩토리, 도메인 전용 예외

엔티티가 상태 전이 메서드를 갖고 있어도, 생성자에서 status를 받거나 속성이 public이면 그 규칙은 강제되지 않습니다. 저장소에서 복원할 때는 reconstitute 같은 별도 팩토리를 쓰고, 상태는 Enum과 읽기 전용 프로퍼티로 바꿉니다. 예외도 InvalidAssetError, InvalidStateTransitionError처럼 도메인 전용으로 나눠야 API 계층이 400과 500을 구분할 수 있습니다.

권장 구조

의존성은 모두 도메인을 향합니다

api/

요청 파싱, 스키마 변환, 예외 → HTTP 상태 매핑

application/

유스케이스: 업로드 등록, 변환 실행, 조회, 다운로드

domain/

엔티티, 값 객체, 상태 Enum, 도메인 예외, 저장소 포트

infrastructure/

메모리 저장소(락 + next_id), 로컬 파일 저장소

저장 경로 규칙 seq_{id}_{name}은 infrastructure 한 곳에만 둡니다. 업로드 핸들러는 다섯 줄 남짓으로 줄어듭니다.

api는 application을 부르고, application은 domain을 씁니다. infrastructure는 domain이 정의한 포트(AssetRepository, FileStorage)를 구현합니다. 그래서 화살표가 전부 domain을 향합니다. 이렇게 나누면 도메인 규칙을 FastAPI 없이 단위 테스트할 수 있고, 메모리 저장소를 DB로 바꿀 때도 도메인 코드는 그대로입니다.

엔티티 스케치

상태는 엔티티만 바꿀 수 있게

  • 새 자산은 항상 PENDING
  • status는 읽기 전용
  • 전이는 _transition 한 곳에서 검증
  • FAILED로 실패를 표현

class AssetStatus(str, Enum):
    PENDING / PROCESSING / COMPLETED / FAILED

class MultimediaAsset:
    def __init__(self, asset_id, filename: FileName, ...):
        self._status = AssetStatus.PENDING
    @property
    def status(self): return self._status
    def mark_as_failed(self, reason):
        if self._status is AssetStatus.COMPLETED:
            raise InvalidStateTransitionError(...)
        self._status = AssetStatus.FAILED
    def _transition(self, expected, to):
        if self._status is not expected:
            raise InvalidStateTransitionError(...)
        self._status = to

핵심은 상태를 바꾸는 길을 엔티티 메서드 하나로 좁히는 것입니다. 생성자는 status를 받지 않고 항상 PENDING으로 시작합니다. 외부에서는 status를 읽기만 할 수 있고, 모든 전이는 _transition에서 검증합니다. mark_as_processing과 mark_as_completed는 _transition을 한 줄로 부르면 됩니다.

우선순위

먼저 손볼 세 가지: 모두 실제 버그와 이어집니다

1

FAILED 상태 추가

변환 실패 시 PROCESSING에 멈추는 문제를 막습니다.

2

저장 경로 규칙 한 곳으로

업로드와 다운로드에 중복된 규칙을 FileStorage로 모읍니다.

3

ID 경쟁 상태 해결

저장소가 ID를 처음에 발급해 동시 업로드 덮어쓰기를 막습니다.

전체 구조 개편은 시간이 걸리니, 실제 버그와 바로 이어지는 세 가지부터 시작하길 제안합니다. 이 세 가지를 하다 보면 자연스럽게 엔티티, 저장소 포트, 파일 저장소가 분리되기 시작합니다. 다운로드 가능 상태 정책은 팀에서 따로 정해야 할 질문으로 남겨 둡니다.
