## 4. 보조 측정 — `echo=True`를 끄면 (같은 날, 판정에 쓰지 않음)

`database.py`의 `echo`를 잠시 `False`로 바꿔 쟀다(측정 뒤 되돌림). 본 측정 중 앱 로그는 약 650만 줄이었다.

| 항목 | echo 켬 | echo 끔 |
|---|---|---|
| s1 c=1 p50 (순차 1건) | 22.1ms | 18.9ms |
| s1 최대 TPS (처리량 한계) | 90.3 | **120.2** |
| s2 핫스팟 max | 618ms | 477ms |
| s5 핫스팟 중 배경 p95 | 823.8ms ❌ | **435.3ms ✅** |
| s5 409 / >4s / 위반 | 0 / 0 / 0 | 0 / 0 / 0 |
| s6 배경 5초 초과 | 3,278 | 1,901 |

echo를 끄면 VC-05가 통과하고 처리 한계가 약 30% 오른다. 다만 기준선도 echo를 켠 채 쟀으므로, echo를 끈 조건을 채택하려면 기준선을 같은 조건으로 다시 재야 한다. 또 처리 한계가 120이 되면 s6(120 TPS)은 과부하가 아니므로 s6 속도를 약 160 TPS로 올려야 한다.

## 5. 보조 실험 — 5초 시간 초과는 서버에 반영됐나

**실험** (`loadtest/probe_disconnect.py`): 방 행을 1.5초 잠가 두고 참가 요청을 보낸 뒤, 클라이언트가 0.5초에 끊었다. 결과는 `saved_in_db=1`이었다. 클라이언트가 끊어도 서버는 잠금을 기다려 끝까지 처리하고 저장한다. ADR-014가 적은 대로 화면의 AbortController는 서버 처리를 취소하지 못한다.

**s6 끝난 뒤 DB 비교** (참가 수 − 받은 200 수):

| | echo 켬 s6 | echo 끔 s6 |
|---|---|---|
| 배경 5초 초과 | 3,278 | 1,901 |
| ① 늦게 처리돼 실제로 참가됨 | **234 (7%)** | **97 (5%)** |
| ② 끊긴 뒤 409로 거절됨 (서버 풀 대기 초과 로그 266 − 받은 409 254) | 약 12 | 0 |
| ③ 서버에 흔적 없음 | **약 3,030 (93%)** | **약 1,800 (95%)** |

- ③은 서버의 처리 코드에 닿기 전에 끊긴 요청으로 본다. 처리 코드에 닿은 요청은 커밋(①)되거나 409(②, 로그에 남음)가 된다. 이 결론은 소거법으로 얻은 것이다. 한계는 두 가지다.
  - echo를 켠 측정의 앱 로그는 덮어써져서, 서버가 받은 요청 수를 직접 세지 못했다.
  - 발생기 CPU가 약 90%라 일부는 발생기 안에서 늦게 출발했을 수 있다.
- 화면에서 ①은 "입장 결과를 확인하지 못했습니다"가 뜨지만 실제로는 참가된 상태다. [새로고침]하면 "현재 참가 방"에 보이고, 같은 방을 다시 누르면 200(변화 없음)이다. ③은 아무것도 바뀌지 않아 다시 시도해도 안전하다. "실패" 대신 "확인하지 못했습니다" 문구를 쓴 결정(D-033)이 이 경우와 맞다.

## 6. 해석

1. **정합성 문제는 해결됐다.** 기준선에서 4인 방에 7~10명이 들어가던 핫스팟이, 목표 규모·과부하 모두에서 4명으로 끝난다. 같은 회원의 동시 중복 요청도 500 없이 400·200으로 정리된다. 15개 회차 모두 위반 0, 5xx 0이다.
2. **목표 규모의 잠금 비용은 작다.** 60 TPS p95는 21.8ms에서 28.1ms로 6ms 늘었다. 순차 처리 시간은 18.6ms에서 22.1ms로 늘었다. 빠른 거절용 잠금 없는 조회와 `SET LOCAL lock_timeout`이 요청마다 쿼리를 더하기 때문이다. 그 결과 처리 한계가 108에서 90 TPS로 17% 줄었다(VC-04 여유 4 TPS).
3. **VC-05 불합격의 원인은 잠금이 아니라 CPU다.** 핫스팟 100건이 워커 1개의 CPU를 약 1초 동안 차지해, 잠금이 겹치지 않는 다른 방 요청도 기다린다. 409가 0이라 풀이 바닥난 것도 아니다. 표본 70건이라 p95가 상위 4건으로 정해지는 점도 고려해야 한다. echo를 끄면 통과한다(§4).
4. **VC-06(과부하 4초 상한)은 지금 구조로 보장할 수 없다.** 풀 1초 + 잠금 2초 상한은 커넥션을 기다리기 시작한 뒤에만 적용된다. 처리 한계를 넘으면 요청이 그보다 앞 단계(이벤트 루프·uvicorn 수신·OS 접속 대기열)에서 쌓이고, 이 대기에는 상한이 없다. 그래서 409로 빨리 거절되는 요청(254)보다 5초 시간 초과(3,278)가 훨씬 많다.
