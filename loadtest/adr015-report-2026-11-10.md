  - `echo`를 설정 값으로 빼고 기본값을 껐다(D-036).
  - VC-05를 핫스팟 구간 p95 1초로 완화했다(D-035).
  - 진입 단계 동시 처리 상한 150을 넣었다(ADR-015, D-037).

## 4. VC-08 화면 체크리스트 (앱 내 브라우저, 2026-11-10)

준비: 측정 DB에 화면 확인용 회원 1명(회원가입 API)과 방 3개를 만들었다. 서버 지연은 운영 코드를 바꾸지 않고, 별도 DB 연결로 방 행을 `FOR UPDATE`로 잡아 만들었다(§4.1 재현 방법). 시간은 페이지에 넣은 관찰 코드(`MutationObserver`, `fetch` 감싸기)로 쟀다.
- 항목 4는 기본 설정(잠금 대기 2초)으로 확인했다.
- 항목 3·5·7은 `DB_LOCK_TIMEOUT_MS=10000`으로 앱을 다시 띄우고, "요청이 잠금 대기에 들어간 순간부터 N초 뒤에 잠금을 푼다"는 방식으로 확인했다. 코드는 바꾸지 않고 환경변수만 바꿨다.

| # | 항목 | 관찰 (+ms는 요청 시작 기준) | 판정 |
|---|---|---|---|
| 1 | 클릭 직후 로딩 | 요청 시작과 같은 시점(16~118ms)에 이미 "입장 중..." / "처리 중..."이 보인다. 문구가 요청보다 먼저 바뀐다 | ✅ |
| 2 | 처리 중 버튼 일괄 비활성화 | 목록 화면 4/4(참가 3 + 방 만들기), 상세 화면 5/5. 결론이 나면 원래 상태로 돌아간다(꽉 찬 방 버튼은 계속 꺼짐) | ✅ |
| 3 | 3초 지연 안내 | +3,011ms에 "사람이 많아 처리가 늦어지고 있습니다", +4,057ms에 200을 받아 상세로 이동 | ✅ |
| 4 | 바빠서 거절 | 목록 참가: +2,013ms에 409 → "입장하지 못했습니다. 다시 시도해 주세요", 버튼 복구. 상세 나가기: +2,010ms에 409 → "처리하지 못했습니다. 다시 시도해 주세요", 상세를 한 번 다시 조회 | ✅ |
| 5 | 5초 시간 초과 | +5,009ms에 AbortError → "입장 결과를 확인하지 못했습니다.", 버튼 복구, 자동 재조회 없음 | ✅ |

함께 발견한 것 (판정과 무관, 개선 후보):
- 7번 상황에서 [새로고침]으로 "참가 중인 방"이 보인 뒤에도 위쪽의 "입장 결과를 확인하지 못했습니다." 문구가 남는다. 목록 [새로고침]은 불러오기 실패 문구만 지우기 때문이다. 결과가 확인되면 이 문구도 지우는 편이 자연스럽다.
- 평소처럼 빠른 응답(약 16~30ms)에서도 진행 문구가 잠깐 바뀌었다가 결론 문구로 넘어간다. ADR-014에서 "감수할 점"으로 적은 동작이다.

## 5. 해석

1. **정합성은 기준선과 차이가 분명하다.** echo를 끈 기준선에서도 핫스팟 방에 9~12명이 들어가고, 같은 회원의 동시 요청은 500을 낸다. 2차는 모든 회차에서 4명, 5xx 0건, 위반 0이다.
2. **잠금 비용은 처리 한계의 약 13%다.** 순차 1건이 16.5ms에서 19.1ms로 늘었다(빠른 거절용 조회와 `SET LOCAL`). 처리 한계는 136.5에서 119.2 TPS로 줄었다. 목표 60 TPS는 한계의 50%라 여유가 충분하다(1차 echo 켬은 66%).
3. **목표 규모(s5)는 모든 기준을 통과한다.** 핫스팟 구간 p95는 802ms로 완화한 기준(1초) 안이다. 다만 표본이 작아 회차마다 435~802ms로 흔들린다. 기준을 안정적으로 판정하려면 s5를 여러 번 재서 중앙값을 써야 한다.
4. **진입 단계 상한(150)은 목표 규모에서는 동작하지 않았다(s5 409 0건).** 과부하에서의 효과는 아직 확인하지 못했다. s6은 부하 발생기가 먼저 한계에 닿아 앱에 요청이 절반쯤만 도착했다. 그래서 상한까지 쌓이지 않았고, 거절도 약 90건뿐이었다.
5. **동시 100 closed loop(s1 c=100)에서는 커넥션 풀 대기 1초 때문에 11%가 409다.** 응답 시간 상한(5초 초과 0, p95 1.05초)은 지켜졌다. 화면 기준으로는 "입장하지 못했습니다. 다시 시도해 주세요"가 뜨는 경우다.

## 7. 재측정 명령

기준선은 `c2f3f44`를 별도 worktree로 꺼내 `src/database.py`의 `echo=True`를 `False`로 바꾸고 띄운다. 2차는 현재 브랜치를 그대로 띄운다. 스키마가 바뀌므로 두 측정 사이에 측정 DB를 다시 만든다.

```bash
docker exec matchmaking-db psql -U matchmaking -d matchmaking_bench -c "DROP SCHEMA public CASCADE; CREATE SCHEMA public;"
```

측정 명령은 `loadtest/README.md` 3절과 같다. 다른 점은 `--tag`(`baseline-echooff` / `adr015`), s1 단계에 100을 더한 것, s6 `--rate 160`이다.
